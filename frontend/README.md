# Демонстрационный frontend

Один экран с тремя фиксированными датасетами, редактированием SQL, профилями частот,
бюджетами и схемой из PostgreSQL. Python-сервер последовательно подготавливает
отдельную demo-БД и запускает существующий CLI. Расчёты и HTML-отчёт выполняет ядро
IndexBudget. Спецификация интерфейса — [docs/demo-web-interface.md](../docs/demo-web-interface.md).

При первом открытии показывается тур: активный блок подсвечен,
остальной экран затемнён. «Пропустить» и Escape закрывают тур, стрелки переключают
шаги. Завершение или пропуск запоминаются в браузере; кнопка «Как это работает»
запускает обучение повторно. Введённые настройки и исходная вкладка сохраняются.
При восстановлении выполняющегося анализа автоматический тур не открывается.
Короткие подсказки `?` доступны отдельно по наведению, фокусу и нажатию.

Схема и данные берутся только из серверного шаблона, диаграмма доступна для просмотра.
Ручные частоты SQL — целые **0–1 000 000 вызовов/час**. Это модель нагрузки,
а не число выполняемых запросов. В каждом профиле нужна положительная частота,
каждый SQL должен использоваться хотя бы одним профилем. Ограничение не относится
к весам, интенсивности изменения строк и входу CLI.

«Сбросить к шаблону» возвращает исходный пример. Старые localStorage-черновики
не восстанавливают пользовательские DDL/seed и каталог; подходящий по ID/версии
workload сохраняется. JSON нагрузки можно просмотреть и скачать.

## Локальный запуск

Нужны Python 3.10+, Docker Compose и JDK 25 для CLI. Зависимостей Python, npm,
сборщика frontend и внешних шрифтов нет.

Из корня репозитория:

```sh
./gradlew --no-daemon installDist
docker compose -f frontend/compose.yaml up -d --build --wait
python3 frontend/server.py
```

Открыть <http://127.0.0.1:8090>. Если Java не выбрана системно, перед запуском
задайте `JAVA_HOME` с JDK 25. Для другого HTTP-порта используйте `--port`.

Редактор работает и без PostgreSQL/собранного CLI, но реальный анализ требует обоих.
Состояние окружения отображается вверху страницы. Для другого готового дистрибутива
CLI задайте `FRONTEND_CLI` — путь к исполняемому launcher.

PostgreSQL frontend использует Compose-проект `indexbudget-frontend`, порт
`127.0.0.1:55433` и временные данные в tmpfs. Общая demo-БД на 55432 не затрагивается.
Переменная `FRONTEND_DB_PORT` меняет порт и должна совпадать при запуске Compose
и сервера. `FRONTEND_DB_IMAGE` позволяет использовать уже собранный образ PostgreSQL
16 с HypoPG вместо стандартного `indexbudget-frontend-db:local`.

Остановка только этой БД:

```sh
docker compose -f frontend/compose.yaml stop
```

## Запуск на Linux-стенде

На стенде нужен успешный CLI-деплой и исходники `deploy/frontend/` для установщика.
Приложение берётся из проверенного CLI-релиза; локальные `.local/` и `__pycache__/`
не копируются. Нужны уже доступные Docker Compose, Python, пользовательский systemd
и CLI с JDK 25. Установщик не устанавливает
системные пакеты и не меняет firewall, Windows/WSL, чужие сервисы или cron.

```sh
bash frontend/install-stand.sh
# Эквивалент из корня репозитория:
python3 deploy/frontend/install.py
```

По умолчанию HTTP работает на **0.0.0.0:3000**, отдельная БД — на loopback:55433.
CLI закреплён на абсолютном пути успешного релиза вместе с Python/JS/CSS того же SHA.
Корни установки задаются `INDEXBUDGET_FRONTEND_ROOT` и `INDEXBUDGET_DEPLOY_ROOT`
или параметрами `--root`/`--cli-root`. Обёртка также принимает `FRONTEND_PORT`
и `FRONTEND_DB_PORT`; полный набор параметров показывает `install.py --help`.
Для стенда произвольный `FRONTEND_CLI` не используется, образ БД определяется
hash серверного build context.

Создаются пользовательский сервис `indexbudget-frontend.service` и timer
`indexbudget-frontend-update.timer`. Timer подхватывает успешно собранный CLI SHA
через минуту после предыдущего прохода. Автозапуск самого WSL и доступность
порта за пределами WSL зависят от существующего окружения стенда.

```sh
systemctl --user status indexbudget-frontend.service
journalctl --user -u indexbudget-frontend.service -n 100 --no-pager
systemctl --user restart indexbudget-frontend.service
systemctl --user stop indexbudget-frontend.service
```

Обновление приложения автоматическое после CLI-деплоя. Изменение самого
`deploy/frontend/` требует повторной установки управляющих скриптов. Задания и
отчёты хранятся в `~/indexbudget-frontend/shared/` вне релиза; первая установка
переносит старую историю с проверкой хэшей. Принятые задания при остановке
завершаются до освобождения общего lock; systemd не обрывает их после 420 секунд.
После аварийного прерывания незавершённые задания отмечаются ошибкой и не повторяются.

[Устройство updater, миграция, настройки и rollback](../deploy/frontend/README.md).
Для локального запуска без установщика можно отдельно задать `FRONTEND_DATA_DIR`;
по умолчанию данные остаются в `frontend/.local`.

Если `loginctl show-user "$USER" -p Linger` возвращает `Linger=no`, запуск после
перезагрузки зависит от входа пользователя и жизни его systemd-сессии. Установщик
не меняет эту системную настройку.

## Файлы и результаты

- `static/` — HTML/CSS/JS; редактор сохраняет черновик в localStorage браузера.
- `templates/*.json` — шаблоны с версией, DDL, заполнением, workload v2 и начальной схемой.
- `catalog.sql` — чтение фактических таблиц, колонок, индексов и FK после подготовки.
- `server.py` — API, общая очередь проверки схемы/анализа, вызов CLI и публикация.
- `.local/jobs/<UUID>/` — снимок запроса, состояние и журнал CLI; не раздаются по HTTP.
- `.local/reports/<UUID>/` — готовые артефакты; доступны как `/reports/<UUID>/report.html`.

Каталог отчёта публикуется атомарно только после экспорта HTML/JSON/SQL и снимков
входа. `completed` и `partial` открывают отчёт; при ошибке форма сохраняется.
UUID HTTP-запуска и UUID анализа CLI различаются: соответствие записано в
`demo-config.json` (`run_id`, `analysis_run_id`); оригинальный отчёт не переписывается.
`/reports/` показывает общий список. Авторизации, разделения пользователей и
автоматического удаления отчётов нет. Адрес подключения не берётся из запроса
или общего `INDEXBUDGET_DATABASE_URL`: анализ всегда работает с БД frontend.

DDL и SQL заполнения выполняются ролью `postgres` только из доверенного серверного
шаблона. `POST /api/runs` и `POST /api/schema-previews` принимают
`{template_id, template_version, workload}`; клиентские `schema_sql`/`seed_sql`
отклоняются с HTTP 400 до очереди. ID/версия проверяются, job сохраняет неизменяемый
снимок серверных DDL/seed. В `demo-config.json` эти поля описывают фактически
использованный датасет. Старый веб-клиент несовместим: после обновления перезагрузите
страницу. При изменении датасета повышайте `version` шаблона. SQL проходит
существующий AST-validator CLI, анализ подключается ролью `frontend_reader`.

## Проверки

Без Docker:

```sh
python3 -m unittest discover -s frontend/tests -v
node --test frontend/tests/test_app.js
```

С уже запущенным сервером и его отдельной БД:

```sh
python3 frontend/tests/smoke.py --url http://127.0.0.1:8090
# На стенде:
python3 frontend/tests/smoke.py --url http://127.0.0.1:3000
```

Smoke создаёт реальные отчёты всех трёх шаблонов, проверяет очередь, запрет
клиентских DDL/seed, частоты, сохранённый JSON, ошибки и восстановление после ошибки.
Это проверка HTTP/CLI/PostgreSQL, а не автоматизированная проверка браузерного UI.

Дополнительно, при установленном Playwright, с тем же запущенным сервером:

```sh
node frontend/tests/browser.cjs
# Другой адрес: FRONTEND_TEST_URL=http://127.0.0.1:8091 node frontend/tests/browser.cjs
```

Браузерная проверка проверяет старый черновик, отсутствие редакторов DDL/seed,
ошибки частот при скрытой вкладке, сохранение SQL, скачивание JSON, сброс и переход
на настоящий отчёт. Снимки 1440/390/320 px сохраняются в
`build/frontend-ui-verification/`. При нестандартной установке Chromium можно задать
`PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`, а расположение пакета Playwright — через `NODE_PATH`.

Проверки CI включают unit-тесты Python/JavaScript и сквозной smoke на отдельной
одноразовой PostgreSQL/HypoPG. Это не деплой на общий стенд.

Локально 12.11.2026 для #101 прошли 19 Python unit/HTTP-тестов, 9 Node-тестов,
сборка `installDist` и smoke с отдельной PostgreSQL 16/HypoPG: `01-records` —
`completed`, `02-shop`/`03-wide` — `partial` в режиме `fast`. Проверены прямые
запросы с DDL/seed, частоты, ошибка SQL, восстановление и согласованность артефактов.
Chromium проверил интерфейс на 1440/390/320 px, скачивание JSON и переход на реальный
отчёт; снимки просмотрены. Новый workflow проверен по YAML/shell-синтаксису,
но его запуск в GitHub Actions и обновление общего стенда здесь не выполнялись.
