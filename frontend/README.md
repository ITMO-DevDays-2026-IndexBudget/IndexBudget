# Демонстрационный frontend

Один экран с готовыми фиксированными датасетами, редактированием SQL, профилями частот,
бюджетами и схемой из PostgreSQL. Python-сервер последовательно подготавливает
отдельную demo-БД и запускает существующий CLI. Расчёты и HTML-отчёт выполняет ядро
IndexBudget. Спецификация интерфейса — [docs/demo-web-interface.md](../docs/demo-web-interface.md).

При первом открытии показывается тур: активный блок подсвечен,
остальной экран затемнён. «Пропустить» и Escape закрывают тур, стрелки переключают
шаги. Завершение или пропуск запоминаются в браузере; кнопка «Как это работает»
запускает обучение повторно. Введённые настройки и исходная вкладка сохраняются.
При восстановлении выполняющегося анализа автоматический тур не открывается.
Короткие подсказки `?` доступны отдельно по наведению, фокусу и нажатию.

Схема и данные берутся только из серверного шаблона, диаграмма доступна для просмотра.
Ручные частоты SQL — целые **0–1 000 000 вызовов/час**. Это модель нагрузки,
а не число выполняемых запросов. В каждом профиле нужна положительная частота,
каждый SQL должен использоваться хотя бы одним профилем. Ограничение не относится
к весам, интенсивности изменения строк и входу CLI.

«Сбросить к шаблону» возвращает исходный пример. Старые localStorage-черновики
не восстанавливают пользовательские DDL/seed и каталог; подходящий по ID/версии
workload сохраняется. JSON нагрузки можно просмотреть и скачать.

Вкладка **«Примеры»** и ссылка из редактора открывают библиотеку
[demo/scenarios](../demo/scenarios/README.md): девять SELECT/UPDATE/DELETE
с названиями, назначением, подсказками синтаксиса и исходными частотами.
Для неё предусмотрен датасет **«Чтение и запись»** (`04-scenarios`, seed v1),
выбранный по умолчанию при первом открытии. Он объединяет прежний «Каталог записей»
и библиотеку чтения/записи; отдельной карточки каталога больше нет.
Для остальных баз вкладка показывает стартовые SQL и частоты именно выбранного
датасета, без перехода к чужой схеме.
Кнопка **«Добавить в нагрузку»** добавляет SQL и частоты, сохраняя текущие запросы
и бюджеты. Дубли не добавляются; совпавший ID изменённого SQL не перезаписывается.
Для нового профиля берётся частота обычного дня либо первого исходного профиля,
если `normal` отсутствует; подстановка поясняется в UI.
Исходные guard и ручной набор сохраняются в workload JSON.
Для ручного источника и нагрузки только из точных SQL библиотеки в JSON включаются write rates
используемых таблиц; числа в форме сохраняются, в том числе при удалении и
повторном добавлении JOIN. Произвольный SQL разбирает CLI.
Наблюдаемый профиль и его provenance сохраняются полностью; добавление примера
не меняет источник записи и выбранную серию бюджетов.

Кнопки «Проверить схему» больше нет: схема фиксирована, подготовка БД и чтение
каталога выполняются автоматически перед анализом. Полная схема и список индексов
находятся в «Настройки анализа → Схема».
Кнопка «Показать диаграмму» открывает отдельное окно с горизонтальной SVG-схемой
выбранного датасета, масштабом 100% и прокруткой. Escape или «Закрыть» возвращает
к настройкам. Справа остаётся сводка «Твоя нагрузка», закреплённая при прокрутке
на широком экране.

SVG хранятся в `static/diagrams/` и не строятся в браузере. После изменения
шаблонов пересоберите их: `python3 frontend/generate_diagrams.py`;
проверка актуальности: `python3 frontend/generate_diagrams.py --check`.
Диаграмма показывает схему выбранного шаблона, а не результат текущего анализа.

## Интернет-магазин

«Интернет-магазин» (`02-shop`, версия 3) содержит 7 таблиц и 8 внешних ключей:
20 000 покупателей, 100 категорий, 20 000 товаров, 300 000 заказов,
1 200 000 позиций, 300 000 платежей и 210 000 доставок — всего 2 050 100 строк.
Данные синтетические и воспроизводимые. Наполнение выполняется при подготовке
выбранного датасета в отдельной frontend-БД.

В нагрузке 12 SELECT, из них 10 с INNER JOIN двух или трёх таблиц:
витрина и остатки, история и состав заказа, проверки оплат, отправка по регионам
и разбор задержек. Профили `normal` (обычный день, вес 7), `sale` (распродажа, 2)
и `fulfillment` (обработка доставок, 1) используют один список SQL с разными
частотами. Это сценарии planner cost, а не имитация конкуренции запросов.
Исходные бюджеты: 8 MiB, 120 000 условных единиц записи/ч и до 5 индексов;
ручные интенсивности изменения строк заданы для всех семи таблиц.

Запрос `orders_by_period` выбирает заказы за 10 апреля 2026 года. В профиле
обработки доставок он вызывается 18 000 раз/ч, чтобы попасть в ограниченный пул
кандидатов. `created_at` растёт вместе с физическим порядком строк; при исходном
бюджете B-tree по этому столбцу не помещается, а BRIN выбирается вместе с B-tree
для других запросов. Все три метода разрешены, индексы выбирает обычный поиск.
Проверка на PostgreSQL 16/HypoPG подтверждает смешанный набор; изменение бюджета,
SQL или частот может изменить рекомендации. Снижение planner cost не означает
измеренного ускорения запросов.

## Локальный запуск

Нужны Python 3.10+, Docker Compose и JDK 25 для CLI. Зависимостей Python, npm,
сборщика frontend и внешних шрифтов нет.

Из корня репозитория:

```sh
./gradlew --no-daemon installDist
docker compose -f frontend/compose.yaml up -d --build --wait
python3 frontend/server.py
```

Открыть <http://127.0.0.1:8090>. Если Java не выбрана системно, перед запуском
задайте `JAVA_HOME` с JDK 25. Для другого HTTP-порта используйте `--port`.

Редактор работает и без PostgreSQL/собранного CLI, но реальный анализ требует обоих.
Состояние окружения отображается вверху страницы. Для другого готового дистрибутива
CLI задайте `FRONTEND_CLI` — путь к исполняемому launcher.

PostgreSQL frontend использует Compose-проект `indexbudget-frontend`, порт
`127.0.0.1:55433` и временные данные в tmpfs. Общая demo-БД на 55432 не затрагивается.
Переменная `FRONTEND_DB_PORT` меняет порт и должна совпадать при запуске Compose
и сервера. `FRONTEND_DB_IMAGE` позволяет использовать уже собранный образ PostgreSQL
16 с HypoPG вместо стандартного `indexbudget-frontend-db:local`.

Остановка только этой БД:

```sh
docker compose -f frontend/compose.yaml stop
```

## Запуск на Linux-стенде

На стенде нужен успешный CLI-деплой и исходники `deploy/frontend/` для установщика.
Приложение берётся из проверенного CLI-релиза; локальные `.local/` и `__pycache__/`
не копируются. Нужны уже доступные Docker Compose, Python, пользовательский systemd
и CLI с JDK 25. Установщик не устанавливает
системные пакеты и не меняет firewall, Windows/WSL, чужие сервисы или cron.

```sh
bash frontend/install-stand.sh
# Эквивалент из корня репозитория:
python3 deploy/frontend/install.py
```

По умолчанию HTTP работает на **0.0.0.0:3000**, отдельная БД — на loopback:55433.
CLI закреплён на абсолютном пути успешного релиза вместе с Python/JS/CSS того же SHA.
Корни установки задаются `INDEXBUDGET_FRONTEND_ROOT` и `INDEXBUDGET_DEPLOY_ROOT`
или параметрами `--root`/`--cli-root`. Обёртка также принимает `FRONTEND_PORT`
и `FRONTEND_DB_PORT`; полный набор параметров показывает `install.py --help`.
Для стенда произвольный `FRONTEND_CLI` не используется, образ БД определяется
hash серверного build context.

Создаются пользовательский сервис `indexbudget-frontend.service` и timer
`indexbudget-frontend-update.timer`. Timer подхватывает успешно собранный CLI SHA
через минуту после предыдущего прохода. Автозапуск самого WSL и доступность
порта за пределами WSL зависят от существующего окружения стенда.

```sh
systemctl --user status indexbudget-frontend.service
journalctl --user -u indexbudget-frontend.service -n 100 --no-pager
systemctl --user restart indexbudget-frontend.service
systemctl --user stop indexbudget-frontend.service
```

Обновление приложения автоматическое после CLI-деплоя. Изменение самого
`deploy/frontend/` требует повторной установки управляющих скриптов. Задания и
отчёты хранятся в `~/indexbudget-frontend/shared/` вне релиза; первая установка
переносит старую историю с проверкой хэшей. Принятые задания при остановке
завершаются до освобождения общего lock; systemd не обрывает их после 420 секунд.
После аварийного прерывания сохранённый комплект серии восстанавливается как partial.
Остальные незавершённые задания отмечаются ошибкой; автоматически анализ не повторяется.

[Устройство updater, миграция, настройки и rollback](../deploy/frontend/README.md).
Для локального запуска без установщика можно отдельно задать `FRONTEND_DATA_DIR`;
по умолчанию данные остаются в `frontend/.local`.

Если `loginctl show-user "$USER" -p Linger` возвращает `Linger=no`, запуск после
перезагрузки зависит от входа пользователя и жизни его systemd-сессии. Установщик
не меняет эту системную настройку.

## Файлы и результаты

- `static/` — HTML/CSS/JS; редактор сохраняет черновик в localStorage браузера.
- `templates/*.json` — шаблоны с версией, DDL, заполнением, workload v2 и начальной схемой.
- `scenarios.py` — подключение общего `demo/scenarios` и seed v1 к датасету «Чтение и запись».
- `catalog.sql` — чтение фактических таблиц, колонок, индексов и FK после подготовки.
- `server.py` — API, общая очередь проверки схемы/анализа, вызов CLI и публикация.
- `.local/jobs/<UUID>/` — снимок запроса, состояние и журнал CLI; не раздаются по HTTP.
- `.local/reports/<UUID>/` — готовые артефакты; доступны как `/reports/<UUID>/report.html`.

Каталог отчёта публикуется атомарно только после экспорта HTML/JSON/SQL и снимков
входа. `completed` и `partial` открывают отчёт; при ошибке форма сохраняется.
UUID HTTP-запуска и UUID анализа CLI различаются: соответствие записано в
`demo-config.json` (`run_id`, `analysis_run_id`); оригинальный отчёт не переписывается.
`/reports/` показывает общий список. Авторизации, разделения пользователей и
автоматического удаления отчётов нет. Адрес подключения не берётся из запроса
или общего `INDEXBUDGET_DATABASE_URL`: анализ всегда работает с БД frontend.

DDL и SQL заполнения выполняются ролью `postgres` только из доверенного серверного
шаблона. `POST /api/runs` и `POST /api/schema-previews` принимают
`{template_id, template_version, workload, series?, write_source?}`;
дополнительные поля описаны в [сериях бюджетов](../docs/demo-budget-series.md)
и [источнике записи](../docs/write-profile-ui.md). Клиентские `schema_sql`/`seed_sql`
отклоняются с HTTP 400 до очереди. ID/версия проверяются, job сохраняет неизменяемый
снимок серверных DDL/seed. В `demo-config.json` эти поля описывают фактически
использованный датасет. Старый веб-клиент несовместим: после обновления перезагрузите
страницу. При изменении датасета повышайте `version` шаблона. SQL проходит
существующий AST-validator CLI. Прежние шаблоны используют `frontend_reader`;
«Чтение и запись» — отдельную `frontend_scenarios` с UPDATE(payload)/DELETE
для records и default read-only. Эти права создаются при подготовке собственной
demo-БД. Анализ выполняет только EXPLAIN, строки не меняет; роли общей БД и
прежняя SELECT-only роль не расширяются.

## Проверки

Без Docker:

```sh
python3 -m unittest discover -s frontend/tests -v
node --test frontend/tests/test_app.js
```

С уже запущенным сервером и его отдельной БД:

```sh
python3 frontend/tests/smoke.py --url http://127.0.0.1:8090
# Для локальной одноразовой Compose-БД с тем же окружением, что у сервера:
python3 frontend/tests/smoke.py --url http://127.0.0.1:8090 --verify-local-database
# На стенде:
python3 frontend/tests/smoke.py --url http://127.0.0.1:3000
```

Smoke создаёт реальные отчёты всех шести шаблонов, проверяет очередь, запрет
клиентских DDL/seed, частоты, сохранённый JSON, ошибки и восстановление после ошибки.
Это проверка HTTP/CLI/PostgreSQL, а не автоматизированная проверка браузерного UI.
Дополнительно проверяются все девять SQL библиотеки и набор без JOIN.
Флаг `--verify-local-database` проверяет права отдельной DML-роли, серверный
read-only и неизменность строк/реальных индексов; используйте его только для
собственной тестовой Compose-БД с совпадающими `COMPOSE_PROJECT_NAME`,
`FRONTEND_DB_PORT` и `FRONTEND_DB_IMAGE`. CI включает этот флаг на одноразовом runner.

Дополнительно, при установленном Playwright, с тем же запущенным сервером:

```sh
node frontend/tests/browser.cjs
# Другой адрес: FRONTEND_TEST_URL=http://127.0.0.1:8091 node frontend/tests/browser.cjs
```

Браузерная проверка проверяет старый черновик, отсутствие редакторов DDL/seed,
ошибки частот при скрытой вкладке, сохранение SQL, скачивание JSON, сброс и переход
на настоящий отчёт. Снимки 1440/390/320 px сохраняются в
`build/frontend-ui-verification/`. При нестандартной установке Chromium можно задать
`PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`, а расположение пакета Playwright — через `NODE_PATH`.

Проверки CI включают unit-тесты Python/JavaScript и сквозной smoke на отдельной
одноразовой PostgreSQL/HypoPG. Это не деплой на общий стенд.

Локально 12.11.2026 для #101 прошли 19 Python unit/HTTP-тестов, 9 Node-тестов,
сборка `installDist` и smoke с отдельной PostgreSQL 16/HypoPG: `01-records` —
`completed`, `02-shop`/`03-wide` — `partial` в режиме `fast`. Проверены прямые
запросы с DDL/seed, частоты, ошибка SQL, восстановление и согласованность артефактов.
Chromium проверил интерфейс на 1440/390/320 px, скачивание JSON и переход на реальный
отчёт; снимки просмотрены. Новый workflow проверен по YAML/shell-синтаксису,
но его запуск в GitHub Actions и обновление общего стенда здесь не выполнялись.

## Серии бюджетов (#105)

В панели бюджетов можно выбрать одиночный анализ или серию 3–5 различных значений
места (байты) либо записи (ед./ч). Серия использует один workload, один подготовленный
датасет и существующий analyze-series. Единый report.html содержит подробности вариантов;
series.json и артефакты точек доступны по локальным ссылкам. Partial сохраняет пригодные
результаты. При аварийном перезапуске сохранённый комплект серии восстанавливается
для наблюдения, без повторного анализа. Контракт API/job, тур и реальная приёмка —
[docs/demo-budget-series.md](../docs/demo-budget-series.md).

## Источник записи (#108)

В дополнительных параметрах выберите ручной профиль либо загрузите рассчитанный
`workload.json` из CLI `import-workload` с `table_write_window`. Форма переносит только

## Методы индексов и журнал событий

Все шаблоны по умолчанию включают `index_methods: ["btree", "brin", "hash"]`.
Старый черновик без поля также получает все методы с сохранением SQL и настроек;
явно заданный список сохраняется. Методы видны в сводке и скачиваемом JSON.
Правило действует для одиночного анализа и серий; default CLI без поля не меняется.

Шаблон **«Журнал событий»** (`04-events-brin`, версия 1) содержит миллион строк
с возрастающим `sequence` и 160-байтовым payload, без исходных индексов. Диапазон
`500000..510000` читается часто, все строки — редко. Бюджет по умолчанию —
**65 536 байт (0,0625 MiB)**: BRIN помещается с запасом 20%, B-tree не помещается.
Измените место на **64 MiB**, чтобы сравнить выбор B-tree. Hash включён, но
диапазоны не порождают hash-кандидатов. Чтение всех строк сохраняет пример без
улучшения cost. Это демонстрация выбора под бюджетом, а не общего превосходства
BRIN или измеренного ускорения.

`frontend/tests/smoke.py` проверяет все методы в сохранённом входе и отчёте v4,
выбор BRIN при малом бюджете, снижение cost диапазона, отсутствие эффекта на
полном чтении и выбор B-tree при большом бюджете на реальном PostgreSQL/HypoPG.

Проверено локально 12.11.2026 через HTTP → CLI → PostgreSQL 16/HypoPG:

| Бюджет | Выбранный метод | Оценка размера с запасом, байт | Baseline cost диапазона | Cost с индексом |
| --- | --- | ---: | ---: | ---: |
| 64 KiB | BRIN | 29 492 | 33 145,90 | 19 260,99 |
| 64 MiB | B-tree | 34 829 108 | 33 356,70 | 661,39 |

В обоих запусках cost чтения всех строк остался 37 500. Подготовка каждого
запуска выполняет ANALYZE, поэтому baseline может различаться из-за выборки
статистики. Числа — пример конкретных запусков, smoke проверяет свойства выбора,
а не точное совпадение costs. Артефакты локальной проверки:
`build/frontend-methods-verification/reports/`.

## Hash и B-tree для разных запросов

Шаблон **«Поиск по строковому ключу»** (`05-lookup-hash`, версия 2) содержит
200 000 записей без исходных индексов. Ключ `external_key` — `varchar(160)`
с collation C; seed воспроизводимо строит значения как `repeat(md5(i::text), 5)`.
`created_at` возрастает с шагом в одну секунду. В workload три SQL:

- `lookup_exact`: точное равенство по строковому ключу, 1000 вызовов/ч;
- `lookup_recent`: `ORDER BY created_at DESC LIMIT 50`, 100 вызовов/ч;
- `lookup_all`: чтение всей таблицы, 1 вызов/ч, контроль без пользы индекса.

При **8 MiB** выбирается hash по `external_key`. При **16 MiB** (default)
помещаются **два индекса**: hash по ключу и B-tree по `created_at` для сортировки.
Лимит числа индексов — **2**; B-tree по длинному строковому ключу превышает оба
бюджета. При увеличении бюджета весь набор заново оценивается на всех трёх SQL.

Все три метода включены. Равенство и сортировка не порождают BRIN-кандидатов,
`SELECT *` исключает INCLUDE. Это пример выбора по planner cost под бюджетом,
не обещание превосходства hash или измеренного ускорения.

Версия шаблона повышена из-за новой колонки и seed. После обновления страницы
старый черновик v1 не применяется к новому датасету; для воспроизведения
выберите шаблон заново. Старые отчёты остаются результатами прежней версии.

Smoke проверяет оба бюджета, методы и колонки выбранных индексов, снижение
cost точного поиска и сортировки при 16 MiB, отсутствие выигрыша сортировки
при 8 MiB и полного чтения при обоих бюджетах, оба CREATE INDEX в SQL.
Браузерная проверка запускает default и проверяет две карточки и подписи
`hash (external_key)` / `btree (created_at)`; размеры экрана — 1440/390/320 px.

Локальный прогон v2 на PostgreSQL/HypoPG подтвердил:

| Бюджет | Выбранный набор | Размер с запасом, байт | Cost точного поиска | Cost последних 50 записей |
| --- | --- | ---: | ---: | ---: |
| 8 MiB | hash(external_key) | 7 569 408 | 8,02 | 14 131,45 |
| 16 MiB | hash(external_key) + btree(created_at) | 14 529 332 | 8,02 | 3,88 |

Baseline: точный поиск — 11 565,77; последние записи — 14 131,45. Полное чтение
осталось 11 524 при обоих бюджетах. Это planner cost, не время выполнения;
числа зависят от статистики. Артефакты проверки —
`build/frontend-mixed-verification/reports/`.

Краткие подписи индексов в рекомендациях, карточках и отчётах серий явно
показывают каждый метод, включая `btree`, наравне с `brin` и `hash`.

## Пасхалка для DROP

При запуске анализа команда `DROP` в начале SQL открывает локальную картинку
`/drop-table.jpg`. Срабатывают и `DROP TABLE`, и `DROP DATABASE`, и другие варианты DROP.
Черновик сохраняется, задание не отправляется на сервер.
Проверка пропускает начальные комментарии; упоминания команды в комментарии или
строковом литерале не вызывают переход. Команды в середине SQL не ищутся.
Это поведение интерфейса: прямой запрос к API и CLI по-прежнему проверяет SQL
основной валидатор, который не поддерживает DROP. Картинка не заменяет эту проверку.
