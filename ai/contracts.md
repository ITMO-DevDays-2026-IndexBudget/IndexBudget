# Контракты и инварианты MVP v0.2

Это памятка для разработки и ревью, а не независимая версия JSON Schema или готовые Kotlin-сигнатуры. Полные правила и формулы задаёт [спецификация v0.2](../IndexBudget-spec-v0.2.md). Текущие Kotlin-модели и интерфейсы описаны в [docs/contracts.md](../docs/contracts.md); их согласование ведётся в [#3](https://github.com/ITMO-DevDays-2026-IndexBudget/IndexBudget/issues/3); распределение ответственности описано в [architecture.md](architecture.md) и [плане #2](https://github.com/ITMO-DevDays-2026-IndexBudget/IndexBudget/issues/2). При расхождении исправляй реализацию и эту памятку по спецификации, не вводи второй контракт молча.

## CLI и WorkloadInput

Целевой интерфейс команды:

```text
indexbudget analyze --workload <path> --output-dir <path> [--analysis-mode fast|normal|deep]
```

Подключение задаётся через `INDEXBUDGET_DATABASE_URL`. Это CLI-контракт, не HTTP API. Наличие собранного исполняемого файла и конкретный способ запуска проверяются по актуальному README и build-файлам.

| Поле / объект | Обязательный инвариант |
| --- | --- |
| `schema_version` | Целое `2`; v1 отклоняется с `UNSUPPORTED_SCHEMA_VERSION` и подсказкой перенести частоты из queries в profiles |
| `queries` | 1–20 общих SQL с уникальными ID, включая разные литералы одного шаблона; не по 20 на каждый профиль |
| `profiles` | 1–3 профиля с уникальными ID; `calls_per_hour` содержит ровно все query IDs |
| Частоты | Конечные неотрицательные; в каждом профиле есть положительная, каждый SQL используется хотя бы одним профилем |
| `weight` | Положительный конечный; нормируется как `p_s = weight_s / sum(weight)`; нормированные веса остаются положительными |
| `objective` | `robust` по умолчанию либо `mean` |
| `analysis_mode` | Необязательные `fast`/`normal`/`deep`, default `normal`; явный `null` и неверное значение — `INVALID_INPUT`; CLI `--analysis-mode` имеет приоритет |
| `storage_budget_bytes` | Обязательное неотрицательное целое, относится только к новым индексам |
| `max_indexes` | Целое 0–5; ноль означает baseline и пустой результат без генерации/поиска |
| `write_budget_units_per_hour` | Конечное неотрицательное число либо явный `null` |
| `table_write_rates` | Один общий профиль записи: все workload-таблицы, три явных неотрицательных конечных rate, `source: manual` |

При включённом write budget полный профиль записи обязателен. При выключенном его можно не передавать или передать целиком; частичный переданный профиль всё равно ошибочен. Неизвестная таблица и отсутствующий rate — ошибки. Без профиля write units равны `null`, а не нулю; при полном профиле рассчитываются даже без лимита. После resolution ключи профиля сверяются с точными физическими `schema.name`, с сохранением регистра и без разбора SQL-алиасов/кавычек. Неоднозначные ключи разных таблиц из-за точек в именах отклоняются.

Лимиты до дорогой работы: JSON ≤ 1 MiB UTF-8, каждый SQL ≤ 64 KiB UTF-8; при проверке AST — ≤ 256 сравнений WHERE/JOIN. Превышение даёт `INPUT_LIMIT_EXCEEDED`; SQL не обрезается. Все суммы, произведения, costs и отношения проверяются на конечность. Underflow положительного нормированного веса или `B_mean = 0` при положительном `B_s` — численная ошибка.

## CatalogSnapshot и ResolvedWorkload

CatalogSnapshot содержит все колонки/типы, оценку числа строк, существующие индексы и доступность статистики только относящихся к workload таблиц. Для SQL resolution он также передаёт эффективный search_path, серверный предел длины идентификаторов, идентичности типов, видимые сигнатуры сравнений и неявные преобразования: совпавшее имя не доказывает встроенную семантику типа/оператора. Ширина таблицы не ограничена 16 колонками. Снимок не обещает неизменность внешней БД во время анализа; воспроизводимость demo обеспечивается отдельно.

ResolvedWorkload сохраняет исходный текст и ID каждого SQL, все разрешённые таблицы, общие профили и признаки WHERE/JOIN/ORDER BY по физическим колонкам. Алиасы не создают новые идентичности. AST проверяется целиком по разрешённому поднабору, а все имена — до shortlist. SQL со 100 условиями не теряет остальные условия после отбора 16 колонок для генерации. Проекция SELECT и `*` проверяются, но не создают кандидатов сами по себе.

JSqlParser AST и JDBC connection не должны становиться частью общего DTO для генератора/метрик/HTML. Поддержанный SQL и ошибки unsupported-конструкций определены разделом 3 спеки и задачами [#6](https://github.com/ITMO-DevDays-2026-IndexBudget/IndexBudget/issues/6), [#8](https://github.com/ITMO-DevDays-2026-IndexBudget/IndexBudget/issues/8), [#9](https://github.com/ITMO-DevDays-2026-IndexBudget/IndexBudget/issues/9).

## IndexCandidate и ограниченный пул

ID определяется канонической структурой `schema, table, method, ordered keys, directions, nulls, collation, opclass`, имя — стабильное `ib_<hash>`. Один renderer формирует DDL с полностью квалифицированной таблицей и экранированными идентификаторами для HypoPG и экспорта. OID HypoPG не является стабильным candidate ID.

Кандидат сохраняет происхождение — уникальные query IDs — и лучший приоритет группы составного индекса среди источников. Дедупликация объединяет происхождение. Удаление точного реального дубля требует валидного доступного обычного B-tree без predicate/expressions/INCLUDE и полного совпадения ключей и их параметров. `(a,b)` не заменяет `(a)`; partial `(a)` не заменяет общий `(a)`.

| Этап | Граница и диагностика |
| --- | --- |
| Признаки на `(query, table)` | ≤ 16 физических колонок до образования пар; `COLUMN_SHORTLIST_TRUNCATED` с исключёнными колонками |
| Локальная генерация | Каждая упорядоченная пара один раз, ≤ 4 варианта направления; ≤ 976 событий на область, ≤ 58 560 всего |
| Локальный список после канонизации/реальных дублей | ≤ 32, сначала одиночные, затем пары по приоритетам спеки; `LOCAL_CANDIDATE_LIMIT` |
| Объединение | ≤ 1920 локальных записей до общей дедупликации, происхождение объединяется |
| Общий shortlist | ≤ 16 через round-robin профилей с чередованием очередей одиночных/пар; `GLOBAL_CANDIDATE_LIMIT` |

Рейтинг использует нормированные внутри профиля частоты `u_s(q)`, а не абсолютный трафик или `weight`. `u_s` применяется только к генерации, не к целевой функции. Порядок и приоритеты полностью определены разделом 5 спеки. Кандидат не получает оценки size/cost до соответствующего обращения к evaluator; неизвестные значения остаются неизвестными. Размеры вычисляются только для финального shortlist; после бюджетного отсева вытесненные кандидаты не подставляются обратно.

Счётчики отражают фактически обнаруженные/перечисленные/дедуплицированные/оставленные элементы. Полное число неперечисленных вариантов — `null`. Статус отсечения не означает «индекс бесполезен».

Production-реализация — `ProfileAwareCandidateGenerator` (#12): одна локальная область обрабатывается
целиком до следующей, между областями остаются только survivors. В `LocalGenerationStatistics`
дополнительно фиксируется `candidatesAfterExistingDeduplication`, чтобы не смешивать канонизацию,
удаление реальных дублей и cap 32. Детали диагностик и очередей — в
[текущих Kotlin-контрактах](../docs/contracts.md#полный-shortlist-кандидатов-12).

## EvaluationResult

`evaluate(S)` оценивает весь набор новых индексов при сохранённых реальных индексах. Baseline — `S = empty`. Результат содержит полный `cost_by_query_id` и планы всех общих SQL; cost берётся из корневого `Plan.Total Cost`. Дочерние costs дополнительно не суммируются.

- Одна выделенная backend session: reset → создать ровно `S` → EXPLAIN всех query IDs в стабильном порядке → полный результат → cleanup в `finally`; при необходимости сначала rollback.
- Ошибка одного EXPLAIN обесценивает весь результат набора. Частичный вектор не участвует в метриках, cache успешных оценок или incumbents.
- Несколько профилей не вызывают новых EXPLAIN: метрики считаются в памяти над общим вектором.
- Cache существует только внутри запуска; ключ — отсортированный набор candidate IDs, значение — полная оценка. Ошибочные наборы помечаются отдельно и не повторяются.
- Сохраняются планы baseline и обоих текущих incumbents. Финальный экспорт не запускает EXPLAIN заново.

## Метрики, бюджеты и компаратор

Единственная реализация находится в модуле [#16](https://github.com/ITMO-DevDays-2026-IndexBudget/IndexBudget/issues/16). Search и отчёты потребляют готовые расчёты. Для профиля `s`:

```text
C_s(S) = Σ f_s(q) * cost(q,S)
B_s = C_s(empty)
C_mean(S) = Σ p_s * C_s(S)
B_mean = C_mean(empty)
M(S) = C_mean(S) / B_mean
R(S) = max(C_s(S) / B_s для B_s > 0)
```

`M` — отношение сумм, а не среднее профильных отношений. Все профили участвуют в `R` независимо от веса. При `B_s = 0` отношение и процент — `null`, абсолютные значения сохраняются; допустимый набор должен сохранить `C_s(S) = 0`, иначе `ZERO_BASELINE_REGRESSION`. При всех нулевых baseline возвращается пустой набор, `M/R = null`, поиск не запускается.

`MetricsCalculator.calculate` возвращает сырые `SetMetrics`. Для принятия оценки используется отдельный от предварительного `assessBudget` метод `assessEvaluation(workload, baseline, evaluation, usage)`: он вызывает тот же расчёт и возвращает `EvaluationAssessment`. `Accepted` содержит метрики и `searchRequired`; значение `false` означает все нулевые baseline. `Rejected` сохраняет метрики и список `AnalysisError` с `ZERO_BASELINE_REGRESSION` и `profileId` каждого нарушившего правило профиля, упорядоченный по ID. Это отказ набору, не исключение и не численный сбой; сами численные ошибки по-прежнему передаются как `AnalysisException(NUMERIC_ERROR)`.

Pipeline использует `Accepted.searchRequired` после полного baseline и завершает baseline-only запуск до генерации/размеров/поиска. Optimizer после каждой полной оценки проверяет `EvaluationAssessment`: rejected набор не сравнивается и не обновляет `bestRobust`/`bestMean`; причина сохраняется, поиск продолжается. `EvaluatedConfiguration` запрещает rejected метрики и непустые IDs при baseline-only, а условие жадного шага запрещает rejected метрики напрямую. Эти проверки защищают внутренний контракт; штатный потребитель должен обработать `Rejected` до создания конфигурации. Greedy и ограниченный repair реализованы в `LimitedRepairOptimizer`; пример стыка и текущие ограничения — в [docs/contracts.md](../docs/contracts.md#допустимость-после-оценки-43).

Для сравнения конечные R/M округляются HALF_EVEN до 9 десятичных знаков (`r/m`); исходные значения сохраняются. Минимизируются лексикографические ключи:

```text
robust: (r, m, budgeted_bytes, write_units?, sorted_ids)
mean:   (m, r, budgeted_bytes, write_units?, sorted_ids)
```

`write_units` присутствует только при полном профиле записи. Сравнение через «разница меньше epsilon» не заменяет транзитивный компаратор.

Размер: `estimated_bytes = hypopg_relation_size`, `budgeted_bytes = ceil(1.2 * estimated_bytes)`; бюджет проверяется по сумме второго значения. Write units индекса — сумма insert/update/delete rates его таблицы, умноженная на число ключевых колонок; все UPDATE учитываются. Размеры и write units суммируются по набору, а полезность сочетания требует оценки всего набора. Нулевой write budget допускает только нулевые write units.

Planner cost не является временем; write units не являются измеренным замедлением записи. Они не складываются в произвольный общий score. В v0.2 отсутствует старый score «выигрыш / доля бюджета».

## SearchResult и RunContext

SearchResult содержит выбранный objective, лучший полный допустимый набор для него, оба incumbents, причины решений/остановки и счётчики. Каждый полный допустимый результат обновляет robust и mean из одного общего пула, включая baseline. Результат не обязан совпасть с последним звеном greedy. `Optimizer` публикует оба сохранённых incumbents через `SearchCheckpoint` перед следующей операцией, чтобы pipeline мог завершиться partial после ошибки без нового EXPLAIN.

Greedy продвигается только при строгом лексикографическом улучшении первых двух компонентов выбранного критерия; plateau по R с улучшением M допустим. Среди пригодных добавлений выбирается минимальный полный ключ. Нулевая одиночная польза не исключает кандидата из repair.

Зарегистрированный в Spring `LimitedRepairOptimizer` выполняет greedy и repair. Repair использует зафиксированный после greedy лучший набор `S0`, очереди `0→2`, `1→1`, `1→2` и до 8/28/256 новых попыток для `fast`/`normal`/`deep`. Очереди обходятся round-robin и не перестраиваются после улучшения. Cache hits не тратят попытку, новая неуспешная оценка тратит. Ранее ошибочные наборы пропускаются. Порядок соседей определён разделом 7 спеки; рейтинг одиночных эффектов задаёт очередь, но не подменяет оценку комбинации. Консервативная граница соседства — 450 структур до фильтрации; верхняя оценка greedy + repair с baseline только для `normal` — 99 наборов / 1980 EXPLAIN при 20 SQL; для `deep` она не заявляется. `GreedyOptimizer` остаётся отдельной стратегией только жадного этапа.

RunContext общий для стадий: монотонное время, deadline, число попыток EXPLAIN, полных наборов и cache hits. Пресеты задают command/search/EXPLAIN/repair: `fast` — 30 с/20 с/500/8, `normal` — 90 с/60 с/2000/28, `deep` — 300 с/240 с/10000/256. Для всех пресетов EXPLAIN ограничен минимумом 2 секунд и остатка, подключение — минимумом 5 секунд и остатка. Выбор режима не сбрасывает часы команды; общий и поисковый deadline применяются совместно. Прежний JSON без `analysis_mode` сохраняет `normal`; расширение совместимо в v2. Кэш не расходует EXPLAIN; ошибки расходуют. Ограничение времени передаётся и CPU-коду, и SQL-адаптеру; подробности владения сессией — в architecture.md. Потокобезопасный `cancel()` делает следующие проверки ошибкой `CANCELLED`. `enterReport()` допускает сохранение уже вычисленного результата после остановки, не продлевая бюджет. `observeProgress` подключает CLI к реальным снимкам стадий и счётчиков.

| Статус | Значение |
| --- | --- |
| `completed` | Предусмотренный ограниченный поиск завершён; candidate caps допустимы с warnings |
| `partial` | Есть полный baseline и пригодный результат, но не всё выполнено из-за времени, EXPLAIN/repair лимита, потери соединения, кооперативной отмены или неполных/ошибочных оценок |
| `failed` | Нет полного baseline либо вход/каталог/числа не позволяют получить корректный сравнимый результат |

`REPAIR_LIMIT` с partial требуется, если исчерпан выбранный предел новых попыток и остались непроверенные допустимые соседи. Ошибка создания одного кандидата даёт исключение с warning; её нельзя путать с потерей соединения. Причины exact duplicate, три уровня shortlist, budget, hypothesis error, отсутствие пользы на шаге, not selected и not evaluated due to limits сохраняются отдельно.

## AnalysisReport и завершение процесса

`report.json` содержит `schema_version: 2`, `spec_version: "0.2"`, run ID, hash входа, версии/длительность, objective, эффективный `analysis_mode`, все эффективные лимиты, нормированные веса, бюджеты/write profile, baseline, выбранный набор, costs/plans по SQL, профильные метрики, обе оценки размера, warnings и счётчики.

Hash — SHA-256 от UTF-8 JSON с рекурсивной сортировкой ключей без пробелов, с сохранением строк SQL и порядка массивов. Нормализация для hash не переписывает SQL и не включает применённые defaults или CLI-переопределение режима. JSON/HTML/SQL относятся к одному run ID/hash и выбранному набору.

Поля `best_robust`, `best_mean`, `comparison_scope: "evaluated_sets"`, `selected_objective` обозначают сравнение в одном исследованном пуле. Это не обещание двух независимых поисков или глобального оптимума. Цена устойчивости — `C_mean(best_robust) - C_mean(best_mean)` в этом пуле; совпавшие наборы показываются явно. Per-query регрессии выделяются, но hard guard для каждого SQL не заявлен.

HTML автономен, без CDN; он отображает метрики общей модели и экранирует SQL/имена/сообщения как текст. SQL содержит только выбранные индексы и заголовок с run ID/hash; не выполняется автоматически. DSN/пароли исключены из логов и артефактов.

Вывод сначала готовится во временных файлах с run ID. Output-dir с прежними артефактами отклоняется; ошибка не оставляет смесь старого SQL и нового отчёта. При failed успешный `indexes.sql` не создаётся.

| Код выхода | Значение |
| --- | --- |
| `0` | completed |
| `2` | Невалидный или неподдержанный вход |
| `3` | partial с сохранённым результатом |
| `1` | Прочий failed или ошибка записи артефактов |

В stderr — стадии validation/introspection/baseline/candidates/greedy/repair/report, эффективные режим и все шесть лимитов, фактические EXPLAIN/evaluation/repair attempts, completed evaluations и cache hits, итоговый статус и причины остановки, без выдуманного процента прогресса. JSON и HTML сохраняют те же значения без дополнительных EXPLAIN. Ошибка имеет `code`, `message` и при необходимости `query_id`, `profile_id`, `details`.

## Как менять контракт

При изменении CLI, JSON, межмодульной модели или артефактов проверь всё затронутое изменение целиком:

1. Зафиксируй смысл поля/параметра, обязательность, единицы, допустимые значения, default и различие `null`/нуля/ошибки в спецификации. Для несовместимого изменения явно определи версию и поведение старого формата; не принимай его молча с новым смыслом.
2. Обнови producer, всех consumers, валидацию, сериализацию и связанные фикстуры. Изменение внутреннего DTO не требует публичного schema bump само по себе, если внешний формат и смысл не меняются.
3. Синхронизируй примеры входа, CLI help/README и примеры результата: хотя бы основной успешный сценарий и затронутую ошибку/partial. Пример не должен обходить новые обязательные проверки.
4. Сохрани согласованность JSON/HTML/SQL и exit codes. Если меняется алгоритм или формула, обнови ожидаемые результаты и документацию вместе с реализацией.
