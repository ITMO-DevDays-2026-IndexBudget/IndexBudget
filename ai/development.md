# Разработка IndexBudget

Этот документ описывает работу над кодом. Для задачи «проведи ревью» действуют [отдельные правила](review.md): в режиме ревью тесты не запускаются. Во время реализации и исправления кода выполняйте проверки, соразмерные изменению.

Требования к поведению задаёт [спецификация v0.2](../IndexBudget-spec-v0.2.md). Границы модулей и обмен данными описаны в [архитектуре](architecture.md) и [контрактах](contracts.md). Общие инструкции агенту — в [AGENTS.md](../AGENTS.md), навигация — в [ai/README.md](README.md).

## Как работать над задачей

1. Прочитайте issue и связанные разделы спецификации. Разделите требуемый PoC-срез и критерии полного MVP; определите, какие интерфейсы затрагивает изменение.
2. Проверьте текущее состояние репозитория и существующую реализацию. Сохраните чужие незакоммиченные изменения. Уровень задачи задаёт порядок координации, а не запрет начать независимый модуль на согласованных фикстурах.
3. Реализуйте минимальный законченный результат в своей области. При изменении общего контракта одновременно обновите его потребителей, фикстуры и документацию; не оставляйте параллельные несовместимые версии формул или DTO.
4. Проверьте поведение подходящим способом и просмотрите diff. В итоговом описании укажите, что теперь работает, какие проверки выполнены и какие ограничения остаются. Не называйте незапущенные проверки пройденными.

Состояние проекта меняется: сначала прочитайте актуальные README, build scripts, wrapper и конфигурацию CI. Планируемый стек — Kotlin/JVM, JDK 25 LTS, Gradle Kotlin DSL, Spring Boot CLI (`WebApplicationType.NONE`), Jackson, PostgreSQL JDBC, JSqlParser и PostgreSQL 16 + HypoPG. Это не утверждение, что все зависимости и команды уже настроены.

Контракт команды — `indexbudget analyze --workload <path> --output-dir <path> [--analysis-mode fast|normal|deep] [--candidate-ranking frequency|baseline_cost]`, подключение — через `INDEXBUDGET_DATABASE_URL`. Не придумывайте готовые Gradle tasks, путь к исполняемому файлу или имя Compose-сервиса. Используйте команды сборки и запуска из [README](../README.md) и существующие стыки из [docs/contracts.md](../docs/contracts.md). Orchestration `AnalysisPipeline` уже есть; `analyze` пока возвращает `NOT_IMPLEMENTED` со списком отсутствующих зависимостей. Не выдавайте проверку orchestration с подставными компонентами за готовый сквозной анализ с БД.

## Kotlin и границы классов

Следуйте принятым в репозитории соглашениям и форматтеру, если они уже настроены. До их появления используйте стандартный стиль Kotlin: понятные имена, небольшие функции, `val` и неизменяемые данные по умолчанию. Не вводите новый framework или слой абстракции ради небольшой задачи.

- Доменные модели и расчёты не зависят от Spring, JDBC и JSqlParser AST. Spring связывает компоненты в точке запуска; внешние библиотеки остаются за адаптерами.
- Типы выражают различия, которые влияют на поведение: objective, статус запуска, ошибка входа, недействительная конфигурация и причина остановки не должны быть неразличимыми строками. Закрытые варианты удобно описывать `enum` или `sealed` типами, данные — `data class`.
- Явно различайте ноль, отсутствие данных и ошибку. `null` для неизвестных write units, размеров или отношений не заменяется нулём. Не используйте `!!` для входных данных и результатов БД вместо проверки.
- Изменяемое состояние держите у его владельца: соединение — у сессии, кэш и текущие лучшие наборы — у поиска, deadline и счётчики — в согласованном контексте запуска. Избегайте глобальных mutable singleton и скрытого состояния между запусками.
- Детерминированный порядок задавайте явно через стабильные IDs. Порядок обхода `HashMap`/`HashSet`, выдачи каталога и OID HypoPG не является частью алгоритма.

| Компонент / модель | Его ответственность |
| --- | --- |
| CLI / application | Разбор параметров, валидация, последовательность стадий, жизненный цикл, exit codes. Не реализация формул поиска. |
| `WorkloadInput`, `Profile` | Общие SQL и профили их частот. Один SQL не копируется для каждого профиля. |
| `CatalogSnapshot`, `ResolvedWorkload` | Факты каталога и все разрешённые признаки исходного SQL. Ограничение кандидатов не меняет SQL. |
| `IndexCandidate` / CandidateGenerator | Каноническая структура, стабильный ID, происхождение, ограниченная генерация и причины отсечения. |
| `AnalysisSession` / ConfigurationEvaluator | Одна физическая JDBC-сессия, размеры, полная оценка набора, plans/costs по query ID, очистка ресурсов. |
| Модуль метрик / компаратор | Единственная реализация расходов, допустимости, метрик профилей и сравнения `robust`/`mean`. |
| Optimizer / `SearchResult` | Выбор следующего набора, greedy/repair, кэш и оба лучших результата из общего пула. Не копия формул метрик. |
| `AnalysisReport` / renderer | Экспорт уже полученных данных. Без нового EXPLAIN, пересчёта формул другим способом и изменения выбранного набора. |

Названия здесь обозначают согласованные роли; это не требование создавать класс на каждую строку или переписывать работающую структуру файлов без причины.

## Инварианты реализации

Ограничения и точные формулы сверяйте со спецификацией. При изменении затронутого участка особенно проверьте следующее:

- `EvaluationResult` успешен только для полного общего списка SQL. Профили считаются в памяти над одним вектором; число профилей не умножает EXPLAIN. Эффект комбинации не равен сумме одиночных выгод.
- `M` — отношение ожидаемой стоимости к её baseline, а не среднее нормированных отношений. Все профили участвуют в худшем критерии независимо от веса. Компаратор использует округление до 9 знаков HALF_EVEN; сравнение через нетранзитивный «epsilon» не подходит.
- Нечисловые, отрицательные costs, переполнение и потеря положительного нормированного веса дают явную ошибку. При нулевом baseline отношения остаются `null`; правила `ZERO_BASELINE_REGRESSION` и baseline-only выполняются до сравнения результатов.
- Размер с запасом считается для каждого индекса как `ceil(1.2 × estimated_bytes)`, затем суммируется. Выбирайте представление чисел и проверки переполнения так, чтобы граница бюджета не нарушалась из-за округления. Write units остаются условной моделью, а cost — единицами планировщика.
- Рейтинг `frequency` сохраняется по умолчанию; экспериментальный `baseline_cost` использует нормированные частоты и сохранённые costs пустого набора только в общем shortlist. Передавай полный baseline через стык генератора без нового EXPLAIN и копии профильных метрик. Проверяй редкий дорогой SQL, zero baseline, числовые границы/ошибки нормирования, веса, tie-break, сценарные квоты, арность и INCLUDE/OR. [Правила рейтинга](../docs/candidate-ranking.md).
- Каталог и SQL resolution поддерживают все колонки широкой таблицы. Ограничения применяются до образования пар: 16 колонок на `(query, table)`, 32 локальных кандидата, начальные 16 и резерв до 48, финальные 16 допустимых; исходный SQL не обрезается. Отсечения и неизвестные оценки сохраняются для отчёта.
- Greedy использует единый компаратор. Repair проходит соседей одного фиксированного `S0` с лимитом выбранного пресета (8/28/256 новых попыток для `fast`/`normal`/`deep`); улучшение не запускает рекурсивный обход. Оба incumbents обновляются из одного общего пула полных допустимых оценок.
- Кэш живёт только внутри запуска. Ошибочные наборы отмечаются отдельно, неполные оценки не кэшируются как успешные. Планы baseline и текущих incumbents сохраняются для экспорта без повторной оценки.

## Ошибки, время и ресурсы

Возвращайте ошибки с устойчивым кодом и понятным сообщением; добавляйте query/profile ID, когда он известен. Не ловите все исключения с возвратом пустого набора, нулевого cost или статуса `completed`. Не скрывайте отмену как обычную кандидатную ошибку.

Одна `AnalysisSession` владеет одним физическим connection. `evaluate(S)` создаёт ровно S и оценивает все SQL, затем очищает гипотезы в `finally`. После ошибки транзакции перед reset нужен rollback. `Statement` и `ResultSet` закрываются в пределах их использования; кто закрывает connection, видно из контракта. Не возвращайте соединение с гипотезами в общий пул.

Используйте общий `RunContext` и монотонные часы. Счётчик увеличивается перед фактически начатым EXPLAIN, включая неудачные. `AnalysisMode` задаёт пределы команда/поиск/EXPLAIN/repair: `fast` — 30 с/20 с/500/8, `normal` — 90 с/60 с/2000/28, `deep` — 300 с/240 с/10000/256. Необязательный JSON `analysis_mode` по умолчанию `normal`; CLI `--analysis-mode` имеет приоритет. Выбор режима не перезапускает часы и не меняет source JSON hash. Поиск получает минимум общего deadline и своего бюджета, начатого до baseline. Таймаут одного EXPLAIN — минимум из 2 секунд и остатка, подключения — из 5 секунд и остатка. Другой SQL также ограничен оставшимся временем.

Проверяйте deadline и в CPU-проходах, до/после стороннего парсера. Не добавляйте собственные несогласованные таймеры в каждый модуль. После исчерпания времени не запускайте новый SQL ради cleanup: отмените незавершённый запрос и физически закройте/прервите соединение. Не обещайте точное время возврата при задержке драйвера, сети или записи отчёта. Старые 99 наборов / 1980 EXPLAIN относятся только к обычному режиму; `deep` не гарантирует улучшение. Режим, все шесть эффективных лимитов, фактические счётчики и остановка должны согласованно отображаться в CLI/JSON/HTML.

Без полного baseline нельзя получить корректный `partial`. При остановке с полным baseline сохраняется лучший полный допустимый результат с причиной ограничения; численная ошибка или некорректный вход не превращаются в успешный partial. Само отсечение кандидатов означает warning, а не незавершённый поиск. Правила завершения repair, `completed`/`partial`/`failed` и exit codes берите из спецификации.

## SQL и артефакты

До оценки допускается только поддержанный и разрешённый через каталог SELECT либо ограниченный однотабличный UPDATE/DELETE (#103, [границы DML](../docs/dml-analysis.md)). Проверяйте AST, а не регулярные выражения. Не меняйте SQL ради того, чтобы он прошёл валидацию, и не игнорируйте неподдержанные конструкции или отдельные запросы.

Генерируемый DDL строится из проверенной канонической структуры; идентификаторы квалифицируются и корректно экранируются. Значения в запросах каталога передаются параметрами там, где это поддерживается. Не используйте простую конкатенацию непроверенных имён и не считайте placeholder заменой экранирования SQL-идентификатора.

Команда анализа вызывает EXPLAIN **без ANALYZE**, использует HypoPG и не создаёт реальные индексы. Seed, установка расширения и физические эксперименты отделены от анализа. Для реальных измерений используйте явно выбранную воспроизводимую тестовую БД и отдельный запуск; не расширяйте полномочия runtime role ради удобства.

DSN и пароли не попадают в логи, отчёты, SQL и тексты ошибок. HTML выводит SQL/идентификаторы как экранированный текст. Экспорт проверяет согласованность run ID, hash и выбранных индексов, не смешивает прежние артефакты с новыми и не оставляет успешный `indexes.sql` после failed.

## Проверки при разработке

Сначала найдите реальные команды проверки и зависимости в репозитории. Запускайте проверки, относящиеся к изменённому поведению; расширяйте набор при новой ошибке, изменении общего контракта или необъяснённом риске. Не добавляйте тесты, которые повторяют строки реализации, ради числа тестов. Для исправления ссылок в документации обычно достаточно проверки ссылок и diff.

- **Метрики:** небольшой числовой пример с заранее известным результатом; отношение сумм, zero baseline, finite/overflow, plateau, равенства, точные границы бюджетов.
- **Поиск:** fake evaluator с независимо заданными полными стоимостями наборов; взаимодействие индексов, ловушка `1→2`, синергия `0→2`, оба incumbents, счётчики, кэш, неполный результат и остановка по лимиту. Тест не должен получать ожидаемый ответ тем же компаратором, который проверяет.
- **SQL и кандидаты:** поддержанный/отклонённый AST, неоднозначные и quoted имена, настоящая структура каталога; 100 колонок, caps до пар, исходный SQL без обрезания, происхождение и детерминированные очереди профилей. Для рейтинга — сравнение `frequency`/`baseline_cost` при одинаковых SQL, budgets, финальной мощности пула и лимитах поиска с сохранением состава shortlist, результатов и затрат. Для refill — бюджетный отсев первых 16, редкий профиль/равные рейтинги, резерв до 48, не более 32 size-вызовов с ошибками, ранняя проверка write budget, исчерпание резерва/deadline и фиксированный пул без refill внутри бюджетных точек.
- **Адаптер БД:** PostgreSQL + HypoPG для изоляции сессий, baseline с реальными индексами, cleanup/rollback/cancellation и повторного запуска. Mock JDBC не доказывает эти свойства.
- **Отчёт и CLI:** согласованность JSON/HTML/SQL, неизвестные значения, отсутствие секретов, HTML escaping, статусы/exit codes и ошибка экспорта.

Фикстуры позволяют параллельно разрабатывать модули, но не заменяют сквозную проверку с PostgreSQL. Сравнения `robust`/`mean` и greedy/repair проводятся раздельно: при проверке одного фактора остальные условия фиксируются. Малый полный перебор — отдельный проверочный инструмент с собственным deadline, а не ветка production CLI. Реальное время, размер, planner cost и write units показываются раздельно; отсутствие выигрыша также является результатом.

## PoC и полный MVP

[Общий план #2](https://github.com/ITMO-DevDays-2026-IndexBudget/IndexBudget/issues/2) задаёт владельцев и зависимости. Изменение в чужом модуле согласуйте через его контракт и конкретную необходимость; не создавайте вторую реализацию только ради независимости от участника.

[PoC #22](https://github.com/ITMO-DevDays-2026-IndexBudget/IndexBudget/issues/22) — ранний сквозной срез к концу 11.11: одна таблица, три SELECT, два профиля, до восьми автоматически полученных кандидатов, полный ручной write profile и оба бюджета. Реальная цепочка заканчивается HTML/JSON/SQL; базовые ошибки, таймауты и cleanup уже обязательны. Полный repair не является барьером этого среза.

[Полный MVP #21](https://github.com/ITMO-DevDays-2026-IndexBudget/IndexBudget/issues/21) включает все ограничения v0.2, широкий SQL/candidate сценарий, repair/cache/partial, обязательные проверки и раздельные эксперименты. Не закрывайте полную задачу по одному PoC-срезу и не расширяйте scope на React, HTTP, LLM/RL или автоматические миграции без соответствующего изменения задачи и спецификации.
