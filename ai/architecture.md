# Целевая архитектура IndexBudget

Это целевая архитектура полного MVP. CLI, orchestration `AnalysisPipeline` и общие интерфейсы уже существуют. Реальный сквозной запуск ещё зависит от неподключённых модулей. Текущие стыки описаны в [docs/contracts.md](../docs/contracts.md), состояние реализации и команды запуска — в [README](../README.md). Источник требований — [спецификация v0.2](../IndexBudget-spec-v0.2.md); последовательность работ и владельцы — [issue #2](https://github.com/ITMO-DevDays-2026-IndexBudget/IndexBudget/issues/2). До изменения кода проверь фактическую структуру репозитория. Не создавай ещё один каркас, если нужный компонент уже появился. Порядок работы — в [development.md](development.md), проверки изменений — в [review.md](review.md).

## Окружение и граница приложения

Целевой стек: Kotlin/JVM, JDK 25 LTS, Spring Boot с `WebApplicationType.NONE`, Gradle Kotlin DSL, Jackson, PostgreSQL JDBC. Для PostgreSQL 16, HypoPG и воспроизводимого demo seed предусмотрен Docker Compose; готовность demo проверяй по фактическим файлам проекта. Версии зависимостей и точные команды сборки бери из build-файлов, Gradle wrapper и README.

Обычная команда `analyze` выполняет один анализ и экспортирует локальные HTML/JSON/SQL. `analyze-series` выполняет общую подготовку и 3–5 независимых бюджетных точек с отдельными каталогами и машинной сводкой [по контракту серии](../docs/budget-series.md). HTTP API, React, worker-сервер и polling не входят в MVP. Анализ предлагает дополнительные индексы, сохраняя реальные индексы в baseline. Он не применяет рекомендации и не выполняет `EXPLAIN ANALYZE` или автоматический `ANALYZE` на целевой БД.

Не переносить формулы в SQL-адаптер, HTML или вторую реализацию поиска. Search получает evaluator и критерий как отдельные зависимости. Метрики должны проверяться на фиксированных векторах costs без PostgreSQL; SQL и кандидаты — на CatalogSnapshot/ResolvedWorkload без JDBC; HTML — на AnalysisReport без запуска поиска.

## Поток данных

```text
WorkloadInput / Profile
  → проверка размера и формы JSON, разбор AST
  → CatalogSnapshot только нужных таблиц + разрешение всех имён
  → ResolvedWorkload и проверка полноты общего write profile
  → baseline evaluate(empty)
  → ограниченная генерация → канонизация → shortlist → размеры / write units
  → Search(objective, budgets) ↔ evaluate(S) → cost_by_query_id
  → единые метрики и компаратор → SearchResult
  → AnalysisReport → report.json / report.html / indexes.sql
```

Разбор AST выявляет таблицы для чтения каталога; семантическое разрешение использует полученный снимок. Генератор получает разрешённые признаки и сохранённый полный baseline пустого набора, а не JSqlParser AST. `WorkloadInput.candidateRanking` выбирает `frequency` (default) или экспериментальный `baseline_cost`: сумму `u_s(q) × cost(q, empty)` только для порядка общего shortlist. Дополнительный EXPLAIN и профильные метрики в генераторе не нужны; локальные caps, INCLUDE-квоты, OR-provenance, сценарные ходы и арность ключей сохраняются. [Формула и числовые границы](../docs/candidate-ranking.md). Валидация SQL проверяет все колонки до shortlist; ограничение признаков не меняет SQL, передаваемый в EXPLAIN.

После полного baseline возможен ранний результат с пустым набором: нулевой бюджет места, `max_indexes = 0` или все профильные baseline costs равны нулю. Эти случаи не требуют генерации и поиска. При обычном ходе ограничение признаков выполняется до образования пар: максимум 16 колонок на область, 32 локальных кандидата после канонизации/дублей, начальный shortlist до 16 и продолжение той же очереди в резерв до 48. Подготовка с бюджетным отсевом и refill передаёт поиску до 16 допустимых кандидатов. Детали детерминированного отбора находятся в разделе 5 спеки; не заменять его сортировкой только по абсолютным частотам.

Оценка набора возвращает стоимость каждого общего SQL один раз. Частоты 1–3 профилей применяются к этому вектору в памяти, поэтому профили не умножают число EXPLAIN. Каждая полностью оценённая допустимая конфигурация обновляет и robust-, и mean-incumbent. HTML показывает альтернативы из этого общего пула, а не два независимо завершённых поиска.

## Владение ресурсами и лимитами

CLI создаёт RunContext в начале команды, выбирает `AnalysisMode` до открытия БД без сброса часов и передаёт контекст pipeline, который отвечает за завершение запуска. Адаптер владеет одной выделенной физической JDBC-сессией на анализ; возврат соединения в пул между гипотезами нарушает контракт HypoPG. Pipeline вызывает закрытие ресурсов в `finally` при успехе, ошибке, timeout и отмене. Контракт `AnalysisSession.cancel()` требует безопасной межпоточной отмены активного SQL и освобождения физического соединения. JVM shutdown hook инициирует её при SIGINT, однако сохранение отчёта при завершении JVM не гарантируется. Кооперативная отмена в продолжающем работу процессе даёт `CANCELLED` и обычный failed/partial по наличию пригодного результата.

Для `evaluate(S)` адаптер очищает предыдущие гипотезы, создаёт ровно `S`, выполняет EXPLAIN по общим query IDs в стабильном порядке и возвращает результат только после всех SQL. В `finally` он очищает HypoPG; после сбоя транзакции сначала выполняется rollback. Нельзя продолжать с частичным cost-вектором. Ошибка cleanup не должна скрывать первичную причину сбоя; если сессия непригодна, она закрывается.

RunContext передаётся в CPU-проходы, адаптер и поиск. Он хранит монотонные отметки времени, общие счётчики и состояние остановки. Бюджеты выбирает `AnalysisMode`: `fast` — 30/20 секунд на команду/поиск, `normal` — 90/60, `deep` — 300/240. Отсчёт команды начинается до валидации, поиска — непосредственно перед baseline, включая baseline, кандидаты и подготовку размеров. На этих стадиях действует минимум двух deadlines. EXPLAIN ограничен минимумом 2 секунд и оставшегося времени; другие SQL — оставшимся временем, подключение — минимумом 5 секунд и оставшегося времени.

Пределы EXPLAIN/новых repair-попыток — 500/8 для `fast`, 2000/28 для `normal`, 10000/256 для `deep`. Неуспешные EXPLAIN учитываются; cache hits не расходуют EXPLAIN или repair, новые ошибочные repair-оценки расходуют слот. Необязательное поле JSON `analysis_mode` и CLI `--analysis-mode` выбирают один пресет; CLI имеет приоритет, прежний вход сохраняет `normal`. Режим не меняет пул до 16 кандидатов или greedy/fixed-`S0` repair. Полная таблица эффективных пределов — в разделе 7 спецификации. Deadline проверяется до/после стороннего парсера, между обходами AST, областями генерации и итерациями поиска. Это бюджет анализа, а не гарантия точной длительности сторонних вызовов или экспорта.

Подготовка проверяет доступный write budget до обращения к размерам и запрашивает не более 32 размеров, включая ошибки, по ограниченной очереди из начальных 16 и резерва до 48. Размеры неизвестных кандидатов остаются `null`; storage и write units проверяются единой реализацией метрик с учётом ключей и INCLUDE. Локальная ошибка гипотезы с успешной очисткой допускает refill, потеря сессии/deadline останавливает подготовку с сохранением baseline. Фиксированный пул для серии готовится один раз при наибольшем бюджете; точки только фильтруют его в памяти. Кэш оценок и набор ранее ошибочных конфигураций принадлежат одному запуску; переносить их между БД, статистиками и запусками нельзя. Планы baseline и текущих двух incumbents сохраняются при оценке, чтобы экспорт не требовал повторных EXPLAIN. Optimizer передаёт оба результата pipeline через `SearchCheckpoint` до следующей операции; сборка отчёта начинается после закрытия сессии.

## Серия бюджетов (#75)

CLI серии читает общий workload v2 и отдельный запрос серии v1. Application подготавливает фиксированный пул при максимальном бюджете в отдельной сессии, затем последовательно вызывает pipeline для каждой точки. Общий deadline ограничивает подготовку и дочерние RunContext; локальные лимиты режима не сбрасываются внутри точки. Каждая точка заново получает каталог и baseline, использует собственные JDBC-сессию и кэш. Общая подготовка передаёт только сохранённые определения/оценки кандидатов и наблюдаемые условия, без сессии и ordinary run cache.

Сводка использует сохранённые результаты и явно отмечает изменения baseline/каталога/доступных версий относительно общей подготовки. Она не пересчитывает метрики, не выполняет EXPLAIN и не гарантирует snapshot isolation всей серии. Артефакты публикуются по точкам, поэтому ошибка или остановка не отменяет ранее завершённую публикацию. [Подробный контракт](../docs/budget-series.md).

## Ошибки, завершение и артефакты

Ожидаемые ошибки передаются через общий контракт `code`, `message`, необязательные `query_id`, `profile_id`, `details`. Уровень pipeline переводит результат в статус и код выхода; SQL-адаптер не решает, как оформлять HTML или какой код вернуть процессу. HTTP-коды не используются.

- Невалидный вход, ошибки каталога или численных расчётов не превращаются в успешный отчёт с нулевыми значениями.
- Ошибка создания отдельного кандидата исключает его с warning. Потеря соединения и исчерпание общего deadline не маскируются под такую локальную ошибку.
- Ошибка EXPLAIN делает весь набор непригодным. Если полный baseline уже есть, сохраняется лучший полный результат с корректным partial; без полного baseline запуск failed.
- Отсечения кандидатов — ограничения качества и warnings. Они сами по себе не означают partial. Незавершённый допустимый repair после исчерпания выбранного лимита новых попыток означает partial с `REPAIR_LIMIT`.

Экспорт использует общий AnalysisReport и один выбранный набор. CLI/JSON/HTML показывают режим, все эффективные пределы, фактические счётчики и причины остановки; hash исходного JSON не меняется CLI-переопределением режима. Временные файлы с run ID и проверка output-dir предотвращают смесь артефактов разных запусков. При failed успешный `indexes.sql` не публикуется; ошибка записи не выглядит успешным завершением. SQL/имена экранируются в HTML, DSN и пароли не попадают в файлы и логи.

## Параллельная разработка и интеграция

Разрабатывать компоненты на согласованных фикстурах можно до готовности соседних модулей. Изменение общего DTO должно обновлять производителя, потребителей и фикстуры в одном согласованном изменении; не добавлять локальный несовместимый дубликат модели. Владение задачами указывает зону координации, а не обязательную последовательность закрытия issues.

[PoC #22](https://github.com/ITMO-DevDays-2026-IndexBudget/IndexBudget/issues/22) — ранний реальный сквозной срез к концу 11.11: одна таблица, три SELECT, два профиля, до восьми автоматически полученных кандидатов, оба бюджета и оба objective. Полный repair не блокирует PoC. Фикстуры не заменяют реальные стыки в показе.

[MVP #21](https://github.com/ITMO-DevDays-2026-IndexBudget/IndexBudget/issues/21) включает полные ограничения, ошибки, repair и раздельные эксперименты: robust против mean при одной стратегии; greedy против greedy+repair при одном objective. Физические индексы, замеры времени и offline-перебор малого пространства выполняются отдельными проверочными инструментами на demo DB, а не скрытым этапом рабочей команды.
