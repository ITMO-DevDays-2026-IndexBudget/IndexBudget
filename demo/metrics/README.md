# Сверка метрик на PostgreSQL/HypoPG (#45)

Это проверка чисел на фиксированном тестовом пуле, а не реализация Optimizer
и не подтверждение готовности сквозного `analyze`. Требования —
[спецификация §4, §9–11](../../IndexBudget-spec-v0.2.md), [issue #45](https://github.com/ITMO-DevDays-2026-IndexBudget/IndexBudget/issues/45).

## Воспроизведение

Нужны Linux/WSL, Docker, Bash, Python 3, JDK 25 и доступ к зависимостям Gradle.
Из корня репозитория:

```sh
bash demo/check-metrics.sh
```

Скрипт собирает существующий образ PostgreSQL 16.15/HypoPG 1.4.2, создаёт
собственный контейнер со случайным loopback-портом и паролем, выполняет
существующий seed и удаляет только этот контейнер с его анонимным volume
при завершении. Общая БД, `.env`, Compose-проект стенда и его volume не используются.
Seed выполняет ANALYZE; тест подключается ролью `indexbudget_reader`, не строит
реальных индексов и вызывает только EXPLAIN без ANALYZE. Планировщик не перенастраивается.

Тест запускается только при `INDEXBUDGET_METRICS_TEST_URL` и
`INDEXBUDGET_METRICS_TEST_PASSWORD`, которые устанавливает скрипт. Не задавайте
URL общего стенда. Обычный `gradlew test` без этих переменных пропускает тест;
это не успешная интеграционная проверка. CI job `postgres-hypopg-metrics`
выполняет реальный прогон и сохраняет артефакт `real-cost-verification`.

## Данные и независимые ожидания

[workload.json](workload.json) фиксирует три SQL, два профиля чтения и две таблицы
с разными rates записи. Три определения индекса заданы вручную только для
контролируемого эксперимента: records(group_id, created_at DESC),
records(value, created_at DESC), groups(category). Используются реальные
каталог, SQL resolution, канонизация и DDL renderer. Короткие ID group/value/category
обозначают варианты этого теста, не production-ID генератора.

Пул заранее фиксирован: baseline, три одиночных набора и три пары — всего
7 полных векторов, ровно 21 EXPLAIN. Частоты обоих профилей и проверочного
`held_out_balanced` (1000/1000/500 вызовов) применяются в памяти. Проверочный
профиль фиксирован в исходнике до прогона и не участвует в выборе.

Ожидания C_s, B_s, gain, процента, нормированных весов, C_mean, B_mean и M/R
вычисляются отдельным тестовым расчётом BigDecimal/DECIMAL128. Production-калькулятор
не используется для ожидаемых чисел. Допуск сравнения — max(1e-9, |expected|×1e-12).
Порядок обоих objective сверяется для всех пар конфигураций отдельным ключом
HALF_EVEN(9), bytes, writes, IDs. Сравниваются результаты одного фиксированного пула.

Расход records-индекса: (1000+3000+100)×2 = **8200** единиц/час;
groups-индекса: (1+8+1)×1 = **10**. Размер с запасом вычисляется независимым
десятичным ceil(1.2×size) для каждого индекса. При исходных лимитах все 7 наборов
допустимы и должен находиться непустой улучшающий набор. Затем отдельно:

- Storage уменьшается до **1 байта**, write остаётся 20000: допустим только baseline.
- Write уменьшается до **1 единицы/час**, storage остаётся 64 MiB: допустим только baseline.

Это намеренно простые ненулевые границы, доказывающие смену допустимости и
лучшего набора тестового пула. Они не доказывают смену рекомендации будущего
greedy. Размеры и costs не назначаются вручную и не считаются универсальными
константами: статистика и окружение могут менять их.

В `build/metrics-verification/real-costs.json` сохраняются workload/hash,
seed/SHA-256, версии, настройки планировщика, DDL, реальные sizes, полные costs/plans,
проверенные и независимые агрегаты, выбранные варианты обоих objective,
ожидаемая разность абсолютных C_mean, бюджетные проверки и sensitivity.
Это технический формат свидетельства теста, не wire-схема `report.json` v2.
Совпавшие наборы и нулевая цена не скрываются. DSN и пароли не записываются.

## Сохранённый прогон 10.11.2026

[Полное свидетельство](real-costs.sample.json) получено указанной выше командой
на PostgreSQL 16.15 (Debian 16.15-1.pgdg12+2), HypoPG 1.4.2, Temurin 25.0.5,
Gradle 9.7.0, Docker 27.3.1 в WSL Ubuntu. Интеграционный тест прошёл,
выполнен 21 EXPLAIN. Файл — снимок одного окружения, не golden-константы теста.
Seed детерминирован по данным; выборка ANALYZE может менять статистику.

Для обоих профилей baseline B_s = B_mean = **20766463**. Порядок costs в таблице:
`by_group / by_value / groups`. C_mean рассчитан независимо десятичной арифметикой;
M/R ниже округлены для чтения, полная точность сохранена в JSON.

| Набор | Полный вектор costs | C_mean | M | R | Байты с запасом | Write units/час |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| ∅ | 6698.23 / 6698.23 / 19.50 | 20766463 | 1 | 1 | 0 | 0 |
| group | 79.18 / 6698.23 / 19.50 | 2828837.5 | 0.136221440 | 0.968126252 | 8355840 | 8200 |
| value | 6698.23 / 79.19 / 19.50 | 18185037.4 | 0.875692572 | 0.968126301 | 8355840 | 8200 |
| category | 6698.23 / 6698.23 / 13.05 | 20765818 | 0.999968940 | 0.999968940 | 19661 | 10 |
| group, value | 79.18 / 79.19 / 19.50 | 247411.9 | 0.011914013 | 0.011915269 | 16711680 | 16400 |

| category, value | 6698.23 / 79.19 / 13.05 | 18184392.4 | 0.875661513 | 0.968095241 | 8375501 | 8210 |

Оценки HypoPG до запаса: group/value — по 6963200 байт, category — 16384 байта.
Для победившей пары C_normal = 247409, C_campaign = 247438;
0.9×247409 + 0.1×247438 = 247411.9. Оба objective выбрали `group, value`;
ожидаемая цена устойчивости = 247411.9 − 247411.9 = **0**. Преимущество одного
критерия над другим этим примером не показано. На held-out профиле стоимость
пары = 168120 при baseline 13406210, отношение ≈ 0.012540457.

Численные ожидания для #21 при том же полном пуле и исходных бюджетах:
малый перебор должен выбрать эту пару для обоих objective. Greedy/repair
не могут получить ключ лучше её; repair не должен ухудшить ключ greedy.
Равенство с oracle и отсутствие эффекта repair допустимы. При каждом из двух
ужесточений бюджета до 1 выбирается baseline: M=R=1, расходы=0.
Эти ожидания относятся к сохранённым costs; новый запуск сверяется со своим
полным пулом, без требования побитового совпадения с этим снимком.

## Оставшаяся приёмка #45

На базовом main отсутствуют production evaluator #13, Optimizer #17/#18,
ReportBuilder/export #19 и HTML #20; helper цены #44 находится в отдельном PR.
Тестовый JDBC-сборщик не заменяет эти модули. После их интеграции требуются:

- Использовать production evaluator и проверить его счётчики/cleanup.
- Сверить production-цену устойчивости и оба incumbents на этих же costs.
- Запустить оба objective одной стратегией, проверить JSON/HTML/SQL и бюджеты.
- Для #21 отдельно сравнить greedy/repair при одном objective и сверить с
  инструментом малого перебора владельца поиска (здесь 3 кандидата, K=2,
  всего 7 допустимых по числу индексов наборов, 21 EXPLAIN).

Численный oracle для будущего поиска — лучший по общему ключу набор сохранённого
пула: результат greedy не может быть лучше него на том же пуле и бюджетах;
repair должен сохранять или улучшать ключ greedy. Это условное сравнение в
фиксированном пространстве, не глобальный оптимум. Физические измерения времени,
размера и записи остаются отдельным экспериментом #21. Issue #45 не закрывается
этим первым интеграционным срезом.
