# Ограниченные покрывающие индексы (#79)

Пример получен 11 ноября 2026 на одноразовой PostgreSQL **16.15** (arm64) + HypoPG **1.4.2**,
без изменения настроек планировщика. [Сохранённые результаты](real-costs.sample.json) — настоящий
planner cost и оценка размера, не время выполнения и не фактический размер индекса.

## Повторение

Из корня репозитория, с Docker и JDK 25:

```sh
bash demo/check-hypopg.sh
```

Скрипт создаёт собственный контейнер на случайном loopback-порту, запускает
`JdbcAnalysisSessionIntegrationTest` и удаляет только свои контейнер и тег образа.
Тест `generated INCLUDE uses real sizes costs budgets catalog and retains no benefit case`
записывает свежий результат в `build/include-demo/real-costs.json`.
Пароли, `.env` и общая demo-БД не используются.

Фикстура: 50 000 строк `records(id integer PRIMARY KEY, a integer, b integer, payload text)`,
`a = id`, `b = 50001 - id`, `payload = repeat('x', 80)`. Тест выполняет VACUUM/ANALYZE
при подготовке своей БД, отдельно от адаптера анализа. Runtime-сессия работает под ролью
с SELECT; HypoPG получает DDL общего renderer. Реальный индекс создаётся администратором
только после cost-эксперимента для проверки чтения каталога и удаления точного дубля.

| Запрос | Вариант | Baseline cost | Cost с INCLUDE | Оценка, байт | С запасом, байт | Write units/час |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| `SELECT b FROM records WHERE a = 314` | `(a) INCLUDE (b)` | 1395 | 4.06 | 1 449 984 | 1 739 981 | 120 |
| `SELECT payload FROM records WHERE a > 0` | `(a) INCLUDE (payload)` | 1395 | 1395 | 7 036 928 | 8 444 314 | 120 |

Оба варианта автоматически получены из разрешённого SQL. Каждый оценивается как отдельный
набор на **всём общем списке SQL**, а таблица показывает cost породившего запроса.
При профиле записи `insert=10, update=20, delete=30` один ключ и один payload дают
`(10 + 20 + 30) × 2 = 120`. Каждый набор проходит бюджеты 100 000 000 байт / 300 units/час;
тест отдельно проверяет отказ при 119 units/час и бюджете места на один байт меньше
индивидуальной оценки с запасом.

В первом случае план содержит Index Only Scan. Во втором снижение cost отсутствует:
покрытие всех колонок само по себе не делает индекс полезным. Отрицательный результат
сохранён, а не исключён из демонстрации. Возможность index-only scan не гарантирует
отсутствия heap fetches: это зависит от visibility map. Здесь нет EXPLAIN ANALYZE или
замеров ускорения. См. [PostgreSQL 16](https://www.postgresql.org/docs/16/indexes-index-only-scans.html).

В JSON случайное имя тестовой схемы заменено на `include_demo`, имена индексов сохранены
из запуска; повторный запуск может дать другие хэши и оценки. Они зависят от схемы,
версий и статистики; тест проверяет свойства, а не равенство чисел этому снимку.

## Контракт

Ключи: 1–2; payload: 0–2 неповторяющиеся колонки явной проекции, без пересечения с ключами.
Звёздочка отключает INCLUDE. Ключи и payload должны покрывать все ссылки на таблицу.
Подмножества широкой проекции не перебираются. Сохраняются caps 976/32/16 и происхождение;
отдельные причины и счётчики показывают ограничения INCLUDE.

Выходной отчёт — [v3](../../docs/report-v3.md), вход workload остаётся v2.
В HTML и SQL экспортируется тот же payload. Синтетический предпросмотр карточки:
`./gradlew reportPreview`, затем `build/report-previews/include.html`.
