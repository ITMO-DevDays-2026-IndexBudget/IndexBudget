# Физический прогон D3 / #110, 12.11.2026

Выполнен локально на PostgreSQL 16.15 aarch64, HypoPG 1.4.2; контейнер ограничен
2 CPU и 2 GiB RAM. Один последовательный клиент, каждый statement — отдельная
committed-транзакция. Код runner: `2710d6309567074ad1c7cb0fb47b4d70d773b7b7`.
Полная среда и настройки — environment.json. Сборка `build installDist` успешна;
предупреждения компилятора не препятствовали выполнению.

Команда из корня репозитория:

```sh
source .idea/java-env.sh
./gradlew --no-daemon build installDist
python3.13 demo/benchmark/run.py --output build/mixed-benchmark-001
```

## Источник и восстановление

Использован общий SQL/seed #106. Табличные before/after снимки получены настоящим
коллектором #102; rates рассчитаны #107 за окно 59,978 секунды. Точные observed
workload, source UUID, database OID, timestamps и бюджеты сохранены в workload.json.
Анализ выполнен отдельно, run ID `f0f8e453-36ab-403b-b1d9-76208c4f69ae`.
Точный hash входа/DDL — identity.json, исходные JSON/HTML/SQL — recommendation/.

Оба режима (read и mixed) выполнены по три раза на вариант. Порядок B/S, S/B, B/S.
Перед каждым из 12 вариантов создан физический клон неизменного seed. Все начальные
fingerprint совпадают. Baseline содержит прежние PK; selected — те же PK и четыре
индекса из indexes.sql: created_at, (group_id,value), (group_id,created_at), value.
Проверены hash DDL, число и имена индексов; логи и итоговые JSON согласованы.
Прогрев одинаковый, только чтение; восстановление через ROLLBACK не используется.
Состояние OS cache не контролируется. Наблюдение и анализ используют отдельные клоны.

## Измеренные результаты

Медиана psql latency в миллисекундах; по три наблюдения каждого SQL/варианта.
Скобки показывают min–max. Это короткий warm-cache эксперимент, не production p99.

| SELECT, режим read | Baseline | Selected |
|---|---:|---:|
| all_records | 56,570 (54,458–60,234) | 56,601 (55,813–58,847) |
| alternative_filters | 8,585 (7,888–9,313) | 0,644 (0,625–0,775) |
| category_join | 7,835 (7,264–8,603) | 1,076 (1,029–1,081) |
| group_list | 10,265 (9,908–10,535) | 0,875 (0,860–0,892) |
| records_by_group | 7,006 (6,856–8,089) | 0,822 (0,785–0,829) |
| records_by_value | 6,808 (6,759–8,099) | 0,864 (0,830–0,929) |
| time_window | 7,150 (6,847–8,621) | 0,450 (0,448–0,494) |

| Запись, режим mixed | Rows/call | Baseline, мс | Selected, мс | WAL/call baseline → selected, bytes |
|---|---:|---:|---:|---:|
| INSERT | 100 | 0,764 | 1,333 | 20 816 → 73 896 |
| UPDATE | 17 | 7,283 | 1,003 | 140 664 → 140 664 |
| DELETE | 2 | 7,500 | 0,876 | 9 376 → 8 288 |

INSERT замедлился примерно на 74,5%, WAL/call вырос в 3,55 раза. Для all_records
ускорения не наблюдается. Точечное чтение, UPDATE и DELETE стали быстрее в этой выборке.
Результаты без выигрыша и рост цены записи сохранены вместе с остальными.
По всем повторениям на вариант: INSERT 3 calls/300 rows, UPDATE 3/51, DELETE 3/6.
Измеренные ошибки — 0; число строк каждого write подтверждено сырым command tag.

Новые физические индексы после mixed занимают 16 744 448 bytes (около 15,97 MiB).
Размеры каждого индекса, БД и всех повторов сохранены в trials.json.
Read throughput: 2,723 → 2,772 SELECT/s; mixed: 2,145 → 2,191 SELECT/s,
каждый вид записи 0,306 → 0,313 calls/s. Знаменатель — всё измеряемое окно trial,
включая подключение, Docker exec, WAL-пробы и запись логов. Поэтому большой выигрыш
короткого SQL не означает аналогичный рост общего throughput этого runner.
Полный вывод all_records и инструментирование занимают заметную часть окна.

WAL измеряется cluster-wide insert LSN собственного контейнера вокруг statement;
setup/построение индексов/прогрев исключены, background WAL может входить.
Нормированные значения WAL/call и WAL/row, rows/s, stdev и все повторы — summary.json
и samples.json. Скриптовые веса не выдаются за фактические calls/hour.

## Модель и факт

Planner mean ratio выбранного набора: 0,096494; worst ratio: 0,097037.
HypoPG estimated bytes: 23 207 936, с запасом: 27 849 525; write proxy:
42 856,024 условных единиц/час. Это оценки отдельной модели из recommendation/report.json,
они не равны latency, фактическим bytes или WAL и не подтверждают SLA.
Синтетические данные, один клиент и три повтора ограничивают переносимость выводов.

## Проверки и артефакты

Проверены 112 записей samples по сырым psql timing/rows (включая observation),
12 одинаковых исходных fingerprint, соответствие DDL рекомендации, повторный расчёт
сводки и успешный cleanup. Unit-тесты отдельно проверяют SQL error, timeout,
сохранение частичных логов и отказ cleanup для чужого ownership label; такие сбои
в данном успешном физическом прогоне не возникали.

Сырые stdout/stderr измерений, CLI и setup/cleanup сохранены без изменения в
raw-logs.tar.xz с относительными путями исходного output-каталога. Для просмотра:

```sh
mkdir -p /tmp/indexbudget-benchmark-logs
tar -xJf demo/benchmark/results/2026-11-12/raw-logs.tar.xz -C /tmp/indexbudget-benchmark-logs
```

checksums.json фиксирует SHA-256 сохранённых файлов. commands.json содержит команды
исходного запуска; локальные абсолютные пути описывают ту машину, переносимые команды
приведены выше. Пароли и внешние DSN для этого эксперимента не использовались.
cleanup.json подтверждает удаление только собственного контейнера и уникального образа.
