# Общий SQL-сценарий демо (#106)

Библиотека для показа «обычный день → пик → бюджет → выбранный набор» и общий
вход для [#109](https://github.com/ITMO-DevDays-2026-IndexBudget/IndexBudget/issues/109)
и [#110](https://github.com/ITMO-DevDays-2026-IndexBudget/IndexBudget/issues/110).
Это конфигурация и проверка planner cost, **не** результаты физического benchmark.

## Один источник SQL и частот

- [workload.json](workload.json) — обычный workload v2: девять неизменённых SQL,
  два полных профиля вызовов/час, ручные write rates обеих таблиц, guard и ручной набор.
- [catalog.json](catalog.json) — статические метаданные библиотеки v1: названия,
  смысл, подсказки синтаксиса и причины отказа отрицательных примеров по query ID.
  Частоты и SQL положительных примеров не дублируются: берутся из workload.
  Это **не** новый вход CLI. [Frontend](../../frontend/README.md) читает библиотеку
  напрямую для вкладки «Примеры» датасета «Чтение и запись»: названия и пояснения
  из каталога, SQL/частоты из workload. Query IDs и физические имена таблиц
  сохраняются; при коллизии с изменённым пользователем SQL UI создаёт новый ID.
- [storage-series.json](storage-series.json) — 0 / 4 / 16 / 64 MiB при неизменном
  write budget 60000 units/час.
- [write-series.json](write-series.json) — 0 / 8200 / 24600 / 60000 units/час
  при неизменном storage budget 64 MiB.

| Query ID | Что показывает |
| --- | --- |
| `records_by_group` | Равенство, явная проекция для INCLUDE, важный SQL с guard 1.05 |
| `records_by_value` | Другой путь доступа, востребованный в пик; проекция payload |
| `time_window` | BETWEEN двух фиксированных timestamp внутри seed |
| `group_list` | IN из трёх литералов |
| `alternative_filters` | Две альтернативы OR с AND внутри ветвей |
| `category_join` | INNER JOIN records/groups, категория, ORDER BY DESC и LIMIT |
| `all_records` | Фильтр на все строки; `SELECT *`, контроль отсутствия пользы |
| `update_payload` | Однотабличный UPDATE, литеральный SET и обязательный WHERE |
| `delete_recent` | Однотабличный DELETE двух ранних записей из seed |

В `normal` вес 9 и чаще запрашивается группа, в `peak` вес 1 и чаще ищут значение
и меняют payload. Это заданная синтетическая модель длительности режимов, не
наблюдаемая статистика и не генератор заданного количества вызовов.
Для каждого примера конкретные частоты обоих профилей доступны в `calls_per_hour`.

## Датасет и фиксированные параметры

Источник — существующий [seed v1](../postgres/init/001-seed.sql), без его изменения:

- PostgreSQL **16.15**, HypoPG **1.4.2**, образ из [Dockerfile](../postgres/Dockerfile).
- `public.records`: 200000 строк, PK `id`; `group_id=i%1000`, `value=(i*37)%997`,
  `created_at=2026-01-01 + i seconds`, `payload=repeat(md5(i::text),4)`.
- `public.groups`: 1000 строк, PK `id`; `category=i%10`, `name='group-'||i`.
- Seed подготавливает ANALYZE; анализатор этого не делает. Изначальные реальные
  PK остаются в baseline. Широкая таблица seed здесь не участвует.
- Все используемые колонки NOT NULL: NULL-примеры намеренно отсутствуют.
  Нельзя показывать IS NULL на данных без пропусков как доказательство эффекта.
- SQL, интервалы и литералы фиксированы; нет `now()`/`random()` или пользовательского DDL.

Низкая кардинальность сама по себе не запрещает B-tree. В частности, `group_id`
имеет 1000 значений, `category` — 10. Пригодность сочетания определяется настоящим
EXPLAIN; категорического правила «мало значений — индекс бесполезен» здесь нет.

## Сценарий показа

1. Открыть общий workload и объяснить разные частоты normal/peak. Профили используют
   один общий SQL-список и один полный cost vector каждого набора.
2. Выполнить обычный анализ с 64 MiB / 60000 units / максимум 5 индексов. Настройки
   допускают выбор 2+ индексов; реальная проверка ниже требует, чтобы это действительно
   произошло на фиксированном seed. Никакой конкретный состав или процент не обещается.
3. Показать выбранный набор и оба incumbents одного исследованного пула.
   Если robust/mean совпали — сохранить и объяснить совпадение.
4. Показать `all_records`: диапазон охватывает всю таблицу, полные строки всё равно
   надо прочитать. Проверка сохраняет отсутствие снижения cost; планировщик не
   принуждается к индексам. Это пример на этих данных, не общий запрет диапазонных индексов.
5. Сравнить с ручным набором `(group_id, created_at DESC)` + `(value)`.
   Он оценивается отдельно и не пополняет пул поиска. Guard `records_by_group=1.05`
   ограничивает planner-cost регрессию 5%, **не** задержку и не SLA.
6. Запустить обе серии по отдельности. Нулевой бюджет возвращает пустой набор;
   более широкий бюджет допускает несколько индексов. Плато и ограничения второго
   бюджета не скрываются; при изменении baseline/каталога сравнение требует оговорки.

Режим `normal` ограничивает repair 28 новыми попытками. На этой библиотеке он может
вернуть **partial / REPAIR_LIMIT** с полным baseline и лучшим полностью оценённым
набором: это остановка ограниченного поиска, не ошибка SQL и не completed.
CLI возвращает код **3**, а серия сохраняет partial у соответствующих точек и
в сводке. Не игнорируйте код/причину и не выдавайте результат за полный обход.
Режим `deep` можно выбрать явно для отдельного сравнения лимитов; его результат
не подменяет normal и не гарантирует улучшения. Проверка допускает только completed
или partial по REPAIR_LIMIT, но не сбои БД, таймауты, отмену или неполный cost vector.

```sh
./gradlew installDist
build/install/indexbudget/bin/indexbudget analyze \
  --workload demo/scenarios/workload.json --output-dir reports/scenario-main-001
build/install/indexbudget/bin/indexbudget analyze-series \
  --workload demo/scenarios/workload.json --series demo/scenarios/storage-series.json \
  --output-dir reports/scenario-storage-001
build/install/indexbudget/bin/indexbudget analyze-series \
  --workload demo/scenarios/workload.json --series demo/scenarios/write-series.json \
  --output-dir reports/scenario-write-001
```

Перед командами нужен `INDEXBUDGET_DATABASE_URL` вашей отдельной seed-v1 БД и
отдельная opt-in роль DML-анализа. Каждый output-dir — новый/пустой, не каталог
предыдущего результата. На Windows используются wrapper и launcher `.bat`.

## Безопасная подготовка и проверка

Общую demo-БД и существующую SELECT-only роль **не менять**. В своей свежей
одноразовой БД после seed v1 администратор один раз выполняет
[prepare-role.sql](prepare-role.sql), передав `INDEXBUDGET_SCENARIOS_PASSWORD` через
окружение psql. Скрипт создаёт отдельную роль `indexbudget_scenarios`, наследует
SELECT-reader и добавляет только UPDATE(payload)/DELETE для records. На роли
включён default read-only; runtime повторно подтверждает серверную защиту.
Это явная подготовка, не GRANT внутри анализа. Скрипт не предназначен для повторной
миграции существующего стенда. Пароли и DSN не сохранять в Git/артефактах.

Самодостаточная проверка, не требующая изменения общей БД:

```sh
./gradlew test --tests '*DemoScenarioExamplesTest'
bash demo/check-scenarios.sh
```

Вторая команда требует Docker, Bash и JDK 25. Она создаёт **свой** контейнер,
применяет точный seed v1 и opt-in роль, запускает обычный pipeline и обе реальные
серии, затем удаляет только свой контейнер и образ. Не читает `.env`, не использует
общий volume и не меняет чужие сервисы. Пароли генерируются на один запуск.

Проверяются AST/каталог всех SQL, документированные ошибки, полный смешанный cost
vector, ручной набор, guard, отсутствие пользы массового фильтра, 2+ выбранных
индекса при широких бюджетах, неизменность данных и реальных индексов, cleanup
сессий и согласованный экспорт. Контрольные отчёты — `build/scenario-runs-*/`,
машинные факты и SHA-256 точного seed — `build/scenarios-verification/`.
Машинные факты включают статусы и причины остановки основного запуска и всех точек;
успешная проверка сценария не переименовывает partial-анализ в completed.
CI публикует их как artifact **demo-scenarios-verification** в job
**postgres-hypopg-integration**. До успешного запуска этой проверки сами файлы
сценария не считаются доказательством эффекта.

## Передача #109 / #110

Workload — общий источник SQL, профилей, литералов и budgets; seed/версии и
метаданные находятся рядом. Ручные rates — изменения **строк**/час: records
1000 INSERT + 3000 UPDATE + 100 DELETE; groups 100 INSERT + 50 UPDATE + 0 DELETE.
Они заданы независимо от DML calls: один вызов может изменить несколько строк
или ни одной. Их нельзя складывать, выводить друг из друга или учитывать дважды.
#109 заменяет manual на один явный пригодный write-window #107 без скрытого fallback.

В `catalog.json → benchmark_handoff` есть шаблон INSERT с отдельным параметром
уникального id начиная с 200001. Это **только** заготовка физического benchmark #110,
не SQL анализатора. INSERT отсутствует в workload; DML обычного анализа отправляется
только в исходный EXPLAIN без ANALYZE. SET не порождает INCLUDE.

#110 фиксирует длительность, конкурентность, warmup, порядок вариантов и минимум
три повтора; перед baseline/selected и каждым повтором восстанавливает одно и то же
исходное состояние. Повтор DELETE без восстановления быстро становится no-op,
повтор UPDATE может менять HOT/bloat; нельзя выдать такую смесь за исходную.
Здесь не реализован генератор нагрузки, не созданы физические индексы и не получены
runtime/TPS/WAL результаты. ModifyTable cost оценивает поиск/подготовку строк,
а не цену фактической записи. [Границы DML](../../docs/dml-analysis.md).
