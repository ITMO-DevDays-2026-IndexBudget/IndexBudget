# IndexBudget: спецификация MVP v0.2 для хакатона

Версия 0.2. Статус: черновик для ревью. Заменяет `IndexBudget-spec-v0.1.md`.

IndexBudget подбирает набор дополнительных индексов PostgreSQL для нескольких возможных режимов нагрузки при ограничении места и необязательном ограничении условной стоимости сопровождения записи. Пользователь задаёт общие SQL и несколько профилей их частот, а инструмент показывает лучший найденный набор для худшего сценария, сравнение со средним результатом и цену компромисса.

Главная проверяемая гипотеза MVP: набор, выбранный для усреднённой нагрузки, может давать мало пользы в другом важном режиме; сценарный критерий позволяет выбрать иной компромисс. Ограниченный пересмотр жадного решения проверяется как отдельное улучшение поиска. Продукт не заявляет научную новизну этих методов или превосходство над существующими советчиками без измерений.

Изменения относительно v0.1: Spring Boot CLI и локальный HTML вместо Ktor/React/REST; формат входа v2 с профилями; критерии `robust`/`mean`; повторное использование стоимости каждого SQL; ограниченные замены и пары; ограничения генерации до образования пар для широких таблиц; обновлённые PoC, задачи и проверки. Распределение владельцев сохраняется из [плана #2](https://github.com/ITMO-DevDays-2026-IndexBudget/IndexBudget/issues/2): поиск принадлежит Марату, расчёты и проверочные сценарии — Равилю.

Отдельное демонстрационное расширение — [веб-интерфейс](docs/demo-web-interface.md)
в каталоге [frontend](frontend/README.md). Он подготавливает собственную demo-БД,
передаёт workload v2 существующему CLI и публикует его отчёты. Это дополнительная
обёртка; формулы, ограничения и критерии приёмки ядра MVP не меняются.
В версии веб-демо 0.2 (#101) ID/версия выбирают доверенный серверный датасет:
клиентские DDL/seed не принимаются. Ручные частоты SQL веб-демо — целые
0–1 000 000 вызовов/час с положительным использованием каждого профиля и SQL.
Это модель нагрузки, а не число реальных выполнений. Ограничение не сужает вход
CLI v2 и не относится к частотам изменения строк; подробный контракт — в
[спецификации веб-интерфейса](docs/demo-web-interface.md).
Веб-демо 0.3 подключает библиотеку #106 к фиксированному датасету «Чтение и запись»:
названия, пояснения и добавление исходных SELECT/UPDATE/DELETE в общую нагрузку.
SQL и частоты берутся из `demo/scenarios`, текущие запросы и бюджеты не заменяются.
Отдельной проверки схемы в UI нет; подготовка и чтение каталога выполняются перед
анализом. DML использует отдельную роль собственной demo-БД, с прежними гарантиями
EXPLAIN без выполнения записи; общая SELECT-only роль не расширяется.

## 1 Пользовательский сценарий и границы обещаний

Основной пользователь — разработчик или инженер БД с репрезентативными запросами и подходящим окружением PostgreSQL. Пример вопроса: «Какие индексы добавить в пределах 64 MiB, если состав запросов различается в обычный день и во время акции?»

1. Поднимает demo DB через Docker Compose; CLI подключается по переменной окружения `INDEXBUDGET_DATABASE_URL`.
2. Передаёт JSON с общим списком SQL, 1–3 профилями частот, бюджетами и выбранным критерием.
3. Запускает анализ из терминала и видит текущую стадию и счётчики.
4. Получает `report.html`, `report.json`, `indexes.sql`: выбранные индексы, расход бюджетов, эффект по профилям/запросам, альтернативу из исследованных наборов и ограничения результата.
5. Проверяет рекомендации на отдельной тестовой БД. Применение SQL — отдельное действие пользователя.

Сценарии описывают разные смеси запросов на одной БД с одной статистикой и одинаковыми настройками планировщика. Они не моделируют конкуренцию запросов, насыщение CPU/I/O, рост данных или неизвестную будущую нагрузку. Устойчивость означает качество оценочной стоимости на переданных профилях; гарантий latency, throughput и SLA нет.

Существующие реальные индексы сохраняются и участвуют в baseline. Бюджеты относятся только к новым индексам. Полное планирование миграций, удаление индексов, автоприменение, публичный сервис произвольного SQL и подключения к недоверенным БД не входят в MVP.

## 3 Входные данные

### Workload и профили

Версия входного формата — `schema_version: 2`; версия документа — 0.2. Формат v1 не принимается молча: CLI возвращает `UNSUPPORTED_SCHEMA_VERSION` с указанием перенести частоты из `queries` в `profiles`. Поле `analysis_mode` добавлено совместимо в v2: прежний вход без него сохраняет обычный режим и прежние ресурсные пределы; версия схемы не меняется.

```json
{
  "schema_version": 2,
  "objective": "robust",
  "analysis_mode": "normal",
  "candidate_ranking": "frequency",
  "queries": [
    {
      "id": "records_by_group",
      "sql": "SELECT id, value FROM public.records WHERE group_id = 42 ORDER BY created_at DESC LIMIT 20"
    },
    {
      "id": "records_by_value",
      "sql": "SELECT id, value FROM public.records WHERE value = 7 ORDER BY created_at DESC LIMIT 20"
    }
  ],
  "profiles": [
    {
      "id": "normal",
      "weight": 0.9,
      "calls_per_hour": {"records_by_group": 3000, "records_by_value": 100}
    },
    {
      "id": "campaign",
      "weight": 0.1,
      "calls_per_hour": {"records_by_group": 100, "records_by_value": 3000}
    }
  ],
  "table_write_rates": {
    "public.records": {
      "inserts_per_hour": 1000,
      "updates_per_hour": 3000,
      "deletes_per_hour": 100,
      "source": "manual"
    }
  },
  "constraints": {
    "storage_budget_bytes": 67108864,
    "write_budget_units_per_hour": 10000,
    "max_indexes": 5,
    "query_cost_guards": {"records_by_group": 1.05}
  }
}
```

- `queries`: 1–20 записей с уникальными `id`. Это объединение SQL всех профилей, включая разные литералы одного шаблона. Нельзя иметь 20 отдельных SQL на каждый профиль сверх общего лимита.
- `profiles`: 1–3 записи с уникальными `id`. Каждый `calls_per_hour` содержит ровно все query IDs; неизвестный или отсутствующий ключ — ошибка. Частоты конечны и неотрицательны; ноль означает отсутствие запроса в этом профиле. В каждом профиле есть хотя бы одна положительная частота, каждый SQL используется хотя бы одним профилем.
- `weight` — положительное конечное относительное значение; для расчётов `p_s = weight_s / sum(weight)`. Вес нужен для среднего и разрешения равенств, но не ослабляет защиту сценария в максимуме `robust`. Это заданная пользователем относительная длительность/вероятность режима, а не частота SQL.
- `objective`: `robust` по умолчанию либо `mean`. При одном профиле критерии совпадают.
- `analysis_mode`: необязательная регистрозависимая строка `fast`, `normal` или `deep`; по умолчанию `normal`. Явный `null`, неизвестное значение или иной тип — `INVALID_INPUT`. CLI `--analysis-mode` имеет приоритет над этим полем; исходный JSON валидируется целиком, поэтому неверное поле не скрывается переопределением. Режим меняет только ресурсные пределы из раздела 7: финальный пул до 16 кандидатов и greedy с одним fixed-`S0` repair сохраняются.
- `candidate_ranking`: необязательная регистрозависимая строка `frequency` или `baseline_cost`; по умолчанию `frequency`. `baseline_cost` — экспериментальный рейтинг общего shortlist из раздела 5. Явный `null`, неизвестное значение или иной тип — `INVALID_INPUT`. CLI `--candidate-ranking` имеет приоритет над валидным значением JSON; исходный JSON проверяется целиком. Поле совместимо расширяет вход v2, прежний вход сохраняет прежний рейтинг.
- `storage_budget_bytes` — целое число от нуля, `max_indexes` — целое 0–5. Бюджет места обязателен; отчёт показывает байты и MiB. При нулевом месте или `max_indexes: 0` оценивается baseline и возвращается пустой набор без генерации/поиска.
- `write_budget_units_per_hour` — конечное число от нуля либо явный `null`. При включённом лимите нужны rates для всех таблиц workload. Отсутствие данных не считается нулём.
- `query_cost_guards` — необязательный объект `query ID → предел` для критических SQL (#78). Предел — отношение planner cost `cost(q,S) / cost(q,empty)`, не проценты: `1.0` запрещает любое ухудшение, `1.1` допускает ухудшение до 10%. Значение — конечное число не меньше 1.0; неизвестный query ID, иной тип или структура — `INVALID_INPUT`. Ключи — точные query IDs входа. Поле совместимо расширяет вход v2: прежний вход без него сохраняет прежнее поведение и прежний hash. Семантика проверки — раздел 4.
- Каждая запись rates обязана содержать `inserts_per_hour`, `updates_per_hour`, `deletes_per_hour` — конечные неотрицательные числа. Пропуск поля, отрицательное значение и неизвестная таблица — ошибка. `source` — `manual` (по умолчанию) либо `observed`. Наблюдаемые rates означают изменённые строки в час, а не SQL-вызовы, и получаются из одной пары табличных снимков по формуле `Δcounter × 3600 / Δseconds`; формат снимков и проверки окна — [docs/table-write-profile.md](docs/table-write-profile.md). Снимок охватывает всю БД, но экспортируемый наблюдаемый профиль обслуживает ровно таблицы выбранного workload: rates остальных таблиц в workload не попадают, а их диагностика остаётся в манифесте импорта; `source_id` окна сверяется с read-окнами. Наблюдаемые rates требуют `table_write_rates_origin`, ручные — не переносят его; смешение источников — `INVALID_WRITE_PROFILE`. Одинаковые ручные и наблюдаемые числа дают одинаковые расходы и решения бюджетов.
- `table_write_rates_origin` — необязательный объект наблюдаемого происхождения профиля записи (#107): ровно одно явно выбранное окно `window` (`from`, `to`, `period_seconds` > 0), флаг `complete` и причины ограничений `reasons`. При включённом `write_budget_units_per_hour` неполное окно — `INVALID_WRITE_PROFILE`: неполное наблюдение не отключает лимит и не подменяется ручными значениями. Явный `null`, `kind` не равный `observed`, происхождение без rates или rates без происхождения — ошибка входа. Поле совместимо расширяет вход v2: прежний ручной вход сохраняет прежний hash.
- При выключенном лимите записи профиль можно не передавать либо передать целиком. Неполный переданный профиль отклоняется. Без профиля write units индексов и наборов — `null`, с подписью «нет данных»; при полном профиле они рассчитываются и без ограничения.
- Ключ `table_write_rates` — точная строка `schema.name` физических разрешённых имён, с сохранением регистра. SQL-алиасы, кавычки и `search_path` в ключах не интерпретируются. Если разные таблицы workload дают один ключ из-за точек в именах, переданный профиль отклоняется как неоднозначный с `INVALID_WRITE_PROFILE`.
- Профиль записи один, общий для всех сценариев чтения; пользователь задаёт выбранную им нагрузку записи, при необходимости консервативную. MVP не заявляет оптимизацию разных write-профилей.
- Максимум 1 MiB UTF-8 для входного JSON, 64 KiB UTF-8 для одного SQL и 256 единиц сложности WHERE/JOIN на запрос (сравнение/null-test: 1, IN: каждый элемент, BETWEEN: 2). Размер проверяется до разбора; сложность — при проверке AST. Превышение — `INPUT_LIMIT_EXCEEDED`, исходный SQL не обрезается.
- Все расчёты должны оставаться конечными: нечисловой/отрицательный planner cost и переполнение промежуточных сумм дают явную ошибку, а не улучшение, ноль или успешный отчёт. Нормированные веса обязаны оставаться положительными; если при наличии положительного `B_s` вычислен `B_mean = 0`, запуск завершается численной ошибкой. Потеря положительного веса из-за underflow не считается нулевой вероятностью сценария.

Частоты задаются в пересчёте на час; ждать час для анализа не требуется. Несколько значений параметра можно представить отдельными SQL с литералами. Это не точная симуляция выбора generic/custom plan у prepared statements. `pg_stat_statements` обычно заменяет литералы параметрами и не предоставляет репрезентативные исходные значения для этого режима. [pg_stat_statements](https://www.postgresql.org/docs/16/pgstatstatements.html), [EXPLAIN](https://www.postgresql.org/docs/16/sql-explain.html).

Необязательное `provenance` (#68) добавляет сведения об импортированной нагрузке без изменения
ручного ввода v2: версия метаданных 1, источник `pg_stat_statements` с UUID, правило отбора,
окна по каждому profile ID, охват calls/исторического времени относительно доступных полных
записей и происхождение примера по каждому query ID. Неполное наблюдение, неизвестный охват
и реальный ноль различаются. Метаданные не пересчитывают частоты или write rates и входят
в input hash и лимит 1 MiB. Формат, проверки и синтетический пример закреплены в
[контракте отчёта](docs/report-v3.md#происхождение-нагрузки-68). Получение этих данных импортёром
остаётся отдельной задачей #67; сам отчёт принимает сохранённые сведения.

### Поддержанный SQL и каталог

Поддерживается один SELECT на запись workload, обычные таблицы, алиасы, до трёх таблиц, INNER JOIN с равенством колонок, WHERE с AND/OR и сравнениями `=`, `<`, `<=`, `>`, `>=`, а также `column IN (literal, ...)`, `column BETWEEN literal AND literal`, `column IS NULL` и `column IS NOT NULL`. ORDER BY — по одной или двум колонкам с ASC или DESC, LIMIT — числовой. В SELECT допускаются колонки и `*`; литералы могут иметь явное приведение к типу, например timestamp.

Расширение #73 сохраняет формат входа v2. Список IN непустой, содержит до 256 поддержанных скалярных литералов, включая NULL и явные casts; значения не подставляются и не переписываются. Общая сложность WHERE + JOIN остаётся ≤256: обычное сравнение или null-test стоит 1, каждый элемент IN — 1 (повторы тоже считаются), BETWEEN — 2. Границы BETWEEN не сортируются, NULL не заменяется нулём/false. В PostgreSQL IN с несколькими литералами может использовать общий тип массива: типы/неявные casts, `pg_type.typarray` и действительная видимая сигнатура равенства проверяются по каталогу. Обе сигнатуры `>=`/`<=` BETWEEN проверяются отдельно; IS NULL/IS NOT NULL не вызывают оператор сравнения.

JOIN ON остаётся равенством колонок. NOT IN, NOT BETWEEN, явные SYMMETRIC/ASYMMETRIC, ISNULL/NOTNULL, IN с подзапросом/колонками/выражениями и null-test над выражением не входят в этот срез. В признаки генератора передаётся один узел на новую форму: IN и IS NULL — equality-like, BETWEEN и IS NOT NULL — range-like. Это эвристика генерации, а не обещание индексного плана: каждое сочетание оценивается целым исходным EXPLAIN. IN не разворачивается в фиктивные совместные AND-условия. См. [NULL-семантику IN](https://www.postgresql.org/docs/16/functions-comparisons.html) и [выбор общего типа](https://www.postgresql.org/docs/16/typeconv-union-case.html).

Расширение #103 допускает также один UPDATE или DELETE на запись и смешанный список SELECT/UPDATE/DELETE. DML обращается к одной обычной постоянной таблице с алиасом и обязательным WHERE из того же поднабора. UPDATE содержит 1–256 одиночных SET-присваиваний скалярных литералов, NULL или поддержанных casts во встроенные скалярные колонки. SET разрешается через каталог отдельно от SELECT-проекции; повторные и квалифицированные SET-цели запрещены. Проверяются implicit/assignment casts, но диапазоны значений/typmods остаются проверкой исходного EXPLAIN. Это не гарантия успешного будущего исполнения DML. SET не порождает ключи или INCLUDE, DML-кандидаты берутся только из WHERE. Лимиты 64 KiB SQL, сложности WHERE и общего списка запросов сохраняются.

CTE, подзапросы, NOT над условием, GROUP BY, оконные выражения, вызовы функций, views, partitioned tables, временные DML-таблицы, пользовательские типы и операторы, параметры `$1` в готовом workload и несколько statements отклоняются с query ID и причиной. INSERT/MERGE, UPDATE FROM, DELETE USING, RETURNING, tuple SET, DEFAULT и вычисляемый SET не поддерживаются. Неподдержанный SQL не исчезает из расчёта молча.

Оценивается исходный DML через EXPLAIN (FORMAT JSON), без ANALYZE и без SELECT-аппроксимации. До оценки серверный `default_transaction_read_only` включается, а `transaction_read_only` проверяется; неподтверждённая защита прерывает соединение. SELECT-only роль сохраняется: DML EXPLAIN требует отдельно выданных администратором прав оригинального statement, runtime не делает GRANT. См. [границы безопасности DML](docs/dml-analysis.md).

ModifyTable Total Cost отражает поиск/подготовку строк, не фактическую запись, WAL, блокировки или триггеры. Полный смешанный вектор использует прежние R/M, guards, cache и partial. Частоты вызовов DML не становятся rates изменённых строк, write budget остаётся отдельным proxy. [PostgreSQL 16 EXPLAIN](https://www.postgresql.org/docs/16/using-explain.html).

SQL разбирается в AST через JSqlParser. Колонки разрешаются через каталог БД, включая алиасы и неоднозначные имена; регулярные выражения не заменяют AST. Проверка корректности SQL использует все его колонки, даже если генератор позже ограничивает признаки. [JSqlParser](https://github.com/JSQLParser/JSqlParser).

Адаптер читает структуру только относящихся к workload таблиц: колонки и типы, оценку числа строк, существующие индексы и доступность статистики. Число колонок таблицы не ограничивается 16: таблица со 100 колонками поддерживается. Demo seed выполняет ANALYZE. CLI не запускает ANALYZE автоматически на целевой БД; отсутствие статистики даёт предупреждение о качестве оценки.

### Логические условия и происхождение (#74)

AND/OR и скобки сохраняются деревом с обычным приоритетом AND над OR. Проверяются все ветви,
включая их колонки, casts и операторы: корректная первая ветвь не скрывает ошибку второй.
Листья JOIN ON по-прежнему только равенства колонок; их можно соединять AND/OR. WHERE и все
INNER JOIN ON объединяются конъюнкцией с сохранением источника каждого листа. При переносе в
домен снимаются только избыточные скобочные обёртки; группировка AND/OR и исходный SQL не меняются.

Ограничение сложности 256 общее для всех ветвей WHERE/JOIN; дополнительно допускаются до
1024 узлов условий (включая скобочные обёртки) и глубина до 512. Превышение даёт
`INPUT_LIMIT_EXCEEDED` с query ID до JDBC. Валидатор обходит AST-условия итеративно с deadline;
разрешение имён рекурсивно обходит уже проверенное дерево в пределах этих лимитов,
также проверяя deadline. Это не гарантия итеративного обхода внутри JSqlParser.
Генерация не разворачивает DNF и не перечисляет комбинации всех OR-ветвей. Для до 256 листьев
строится попарная структурная совместимость: листья под разными сторонами OR несовместимы,
под сторонами AND совместимы. Для одной физической колонки учитываются все её вхождения/роли.

Условная пара ключей создаётся только при наличии совместимых вхождений требуемых ролей:
`a=1 OR b=2` даёт одиночные, но не пару; `a=1 AND (b=2 OR c>3)` допускает `(a,b)`, `(b,a)`,
`(a,c)`, но не `(b,c)`. ORDER BY — безусловный источник: точная сортировочная пара и
equality + sort не требуют нахождения sort-колонки в той же WHERE-ветви. Совместимость не
доказывает выполнимость условий (например, противоречащих литералов), полезность или выбор плана.

Для OR-workload сохраняется `source_branches`: пары query ID / путь листа (`condition/L/R/...`)
или `order_by`. Это объединение породивших вхождений, не полный набор DNF-термов и не утверждение,
что все перечисленные листья совместны одновременно. Пути отсчитываются от дерева, построенного
из WHERE, затем ON в порядке JOIN и объединённого слева через AND; у AND/OR L/R означает левый/
правый дочерний узел. Дедупликация объединяет источники; IDs/DDL определяются только индексной
структурой. Рейтинг по профилям по-прежнему учитывает уникальные query IDs, не число ветвей.
Без OR список источников ветвей пуст. JSON/HTML показывают происхождение и warning
`OR_BRANCH_AWARE_GENERATION` с числом OR-узлов/листьев и `dnf_expanded: false`.
Caps 16 колонок / 32 локальных / 16 общих сохраняются до оценки размеров и не меняют SQL.
Формат входа остаётся v2; новые поля отчёта добавляются совместимо, существующие не переименовываются.

## 4 Метрики, критерии и бюджеты

### Стоимость по сценариям

`S` — набор новых индексов, `cost(q,S)` — корневой `Plan.Total Cost` из EXPLAIN, `f_s(q)` — частота в профиле `s`. Реальные индексы доступны при любой оценке.

```text
C_s(S) = sum(f_s(q) * cost(q,S))
B_s = C_s(empty)
gain_s(S) = B_s - C_s(S)
gain_percent_s(S) = 100 * gain_s(S) / B_s       # только если B_s > 0

C_mean(S) = sum(p_s * C_s(S))
B_mean = C_mean(empty)
M(S) = C_mean(S) / B_mean                     # если B_mean > 0
R(S) = max(C_s(S) / B_s for s where B_s > 0)
```

`M` — отношение ожидаемой стоимости к её baseline; оно не равно среднему отношений сценариев. `R` — худшая нормированная стоимость среди переданных сценариев, не regret относительно неизвестного оптимума. Все сценарии участвуют в `R` независимо от `weight`.

При `B_s = 0` процент и отношение этого профиля — `null`; абсолютная стоимость сохраняется. Такие профили не входят в максимум, но допустимый набор обязан сохранять для них `C_s(S) = 0`; иначе причина отказа — `ZERO_BASELINE_REGRESSION`. Если все `B_s = 0`, возвращается baseline и пустой набор, `M`/`R` — `null`, поиск не запускается: неотрицательную стоимость уже не уменьшить.

Необязательные ограничения регрессии критических SQL (#78) проверяются в общей оценке допустимости после полного вектора costs. Для каждого guard `g(q)` набор допустим, если `cost(q,S) / cost(q,empty) <= g(q)`; равенство порогу проходит, превышение — отказ всего набора с причиной `CRITICAL_QUERY_REGRESSION`, заданным пределом и наблюдаемым отношением по этому SQL. Отклонённый набор не обновляет incumbents ни в greedy, ни в repair и не завершает запуск: если отклонены все наборы, сохраняется рекомендация baseline (пустой набор новых индексов) со статусом completed, а не failed. При `cost(q,empty) = 0` отношение не вычисляется: нулевая база не делится и неизвестная регрессия не считается нулём; любой положительный `cost(q,S)` нарушает guard, сохранение нуля — допустимо. Неконечное отношение — численная ошибка. Это ограничение planner cost, а не latency и не SLA.

Для детерминированного сравнения конечные `R` и `M` округляются до 9 десятичных знаков с HALF_EVEN; обозначим их `r` и `m`. Отчёт хранит и исходные значения. Сравнение выполняется по округлённым значениям, без нетранзитивного компаратора «разница меньше epsilon».

```text
robust: минимум лексикографического ключа (r, m, bytes, writes?, sorted_ids)
mean:   минимум лексикографического ключа (m, r, bytes, writes?, sorted_ids)
```

`bytes` — сумма размеров с запасом; `writes` участвует в ключе только при полном профиле записи, иначе пропускается для всех наборов. `sorted_ids` — лексикографический список стабильных candidate IDs. Критерий `robust` может пожертвовать средним эффектом ради худшего сценария: в отчёте эта цена должна быть видна.

Метрика называется «снижение взвешенной стоимости планов». Cost — условные единицы PostgreSQL, не миллисекунды; корневой Total Cost уже включает дочерние узлы. Нельзя переводить процент изменения cost в процент реального ускорения. Отдельный запрос может ухудшиться; такие строки выделяются. Ограничения SLA и реального времени не входят в MVP; необязательные ограничения регрессии planner cost критических SQL (#78) описаны выше. [Using EXPLAIN](https://www.postgresql.org/docs/16/using-explain.html).

### Место

```text
estimated_bytes(i) = hypopg_relation_size(i)
budgeted_bytes(i) = ceil(1.2 * estimated_bytes(i))
sum(budgeted_bytes(i) for i in S) <= storage_budget_bytes
```

Коэффициент 1.2 сохраняется в отчёте. Показываются исходная оценка и объём с запасом. Это ограничение оценки; фактический размер после построения может отличаться.

### Сопровождение записи

```text
row_changes(t) = inserts_per_hour(t) + updates_per_hour(t) + deletes_per_hour(t)
write_units(i) = row_changes(table(i)) * (number_of_key_columns(i) + number_of_include_columns(i))
sum(write_units(i) for i in S) <= write_budget_units_per_hour  # если лимит включён
```

Единица — «условные единицы сопровождения индексов в час». Например, 4100 изменяемых строк дают 8200 единиц для двухколоночного индекса. Это вспомогательная эвристика, не прогноз WAL, I/O, throughput или замедления INSERT/UPDATE. Все UPDATE учитываются; ширина ключа, HOT, bloat и отложенная очистка DELETE не моделируются. Каждая INCLUDE-колонка также стоит одну единицу на изменение строки; payload не бесплатен. Например, один ключ + две INCLUDE-колонки при 4100 изменениях дают 12300 units/час. При одной таблице модель различает кандидаты по общему числу ключевых и INCLUDE-колонок.

Нулевой write budget допускает только индексы с нулевыми write units. Модель записи и planner cost не складываются в одну сумму с произвольным коэффициентом. При будущем импорте счётчиков нужны разности между наблюдениями и обработка сбросов; текущую долю HOT нельзя переносить на новые индексы. [Статистика PostgreSQL](https://www.postgresql.org/docs/16/monitoring-stats.html), [HOT](https://www.postgresql.org/docs/16/storage-hot.html).

## 5 Ограниченная генерация кандидатов и широкие таблицы

По умолчанию генератор рассматривает неуникальные B-tree на 1–2 ключевых обычных колонках и до двух дополнительных колонок INCLUDE (#79). Ключи берутся только из WHERE, JOIN и ORDER BY поддержанных SQL. Явная проекция SELECT может дополнить существующий ключевой вариант payload, но сама не создаёт ключи. `SELECT *`, `table.*` и смешанная проекция со звёздочкой не порождают INCLUDE-вариантов. Полный перебор всех колонок схемы запрещён.

### Явно включаемый hash (#115)

Резервное расширение #115 использует общую модель методов #114. `hash` разрешается
явно в `index_methods` (один или вместе с `btree`/`brin`); прежний default — B-tree.
После общего column cap hash создаётся только для простого скалярного WHERE
`column = literal` (включая нормализованное `literal = column`). IN, null-test,
диапазоны, сравнение колонок, JOIN и ORDER BY сами по себе hash не порождают.
В AND/OR сохраняется происхождение только применимого листа. SQL не меняется.

Один ключ, default collation/opclass своего метода, без INCLUDE, направлений,
partial/expression и настройки fillfactor. Hash занимает до 16 событий внутри
общего cap 976, BRIN — ещё до 16; B-tree использует остаток, затем INCLUDE.
Все методы делят прежние caps 16/32/16, резерв 48, size/EXPLAIN/repair/deadline.
Отсутствие default hash opclass даёт `NO_HASH_OPERATOR_CLASS`, не нулевой размер;
происхождение — `HASH_EQUALITY`. Метод входит в ID/DDL, B-tree IDs не меняются.
Точный реальный дубль hash требует совпадающего opclass/collation и отсутствия
reloptions; другие реальные индексы остаются частью baseline.

Ручной `method: "hash"` независим от автоматического списка. Ключ принимает только
`column`, даже явные direction/nulls по умолчанию запрещены. Полный смешанный набор
оценивается целиком общей сессией, метриками и бюджетами; одиночные эффекты не складываются.
Write proxy по числу колонок не различает реальную цену сопровождения методов.
Hash не обещает преимущества перед B-tree или ускорения по одному planner cost.

Workload остаётся v2; строгий reader без hash отклоняет новый enum, не подменяет метод.
Метод-осведомлённые report v4 / сводка v2 расширяют перечень методов значением `hash`
без изменения структуры/единиц; B-tree-only сохраняет report v3 / сводку v1.
Это действует при явно разрешённом или ручном hash также для failed/partial и пустого
набора. В JSON hash direction/nulls равны null, HTML/SQL сохраняют метод и общий
run ID/hash. Consumers обязаны отклонять неизвестный метод, а не считать его B-tree.
[Контракт и воспроизведение](docs/hash.md).

### Явно включаемый BRIN (#114)

Необязательный `index_methods` в workload v2 — непустой массив уникальных строк
`btree`/`brin`/`hash`. Отсутствие поля означает `["btree"]`; `null`, пустой массив, повторы,
неизвестные методы и иной тип отклоняются. Порядок массива не задаёт приоритет;
эффективные методы сериализуются в порядке `btree`, `brin`, `hash`. Отдельного CLI override нет.

После общего отбора ≤16 колонок BRIN добавляется только для скалярных WHERE
`<`, `<=`, `>`, `>=`, `BETWEEN` с литералами. Равенство, IN, null-test, JOIN,
сравнение двух колонок и ORDER BY сами по себе BRIN не порождают. Каждый такой
индекс имеет одну колонку, default collation/opclass своего метода и стандартные
параметры PostgreSQL, без INCLUDE, сортировки или подбора pages_per_range.
Условия OR сохраняют происхождение диапазонного листа; SQL не меняется.

Не создаётся копия всех B-tree вариантов для каждого метода. BRIN занимает до 16
мест внутри прежних 976 событий на область: B-tree перечисляется в прежнем порядке
до `976 − brin_count − hash_count`, затем покрывающие варианты используют остаток. Отсечённые
B-tree варианты отмечаются `METHOD_VARIANT_LIMIT`. Оба метода вместе проходят
локальные 32, сценарный shortlist 16, резерв 48 и до 32 size-попыток. Квот на метод
нет, tie-break использует общий стабильный ID. EXPLAIN/deadline/repair caps прежние.

Каталог разрешает default opclass отдельно по методу теми же правилами PostgreSQL.
Отсутствующий BRIN opclass исключает автоматический вариант с
`NO_BRIN_OPERATOR_CLASS`, сохраняя пригодные B-tree варианты и исходный SQL;
ручное определение без доступного default opclass — `INVALID_INPUT` до baseline.
Канонический ID включает метод и opclass; прежние B-tree IDs не меняются.
DDL BRIN не содержит ASC/DESC/NULLS. Внутренние поля направления имеют фиксированные
значения ASC/LAST только для канонического кодирования, а не смысл сортировки.

`manual_indexes[].method` по умолчанию `btree`, явно допускается `brin` с одной
колонкой. Для BRIN ключ принимает только `column`: даже явные ASC/NULLS LAST
отклоняются. Ручной метод независим от автоматического `index_methods` и оценивается
отдельно по прежним правилам ручного набора.

Workload остаётся v2: поля аддитивны, старый строгий reader отклоняет неизвестное
`index_methods`/`method`, а не молча запускает B-tree. Отчёт с разрешённым или ручным
BRIN получает **schema_version 4**, включая failed/partial и пустой selected;
B-tree-only сохраняет v3. Сводка такой бюджетной серии получает v2 (прежняя v1 для
B-tree), запрос серии остаётся v1. Старые readers должны отклонять новые версии.
В отчёте фиксируется `index_methods`, у каждого определения — `method`, для BRIN
`direction`/`nulls` равны `null` (неприменимы). HTML и SQL показывают тот же метод;
SQL-заголовок сохраняет эффективный список методов. Все артефакты используют один
run ID/hash и выбранный набор. [Контракт и воспроизведение](docs/brin.md).

Размеры и полные costs смешанных наборов измеряются обычной HypoPG-сессией, с общим
cleanup и бюджетом `ceil(1.2 × estimated_bytes)` на индекс. Write proxy остаётся
прежней моделью по числу колонок: равное число колонок разных методов **не доказывает
равную реальную стоимость сопровождения**. BRIN полезен не для любого диапазона;
корреляция данных и планировщик влияют на результат. Отрицательные результаты
сохраняются, planner cost не превращается в время или обещание ускорения.

### Ограничение признаков до образования пар

Для каждого `(query_id, table)` собираются различные физические колонки условий и сортировки. Нормированная частота `u_s(q) = f_s(q) / sum_q f_s(q)` используется только для отбора кандидатов, не заменяет частоты в целевой функции. Поддержка колонки в сценарии — сумма `u_s(q)` по различным запросам, использующим её в условиях/сортировке.

Оставляем до **16 разных колонок на `(query, table)`**:

1. Сначала колонки ORDER BY этого запроса в исходном порядке (их не более двух).
2. Остальные — по убыванию максимальной поддержки колонки среди сценариев.
3. При равенстве: колонки равенств WHERE/JOIN перед диапазонами, затем стабильный идентификатор `schema/table/column`.

Это ограничение генератора, а не изменение SQL: все исходные условия остаются в EXPLAIN. Если участвовало больше 16 колонок, отчёт содержит `COLUMN_SHORTLIST_TRUNCATED`, query ID, таблицу, обнаруженное и сохранённое число и список исключённых колонок.

### Локальные кандидаты

На оставшихся колонках генерируются:

- Одноколоночные индексы с ASC и стандартным NULLS LAST. PostgreSQL может сканировать B-tree в обратном направлении; все варианты направления одного ключа не перечисляются.
- Двухколоночные варианты на одной таблице из одного запроса: равенство перед диапазоном; равенство перед колонкой сортировки; две колонки равенства в обоих порядках; пара ORDER BY в исходном порядке и направлениях. Для ключей без явной сортировки — ASC; для ключей из ORDER BY — направление запроса и соответствующее стандартное NULLS.
- Повторяющиеся признаки одного столбца предварительно объединяются. Каждая упорядоченная пара разных колонок обходится один раз; для неё создаются только направления, вытекающие из правил, максимум четыре. Нельзя перечислять пары заново для каждого повторного предиката.

После локальной канонизации и удаления точных реальных дублей сохраняется не более **32 кандидатов на `(query, table)`**. Для INCLUDE резервируется до восьми мест; остальные места (не менее 24) занимают обычные кандидаты: сначала одноколоночные (до 16 при одном методе, до 48 при B-tree + BRIN + hash, перед общим cap 32), затем составные. Неиспользованные INCLUDE-места доступны обычным индексам; более восьми INCLUDE не сохраняются даже при свободных местах. INCLUDE-очередь сортируется так же: число ключей, лучший приоритет пары, ID. Приоритет составных: точная пара ORDER BY, равенство + сортировка, равенство + диапазон, два равенства. Кандидат из нескольких групп получает наивысший приоритет; внутри группы порядок по стабильному ID. При отсечении — `LOCAL_CANDIDATE_LIMIT` с числами и областью.

Точный дубль проверяется только против валидного готового доступного обычного индекса того же метода без predicate и expressions. Для BRIN/hash дополнительно требуется отсутствие reloptions; явно заданные параметры, даже совпадающие с defaults, консервативно не считаются точным дублем. Должны совпасть ключи, порядок, направления, NULLS, collation, opclass и множество INCLUDE-колонок. Порядок payload канонизируется по имени; payload отличается от ключей. Обычный `(a)`, `(a,b)` и `(a) INCLUDE (b)` — разные определения, ни одно не удаляется как точный дубль другого. Partial index `(a) WHERE ...` не заменяет общий `(a)`; наличие `(a,b)` не даёт основания удалить `(a)`. Существующие индексы других видов не удаляются и остаются доступны планировщику.

### Ограниченные INCLUDE-варианты (#79)

Для каждого уже перечисленного ключевого определения берётся вся явная проекция данной таблицы без ключей, в порядке физических имён. Если она пуста, дополнительный вариант не нужен; если в ней больше двух колонок, вариант не генерируется (`INCLUDE_PAYLOAD_LIMIT`). Подмножества проекции не перебираются. Если ключи и payload не покрывают все ссылки на эту таблицу в исходном SQL (включая условия и сортировку), покрывающий вариант также не предлагается. Проверка использует полный ResolvedQuery, а не обрезанные признаки. Звёздочка в любой части проекции отключает INCLUDE для всего запроса.

Порядок базовых определений детерминирован: одиночные по физическому имени, затем упорядоченные пары имён и направления ASC/DESC. Добавляется не более `min(16, 976 − ordinary_count − brin_count − hash_count)` покрывающих определений на область; остальные подходящие варианты отражаются как `INCLUDE_VARIANT_LIMIT`. Поэтому общий предел **976 на область / 58 560 на запуск**, caps **16/32/16**, число SQL и EXPLAIN не растут. Для каждого варианта сохраняются query IDs, исходные причины ключей и `COVERING_PROJECTION`. Локальные счётчики отдельно содержат перечисленные и оставленные INCLUDE; `LOCAL_CANDIDATE_LIMIT` также сообщает `include_before`, `include_after`, `include_limit`.

INCLUDE не добавляет сортировку, collation или opclass payload. Канонизация проверяет существование колонок, отсутствие повторов/пересечения с ключами и принадлежность одной таблице; DDL экранирует каждый идентификатор. ID обычных индексов не меняются; непустой канонический payload расширяет кодируемую структуру перед SHA-256.

Размер и полный cost-вектор получаются обычным путём через HypoPG. Payload влияет на размер и write proxy; он не получает бесплатного бюджета. INCLUDE допускает index-only scan, но не гарантирует выбор такого плана или отсутствие heap fetches: это зависит в том числе от visibility map. Planner cost не является измерением времени. [PostgreSQL 16: index-only scans](https://www.postgresql.org/docs/16/indexes-index-only-scans.html).

### Общий shortlist с учётом сценариев

Варианты с ключом без подходящего default B-tree opclass и без явно заданного opclass
исключаются до канонизации с `NO_BTREE_OPERATOR_CLASS` и warning, а не превращают корректный
каталог в `CATALOG_ERROR`. Это относится и к `json IS NULL` / `IS NOT NULL`: исходный SQL
остаётся целым, индексируемые колонки продолжают участвовать в генерации/поиске. Сохраняется
фактическое число исключённых перечисленных вариантов; им не назначаются ID/DDL/size/cost.

Локальные списки объединяются по канонической структуре с объединением породивших query IDs. Выбранный `candidate_ranking` задаёт только порядок общего shortlist после локального отбора. Для сценария `s` и множества различных породивших кандидата запросов `Q(c)`:

```text
frequency:     rating_s(c) = Σ_{q ∈ Q(c)} u_s(q)
baseline_cost: rating_s(c) = Σ_{q ∈ Q(c)} u_s(q) × cost(q, empty)
u_s(q) = f_s(q) / Σ_q f_s(q)
```

`frequency` остаётся default; `baseline_cost` экспериментален до убедительного сравнения на реальной нагрузке. Большая стоимость baseline даёт редкому дорогому SQL возможность повлиять на shortlist, но не доказывает пользу его индекса. Для `baseline_cost` сравниваются точные десятичные числители `Σ f_s(q) × cost(q, empty)` через `BigDecimal.valueOf` исходных конечных `Double`: общий положительный знаменатель одинаков внутри сценария. Рейтинг не требует деления и округления до 9 знаков; произведения/суммы рейтинга не переполняют `Double` и не теряют положительный вклад из-за underflow. Существующие проверки нормирования частот сохраняются: переполнение `Σ f_s(q)` или потеря положительного `u_s(q)` даёт `NUMERIC_ERROR` и при новом рейтинге. Ноль частоты или cost даёт нулевой вклад; кандидат с нулевым рейтингом во всех профилях исключается с `ZERO_BASELINE_COST_SUPPORT`, отдельно от глобального лимита. Профиль с нулевой стоимостью всех используемых SQL не имеет положительной очереди; все нулевые профильные baseline завершают pipeline до генерации по общему правилу.

Генератор получает разрешённый workload и сохранённый полный `EvaluationResult` пустого набора с точным покрытием query IDs. Отсутствующий/неполный baseline или непустые candidate IDs при `baseline_cost` — явная ошибка контракта. Отрицательные/нечисловые costs и частоты не заменяются нулём. Дополнительный EXPLAIN, повторный расчёт профильных метрик и бюджетов ради рейтинга не выполняются. `weight` не участвует ни в рейтинге, ни в сценарных квотах; постоянный положительный вес не менял бы порядок внутри своей очереди. Локальные caps, OR-provenance по уникальным SQL, INCLUDE-квоты и арность ключей сохраняются.

У каждого сценария две очереди: с одним и с двумя ключами, включая INCLUDE-варианты соответствующей арности. Payload не считается дополнительным ключом. Обе сортируются по убыванию рейтинга; для пар при равенстве используется приоритет группы из локальной генерации (лучший из породивших запросов), затем стабильный ID; для одиночных при равенстве — ID.

Начальные **до 16 кандидатов** выбираются внешним round-robin по profile ID. Каждый сценарий за ход добавляет первый ещё не выбранный кандидат с положительным рейтингом из своей текущей очереди, пропуская уже выбранные. Внутри сценария очереди чередуются после каждого успешного выбора, начиная с одноколоночной; если нужная очередь исчерпана, используется другая. Первые 16 образуют начальный shortlist. Затем обход продолжается с сохранёнными позициями очередей до ещё **48 резервных кандидатов** либо исчерпания всех списков; всего хранится до 64 различных кандидатов. Поэтому равные рейтинги одного широкого запроса не отдают все места одиночным индексам. `weight` не используется для распределения. Это уменьшает риск подавления редкого режима абсолютным объёмом другого, но не гарантирует покрытие каждого SQL или качество каждого сценария. Кандидаты с положительной поддержкой вне ограниченной очереди из 64 получают `GLOBAL_CANDIDATE_LIMIT`; попадание в резерв само по себе не означает отказ.

Подготовка проходит начальный shortlist и затем резерв в том же порядке, пока не накопит **16 индивидуально допустимых кандидатов** либо не достигнет ограничений. Дедупликация, представительство профилей и чередование одиночных/пар сохраняются; SQL и локальная генерация не расширяются. После бюджетного отказа или локальной ошибки гипотезы берётся следующий кандидат. Отсев по доступному write budget выполняется общим модулем метрик **до запроса размера**; неизвестный размер при этом остаётся `null`, а не подменяется нулём. После успешного размера допустимость проверяется общим расчётом бюджетов, включая `ceil(1.2 × estimated_bytes)`.

На всю подготовку разрешено не более **32 вызовов `estimateSize`**, включая неуспешные. Пределы подготовки — 16/48/32; она использует общий эффективный deadline команды/поиска без нового отсчёта. Уже измеренный кандидат повторно не измеряется. Размеры и write units непроверенного остатка неизвестны. Кандидатная `HYPOTHETICAL_INDEX_ERROR` допускает продолжение только после успешной очистки сессии и отражается отдельно от бюджетного отказа. Потеря сессии, deadline и отмена прекращают подготовку: полный baseline позволяет сохранить `partial` без нового EXPLAIN; численная ошибка остаётся `failed`.

Остановка подготовки различает `SHORTLIST_FULL`, `RESERVE_EXHAUSTED`, `SIZE_LIMIT`, `DEADLINE_EXCEEDED`, `CANCELLED`, `CONNECTION_LOST` и `FAILED`. Исчерпание резервной очереди или лимита размеров не запускает новую генерацию. `SIZE_LIMIT` сопровождается warning; поиск выполняется на уже подготовленных кандидатах и может завершиться `completed`, как при других candidate caps. Эти пределы ограничивают затраты и не гарантируют улучшение качества.

Для серии бюджетов предусмотрен общий путь подготовки: один финальный пул до 16 кандидатов готовится с refill при наибольшем бюджете серии. Отдельные точки фильтруют этот фиксированный пул по своим бюджетам в памяти; независимые запросы размеров, refill и изменение исходного пула запрещены. Команда `analyze-series`, общий deadline, независимые точки и сводка определены в дополнении #75.

ID определяется канонической структурой `schema, table, method, ordered keys, directions, nulls, collation, opclass, sorted included columns`; имя `ib_<hash>` стабильно, идентификаторы экранируются средствами драйвера. Для финальных кандидатов сохраняются DDL, происхождение, размер, write units и состояния рассмотрения. Структурные ограничения порядка ключей и сортировки описаны в [Multicolumn indexes](https://www.postgresql.org/docs/16/indexes-multicolumn.html), [Indexes and ORDER BY](https://www.postgresql.org/docs/16/indexes-ordering.html).

### Границы работы и диагностика

До 20 запросов × 3 таблицы дают не более 60 локальных областей. После ограничения колонок локальная генерация рассматривает не более `16 + 4 * 16 * 15 = 976` определений на область, то есть до **58 560 событий генерации** всего. Обрабатывается одна область за раз; после shortlist в общем пуле не более **1920 локальных записей** до дедупликации. Лимиты проверяются до создания больших списков; deadline действует и на AST/генерацию. Эти границы не включают внутреннюю работу планировщика PostgreSQL.

Для каждой области сохраняются число обнаруженных/оставленных колонок, фактически перечисленных/дедуплицированных/оставленных определений. Для общего пула — число до/после дедупликации, начальный shortlist, размер резерва, проверенные кандидаты, size-вызовы, бюджетные отказы, кандидатные ошибки, допустимые пополнения из резерва, итоговый размер shortlist и причина остановки подготовки. В отчёте сохраняется вся ограниченная очередь, включая нерассмотренный остаток; она не означает, что поиск получил больше 16 кандидатов. Условное «полное число всех возможных индексов» не вычисляется: для неперечисленной части оно `null`. Формулировка — «часть пространства не генерировалась», а не «все остальные бесполезны».

Таблица со 100 колонками и фильтрами по двум не вызывает перебора 100 колонок. Если запрос использует все 100 в условиях, применяются ограничения с предупреждениями. Даже 100 одиночных и 100 × 99 упорядоченных двухколоночных определений дали бы 10 000 кандидатов без дополнительных направлений. После shortlist из 16 полный перебор наборов размера 0–5 всё ещё равен 6885; он не используется в рабочем анализе.

## 6 Оценка наборов через HypoPG

Один запуск владеет одним физическим PostgreSQL connection. HypoPG хранит гипотетические индексы в backend session и использует их для EXPLAIN без ANALYZE. Оценка размера — `hypopg_relation_size`. [HypoPG usage](https://hypopg.readthedocs.io/en/rel1_stable/usage.html).

Контракт `evaluate(S)`:

1. Очистить предыдущие гипотезы через `hypopg_reset()`.
2. Создать ровно индексы набора `S` через `hypopg_create_index()`.
3. Для каждого query ID общего workload выполнить `EXPLAIN (FORMAT JSON)` и прочитать корневой Total Cost; запросы идут в порядке query ID.
4. Вернуть `cost_by_query_id` и планы только после успеха всех SQL. Отдельные профили не вызывают повторного EXPLAIN: метрики считаются над этим вектором в памяти.
5. В `finally` очистить гипотезы; после сбоя транзакции сначала rollback. Закрытие соединения завершает сессию.

Baseline оценивает пустой набор гипотез. Все оценки используют одну БД и одинаковые настройки планировщика; `enable_seqscan=off` ради красивого эффекта не включается. Изменение схемы/данных/статистики во время анализа может менять результаты: воспроизводимое демо выполняется без параллельных изменений и с сохранённым seed/ANALYZE. Одна сессия не обещает неизменность внешней БД.

Кэш живёт только внутри запуска; ключ — отсортированные candidate IDs, значение — полный вектор стоимости. Baseline и планы текущих лучших `robust`/`mean` наборов сохраняются при оценке; промежуточные планы остальных наборов можно освобождать. Финальный экспорт не запускает EXPLAIN заново. Ошибочные наборы помечаются отдельно и не повторяются в этом запуске.

Нельзя суммировать одиночные выигрыши и выдавать их за эффект комбинации: каждый рассмотренный набор оценивается целиком. [Combining indexes](https://www.postgresql.org/docs/16/indexes-bitmap-scans.html).

Extension устанавливается при подготовке контейнера. Runtime role получает доступ на чтение demo schema и функции HypoPG. Анализ не создаёт реальные индексы и не исполняет пользовательский SQL через ANALYZE. Фактические измерения — отдельный явно запускаемый эксперимент на тестовой БД.

## 7 Алгоритм поиска

Поиск отделён от evaluator и критерия сравнения. MVP не гарантирует глобальный оптимум; возвращает лучший полностью оценённый допустимый набор для выбранного `objective`. При любом успешном `evaluate` обновляются оба лучших набора (`robust` и `mean`) среди общего пула исследованных конфигураций, включая baseline и одиночные индексы.

### Жадный этап

1. Полностью оценить baseline. Если поиск не нужен из-за нулевого места, `max_indexes` или всех нулевых baseline costs, завершить с пустым набором.
2. Сгенерировать начальный shortlist и ограниченный резерв; подготовить до 16 индивидуально допустимых кандидатов по правилам §5 с размерами/write units и причинами отказов. Поиск получает только подготовленный финальный shortlist.
3. Начать цепочку с `S = empty`. Для каждого допустимого добавления `i` полностью оценить `S + i`, включая нулевую/отрицательную одиночную пользу.
4. Для движения по цепочке пригодны только добавления, лексикографически улучшающие первые два компонента критерия: `(r,m)` для `robust`, `(m,r)` для `mean`. Равный худший результат и лучшее среднее — разрешённое продвижение; меньшие bytes сами по себе не являются пользой добавления.
5. Из пригодных добавлений выбрать результат с минимальным полным ключом выбранного objective из раздела 4. Место и запись определяют допустимость и разрешают равенства; в v0.2 старый скалярный score «выигрыш / доля бюджета» не используется. Так критерий выбора шага совпадает с критерием итогового результата.
6. Добавить выбранный индекс и повторять до отсутствия положительного допустимого добавления или достижения `max_indexes`. Кандидат с нулевой одиночной пользой не объявляется глобально бесполезным: он остаётся доступен repair-этапу.

### Один ограниченный проход пересмотра

После greedy фиксируется `S0` — лучший допустимый набор для выбранного критерия среди всех уже полных оценок. До **8 / 28 / 256 новых попыток оценки наборов** для `fast` / `normal` / `deep` используются для одного прохода по соседям этого фиксированного набора; очередь не перестраивается рекурсивно после улучшения.

Три очереди:

1. `0→2`: `S0 + {j,k}` при наличии двух свободных слотов; в том числе пары из пустого набора.
2. `1→1`: `(S0 - {i}) + {j}`.
3. `1→2`: `(S0 - {i}) + {j,k}`.

`i` берётся из `S0`, `j,k` — разные кандидаты финального shortlist вне `S0`. Проверяются max_indexes, бюджеты и известные ошибки. Объединённый список имеет не более `120 + 55 + 275 = 450` структур до фильтрации — это консервативная граница для 16 кандидатов и 5 выбранных. Полные наборы дедуплицируются.

Порядок детерминирован: для `robust` выбирается худший положительный-baseline профиль `S0` (при равенстве — profile ID), для `mean` используется ожидаемая стоимость. Входящие кандидаты ранжируются по убыванию известной одиночной пользы на этой метрике, затем по размеру и ID. Кандидаты без успешной одиночной оценки идут после известных, в порядке ID; нулевая польза не исключает кандидата. Для пары используется лексикографическая пара рангов её членов, для замен последним ключом — ID удаляемого индекса. Эти ранги задают только порядок проверки, не оценку эффекта сочетания.

Очереди обходятся round-robin в порядке `0→2`, `1→1`, `1→2`, пропуская пустые. Кэшированные оценки переиспользуются без расхода слота; ранее ошибочные конфигурации пропускаются. Неудачный новый вызов `evaluate` расходует один слот выбранного repair-лимита. После каждого полного результата обновляются incumbents. Лучший итог не обязан совпадать с последним звеном greedy или первым улучшением repair.

Один проход не гарантирует нахождение всех полезных пар, выхода из любого локального решения или покрытия всего соседства. Он должен исправлять предусмотренную фикстурами бюджетную ловушку, где замена одного индекса парой даёт лучший допустимый результат.

### Лимиты, ошибки и статусы

Пользователь выбирает разрешённые затраты анализа именованным пресетом. Все шесть эффективных пределов задаются одной моделью `RunLimits` в общем `RunContext` и передаются evaluator; локальные таймеры или отдельные несогласованные лимиты не вводятся.

| Режим | Весь анализ, с | Поиск, с | Один EXPLAIN, с | Подключение, с | Попытки EXPLAIN | Новые repair-попытки |
| --- | --- | --- | --- | --- | --- | --- |
| `fast` — быстрый | 30 | 20 | 2 | 5 | 500 | 8 |
| `normal` — обычный, default | 90 | 60 | 2 | 5 | 2000 | 28 |
| `deep` — глубокий | 300 | 240 | 2 | 5 | 10000 | 256 |

`normal` сохраняет прежние ресурсные пределы. Лимиты `fast` сокращают разрешённую работу; `deep` разрешает больше времени и новых оценок того же фиксированного соседства. При любом режиме пул содержит до 16 кандидатов, `max_indexes ≤ 5`, greedy и fixed-`S0` repair не меняются. Более глубокий режим может вернуть тот же результат; улучшение не гарантируется. Сравнение качества и затрат при одинаковом пуле описано в [режимах анализа](docs/analysis-modes.md).

Лимит EXPLAIN включает неуспешные попытки, baseline и все этапы; кэш не расходует EXPLAIN. При `Q≤20`, `N≤16`, `K≤5` greedy делает не более `Q * (1 + 16 + 15 + 14 + 13 + 12) = 1420` вызовов. Только для `normal` repair добавляет не более `28 * Q = 560`: верхняя оценка обычного запуска — **99 наборов / 1980 EXPLAIN**, оставшиеся 20 не обещают дополнительный поиск. Для `deep` граница 1980 не действует; разрешено до 10000 попыток EXPLAIN и 256 новых repair-попыток. Профили не умножают число вызовов. Экспорт не переоценивает финальные планы.

Время всего анализа отсчитывается с начала команды, включая валидацию и introspection. Поисковый бюджет включает baseline, генерацию и подготовку размеров. До baseline фиксируется `search_started_at`; для baseline/candidates/greedy/repair действует `effective_deadline = min(command_started_at + command_timeout, search_started_at + search_timeout)` с пределами выбранного режима. Выбор режима до открытия БД не перезапускает часы команды. Подготовка до baseline использует общий deadline. Часы монотонные; оставшееся время проверяется перед каждой операцией.

Пока режим из JSON ещё не извлечён, чтение и разбор ограничены максимальным общим бюджетом `deep` (либо явным CLI-пресетом); после выбора режима немедленно проверяется его собственный предел с учётом всего уже прошедшего времени, без перезапуска часов.

Effective deadline передаётся всем CPU-проходам и операциям адаптера соответствующей стадии. Один EXPLAIN — не дольше меньшего из двух секунд и оставшегося времени. Другие SQL получают statement_timeout по оставшемуся времени; подключение — не более пяти секунд и оставшегося времени. Deadline проверяется до/после вызова парсера и между проходами AST/генерации; принудительное прерывание внутри стороннего парсера не обещается, а превышение обнаруживается при его возврате. По окончании незавершённый SQL отменяется, соединение очищается или закрывается. Ограничения — бюджет анализа, а не обещание точной длительности при задержке стороннего вызова, отказе сети/драйвера или записи отчёта. Экспорт результата использует оставшееся общее время, если оно есть; минимальный partial сохраняется и при исчерпании бюджета поиска.

Кооперативная отмена обозначается `CANCELLED`: новый SQL не запускается, активная операция отменяется и сессия закрывается. При полном baseline и пригодном сохранённом результате возвращается partial, иначе failed. Обработчик SIGINT инициирует отмену и освобождение сессии; сохранение отчёта при завершении JVM не гарантируется.

- `completed`: предусмотренный ограниченный поиск завершён; candidate caps сами по себе не превращают статус в partial, но всегда дают warnings.
- `partial`: есть полный baseline и пригодный результат, но выполнению мешал временной/EXPLAIN/repair лимит, потеря соединения, кооперативная отмена или неполные/ошибочные оценки. При достижении выбранного лимита новых repair-попыток и оставшихся непроверенных допустимых соседях — `partial`, причина `REPAIR_LIMIT`. В отчёте видны завершённые этапы.
- `failed`: нет полного baseline либо вход/каталог/численные расчёты не позволяют получить корректный сравнимый результат.

Ошибка создания конкретного кандидата исключает его из дальнейшего поиска с причиной, анализ остальных продолжается; кандидатная ошибка даёт warning. В данных отчёта остаётся полная запись отклонённого кандидата: определение, DDL, происхождение и причина отказа; не полученные оценки остаются `null`. Ошибка EXPLAIN обесценивает весь рассматриваемый набор: запрещено подменять его нулевым cost или суммой по оставшимся SQL. Потеря соединения и общий deadline не маскируются под ошибку отдельного кандидата. Неполный набор не участвует в incumbents.

## 8 Архитектура, CLI и отчёты

Стек: Kotlin/JVM на JDK 25 LTS (уточнено 10 ноября 2026 при создании каркаса), Spring Boot в режиме CLI (`WebApplicationType.NONE`), PostgreSQL JDBC, Gradle Kotlin DSL. Сериализация JSON — Jackson. PostgreSQL 16 с HypoPG и demo seed поднимается через Docker Compose. React, HTTP API, worker-сервер и polling не требуются.

Контракт команды: `indexbudget analyze --workload <path> --output-dir <path> [--analysis-mode fast|normal|deep] [--candidate-ranking frequency|baseline_cost]`. CLI-параметр `--analysis-mode` переопределяет `analysis_mode` JSON; если оба отсутствуют, используется `normal`. `--candidate-ranking` аналогично переопределяет `candidate_ranking`; без обоих используется `frequency`. Неизвестное значение и повторный CLI-параметр отклоняются с `INVALID_INPUT` (exit 2). Настройки подключения берутся из окружения; DSN и пароли не попадают в отчёт, SQL и логи. Примеры входа хранятся в репозитории. Обычная команда `analyze` выполняет один анализ и использует одну выделенную JDBC-сессию. Команда серии `analyze-series` описана в дополнении #75: подготовка и каждая точка имеют отдельные сессии.

```text
CLI/JSON → CatalogSnapshot + AST → ResolvedWorkload → ограниченные кандидаты
        → Search(objective, budgets) ↔ HypoPG evaluator → cost_by_query_id
        → расчёты профилей/выбор → AnalysisReport → HTML / JSON / SQL
```

Модули обмениваются `WorkloadInput`, `Profile`, `CatalogSnapshot`, `ResolvedWorkload`, `IndexCandidate`, `EvaluationResult`, `SearchResult`, `AnalysisReport` и общим `RunContext` с deadline/счётчиками. `EvaluationResult` содержит стоимость по каждому query ID; средние и сценарные метрики вычисляются модулем расчётов, не адаптером БД. Search использует единый компаратор и не содержит второй независимой реализации формул.

Стадии в stderr: validation, introspection, baseline, candidates, greedy, repair, report. Показываются выбранный режим, рейтинг shortlist, все шесть эффективных лимитов, фактические попытки EXPLAIN/оценок/repair, полные оценки и cache hits; итог содержит статус и причины остановки, в том числе для completed. Процент прогресса не выдумывается. Ошибка содержит `code`, `message`, при необходимости `query_id`, `profile_id`, `details`. Сохранённые ошибки результата `partial` также выводятся в stderr, каждая отдельной строкой `CODE: JSON`; после успешного сохранения такого результата код выхода остаётся 3.

Коды выхода: `0` — completed, `2` — невалидный/неподдержанный вход, `3` — partial с сохранённым результатом, `1` — прочий failed или ошибка записи артефактов. При failed успешный `indexes.sql` не создаётся. Вывод сначала записывается во временные файлы с run ID; на ошибке нельзя оставлять смесь старого SQL и нового отчёта. Непустой output-dir на начальной валидации отклоняется с `OUTPUT_DIRECTORY_NOT_EMPTY` и кодом 2. Если повторная проверка каталога на стадии экспорта обнаруживает появившиеся файлы, это ошибка публикации `EXPORT_FAILED` с кодом 1; существующие файлы сохраняются. Для каждого запуска пользователь задаёт отдельный каталог.

`report.json` имеет `schema_version: 3` для B-tree-only или `4` при разрешённом/ручном BRIN или hash (#114), `spec_version: "0.2"`, run ID, hash входа, версии окружения, длительность, objective, `analysis_mode`, эффективный `candidate_ranking`, все эффективные лимиты, нормированные веса, budgets, write profile, `cost_guards` (заданные пределы и исходы по выбранному набору с подписью planner cost, не latency/SLA), baseline, выбранный набор и costs/plans по SQL, метрики каждого профиля, обе оценки объёма, warnings и статистику отсечений/поиска. Hash — SHA-256 от UTF-8 JSON с рекурсивной сортировкой ключей, без пробелов, с сохранением строк SQL и порядка массивов. Нормализация для hash не подменяет исходные SQL. Hash описывает исходный JSON до defaults и CLI-переопределения: флаги режима и рейтинга не меняют hash файла; эффективные режим, рейтинг и лимиты фиксируются отдельно в отчёте. Поле `candidate_ranking` и новые поля режима — совместимое расширение выходного JSON v3, существующие поля и единицы не меняются.

Диагностика подготовки #70 добавляет поля к выходному JSON v3 без изменения смысла прежних полей. `shortlisted_candidates` по-прежнему означает число первоначально отобранных кандидатов и равен новому `initial_shortlisted_candidates`; итог подготовки хранится только в новом `preparation.final_shortlisted_candidates`. У прежнего отчёта без новых полей сведения о refill неизвестны.

Имена и вложенность полей выходного JSON v3, единицы измерения и nullable-значения зафиксированы в [контракте отчёта v3](docs/report-v3.md). `selected_objective` задаёт критерий запуска; `incumbents_coincide` явно отмечает совпадение наборов. Сохранённые планы представлены JSON-значениями, неизвестные версии БД и неисследованные количества — `null`.

Расширение #79 версионирует выходной отчёт как **v3**: `definition.included_columns` — обязательный массив физических колонок (пустой для обычного индекса), `write_proxy_model: "row_changes_times_key_and_include_columns"` явно задаёт модель записи. Старый reader отчётов v2 должен отклонить v3 либо обновиться с поддержкой payload; игнорировать INCLUDE и воспроизводить только keys нельзя. Вход workload остаётся **v2**, параметры CLI не меняются. HTML и SQL используют те же определения и выбранные IDs, что JSON.

Сохраняются `best_robust` и `best_mean` из **одного общего пула полностью оценённых наборов**, `comparison_scope: "evaluated_sets"` и `selected_objective`. Это не два независимо завершённых поиска и не глобально лучшие решения. В HTML явно указывается, какой критерий управлял исследованием пула. Если наборы совпали, отчёт так и сообщает. Сравнение содержит среднюю/худшую стоимость, эффекты всех профилей, место и write units; цена устойчивости — `C_mean(best_robust) - C_mean(best_mean)` среди этого пула.

Причины различаются: точный дубль, отсечение колонок/локального/общего shortlist, превышение бюджета, ошибка гипотезы, отсутствие предельной пользы на конкретном шаге, не выбран поиском, не проверен из-за лимита. Слово «бесполезный» не используется как глобальный вывод. Кандидаты, не дошедшие до HypoPG, не получают вымышленных размеров и cost.

`report.html` — автономный файл без внешних CDN: сводка решения, сравнение профилей и двух incumbents, per-query таблица с регрессиями, бюджеты, индексы, режим анализа, рейтинг shortlist, все эффективные лимиты, фактические counters и причины остановки, ограничения модели и поиска. SQL/идентификаторы экранируются как текст HTML. `indexes.sql` содержит только выбранный набор с полностью квалифицированными таблицами и стабильными именами; другие рассмотренные индексы туда не попадают. В шапке SQL — run ID и hash входа. Автоматического выполнения нет.

Диагностика фиксированного пула: `preparation_scope` равен `run` для обычного анализа и
`common_pool` для бюджетной точки. В последнем случае `preparation` сохраняет работу общей
подготовки при максимальном бюджете. Отдельный `fixed_pool_selection` описывает текущую точку:
`pool_candidates`, `admissible_candidates`, `budget_rejected_candidates`, `size_attempts` (всегда 0).
В обычном анализе `fixed_pool_selection` равен `null`. HTML подписывает общую подготовку и
текущую точку отдельно; общий shortlist точки показывает число допустимых для неё кандидатов.
Значение `initial_shortlisted_candidates` по умолчанию наследует `shortlisted_candidates`,
в том числе для producers, заполняющих только прежнее поле.

### Представление рекомендации в HTML (#69)

Первый экран «Результат анализа» содержит выбранные `table(columns)`, эффект,
регрессии SQL. Рядом показаны число выбранных SQL и, если известны,
источник нагрузки, длительность окон и неполнота наблюдений. Baseline включает
существующие реальные индексы; selected — добавленный гипотетический набор.
Основной показатель подписан как оценочная стоимость выбранных запросов с учётом
их частот в сравнении с текущим набором индексов, без обещания ускорения выполнения.
После сводки следуют изменения SQL, сравнение профилей при двух–трёх профилях,
ресурсы и каталог индексов/DDL, исходная нагрузка и следующие шаги.
Формулы R/M, подробная методика, счётчики поиска и технические IDs находятся в раскрытиях.
Основной поток содержит короткие пояснения по месту использования без повторных
карточек, полных определений, SQL и планов.
При одном профиле средний и худший эффект совпадают и не дублируются; сравнение
критериев не показывается. При двух–трёх профилях сохраняются исходные имена и
повторяемая структура строк. Совпавшие наборы свёрнуты в подпись
«Оба критерия выбрали один набор» с раскрываемыми подробностями.
Таблицы SQL и профилей показывают исходную стоимость, стоимость всего выбранного
набора и сохранённое изменение; меньшая стоимость лучше. Повторяющие таблицы графики
не выводятся. При нулевом baseline процент неприменим, рост и отсутствие данных
подписываются явно. Таблица ресурсов различает оценку HypoPG и объём с запасом,
отключённый лимит записи, нулевой лимит, неизвестный расход и настоящий ноль.
Planner cost не является временем выполнения, а write proxy — измеренным замедлением
записи или количеством операций. Завершение поиска не подтверждает репрезентативность
наблюдений; неизвестные период и охват обозначаются рядом с выводом.

Основные проценты округляются обычно до одного знака, размеры используют читаемые
KiB/MiB/GiB или байты; число и единица не разрываются. Полные значения сохраняются
в деталях и JSON. Малое ненулевое изменение не называется отсутствием изменения.
Фиксированные шаблоны различают снижение, рост, неизменность, неприменимый процент
и отсутствующую рекомендацию; renderer не вводит собственные формулы метрик.
SQL с ухудшением показываются первыми; локальная сортировка меняет только порядок
строк, а ссылки раскрывают исходный SQL и сохранённые планы. Короткие подписи
`SQL 1`, `SQL 2` сохраняют исходный порядковый номер; полные IDs доступны в деталях.
Индексы обозначаются как `records(value)`, неоднозначные имена разных схем различаются
явно; полные определения и DDL сохраняются. `sourceQueryIds` означает происхождение
кандидата, не измеренную индивидуальную пользу. Источник, интервалы и охват импорта
видны только при наличии provenance; историческое время не смешивается с planner cost,
частоты в час — с фактически наблюдавшимися вызовами. Новых порогов достаточности окна нет.
CSS и фиксированный скрипт встроены в HTML; внешние ресурсы/запросы отсутствуют,
динамические значения экранируются, CSP разрешает только хеш скрипта сортировки,
раскрытия и копирования текста. Таблицы, приоритет регрессий и нативные детали
доступны также без JavaScript. В едином HTML серии каждый полный SQL, уникальный
сохранённый план и DDL имеют одно основное место; строки вариантов ссылаются на
общие каталоги. Различающиеся значения и планы разных запусков не объединяются
только по совпадению ID.
CLI, вход v2, JSON v3 и общая модель #68 сохраняют свои форматы и семантику.

### Сводка и происхождение (#68)

Общий `AnalysisReport` содержит сводку выбранных IDs, снижения ожидаемой взвешенной стоимости
(`100 * (B_mean - C_mean) / B_mean`), M/R, расходов/лимитов и числа SQL с ростом cost.
Все проценты используют один доменный расчёт; расходы берутся из сохранённых бюджетных метрик.
Серии baseline/selected/best_robust/best_mean по профилям и SQL строятся только из сохранённых
данных, без новых EXPLAIN. JSON и HTML получают одну модель; внешний отчёт v3 расширяется
аддитивно полями `summary`, `profile_comparisons`, `query_effects`, `workload_provenance`.

Нулевой baseline, отсутствие данных, отключённый лимит и фактический ноль различаются.
Непредставимые относительные **per-query** показатели, включая underflow положительного отношения в ноль, помечаются `out_of_range`, при этом
полные исходные costs сохраняются; это не отменяет `NUMERIC_ERROR` для некорректных поисковых
метрик. Потеря положительного профильного отношения или M в ноль даёт `NUMERIC_ERROR`;
реальный ноль при нулевой стоимости и представимые subnormal-отношения допустимы.
Профильные метрики/сохранённое M не пересчитываются в renderer.
M нельзя называть средним отношений профилей, R — гарантией отсутствия регрессии отдельных SQL.
Сводка сохраняет `evaluated_sets`, совпадение incumbents, цену компромисса и ошибки/остановки
partial/failed. Failed не получает ни рекомендованного набора, ни нулевого числа регрессий.

При наличии provenance показываются источник, интервалы и полнота наблюдения, правило отбора,
числитель/знаменатель охвата и репрезентативность примеров SQL. Историческое время в миллисекундах
выводится отдельно; оно не является ожидаемым временем с новыми индексами. Для ручного workload
эти сведения отсутствуют. Конкретный wire-контракт и nullable-семантика — в
[формате отчёта v3](docs/report-v3.md#сводка-и-данные-сравнений-68).

Приёмка интеграции #68 использует фактический результат импортёра #67: сохранённые
снимки → workload и манифест → обычный analyze → HTML/JSON/SQL. Источник, окна, отбор,
охват и примеры должны соответствовать манифесту; исключённые из анализа доступные полные
top-level записи остаются в знаменателе охвата. Сборка/экспорт сводки после закрытия сессии не увеличивает
счётчики оценки и EXPLAIN. Синтетический provenance не заменяет эту проверку.

## 9 Демо и проверка гипотез

Все реальные измерения выполняются отдельно от команды анализа на воспроизводимой тестовой БД. Оценка planner cost, фактическое время, фактический размер и write units показываются раздельно.

1. **Сценарный критерий:** один список SQL, одинаковые кандидаты и бюджеты, два разных профиля частот. Сравнить `mean` и `robust` при одинаковой стратегии и лимитах поиска; показать среднее и худшее отношение к baseline. Дополнительные заранее зафиксированные профили частот не используются для настройки выбора, а служат проверкой чувствительности.
2. **Поиск:** при одном фиксированном objective сравнить greedy и greedy+repair. Показать качество, время, число EXPLAIN и расхождение с эталоном. Нельзя приписывать эффект одновременно изменённых objective и стратегии только новой эвристике.
3. **Малый эталон:** для до восьми кандидатов и максимум пяти выбранных полный перебор в отдельном проверочном инструменте рассматривает до 219 наборов (657 EXPLAIN для трёх SQL). Это оптимум только в фиксированном пространстве кандидатов по модели. Инструмент не входит в рабочую команду и не наследует ресурсные пределы её пресетов; имеет собственный явно заданный предел времени.
4. **Фактическая проверка:** построить выбранные финальные наборы на отдельной demo DB, измерить размеры и времена запросов с повторениями и одинаковыми условиями; зафиксировать прогрев, порядок прогонов, число повторений и разброс. При демонстрации влияния записи — отдельный write benchmark с восстановлением одинакового состояния между вариантами.
5. **Бюджетные профили:** изменение ненулевых бюджетов должно менять допустимость и на подготовленном примере рекомендацию. Для демонстрации модели записи полного MVP использовать две таблицы с разными частотами изменений; одностабличный PoC остаётся допустим.

Воспроизводимый эксперимент #109 на сценарии #106 использует один реальный write-window
#107, сохраняет совпадения robust/mean одного запуска и отдельно проверяет смену наборов
между ненулевыми бюджетами места и записи при неограничивающем втором бюджете.
[Методика и результаты](docs/experiments/observed-budgets-2026-11-12/README.md).
Это проверка planner cost и write proxy; физический смешанный benchmark относится к #110.

Сравнение `frequency` и `baseline_cost` фиксирует SQL, каталог/baseline, budgets, objective, финальное число кандидатов и лимиты поиска. Состав shortlist является результатом сравнения; сохраняются оба состава, выбранные наборы, профильные/средние/худшие метрики, size/write расходы, size/EXPLAIN/evaluation counters и длительность. Совпадение и ухудшение также фиксируются. Синтетические vectors проверяют механику и не служат основанием менять default; [контрольный эксперимент](docs/experiments/candidate-ranking-2026-11-11/README.md).

Успех сценарного эксперимента — обнаруженный и объяснённый компромисс на реальных оценках/измерениях, а не заранее назначенный процент выигрыша. Если наборы совпали или ремонт не помог, это фиксируется. Синтетические evaluator-фикстуры проверяют алгоритм, но не заменяют PostgreSQL и не доказывают рыночное преимущество. Идея нескольких сценариев имеет исследовательские предшественники: [Robust Index Selection](https://link.springer.com/article/10.1007/s42979-022-01473-7), [Index Selection Evaluation](https://github.com/hyrise/index_selection_evaluation).

## 10 Обязательные проверки

- Валидация query/profile IDs, нулевых частот, весов, лимитов входа, неизвестных SQL-конструкций, отсутствующих/отрицательных/нечисловых write rates, отключённого/нулевого write budget и v1 input.
- Метрики: разные baseline profiles; различие `sum(p*C)/sum(p*B)` и `sum(p*C/B)`; нулевой baseline; конечность чисел; один профиль; plateau по `R` с улучшением `M`; детерминированные равенства.
- Режимы анализа: каждый пресет, прежний вход без поля, CLI/JSON precedence, неверные значения, границы времени/EXPLAIN/repair, cache/error accounting, failed без полного baseline и partial с сохранённым результатом без дополнительных EXPLAIN; сравнение качества/затрат на одном workload при одинаковом пуле.
- Поиск: взаимодействие индексов без сложения одиночных выгод; бюджетная ловушка 1→2; 0→2 из пустого набора; сохранение лучшего полного результата при ошибке/timeout; оба incumbents из одного пула; cache hit; repair cap и точные счётчики.
- HypoPG: изоляция сессии, создание ровно набора, cleanup после успеха/ошибки, rollback, cancellation, повторный запуск, реальные существующие индексы в baseline.
- Широкая таблица: 100 колонок, `SELECT *`, условия/сортировка на двух — остальные 98 не порождают кандидатов. Добавление неиспользуемых колонок не меняет генерируемые структуры, хотя costs из-за ширины строки могут измениться.
- Широкий workload: запрос со 100 колонками условий остаётся целым в EXPLAIN; ограничения 16/32/16 срабатывают до раздувания списков и сопровождаются диагностикой. До 1920 локальных записей, до 58 560 событий генерации; число EXPLAIN ограничено выбранным пресетом (до 2000 в `normal`).
- Рейтинг shortlist: редкий дорогой и частый дешёвый SQL, независимость сценарных квот от относительных весов, детерминированные равенства, zero baseline, числовые границы и неверный baseline; CLI/JSON precedence и исходный hash. Robust/mean, budgets и полная оценка наборов сохраняются.
- Сценарный shortlist: профиль с малым абсолютным трафиком и собственными кандидатами участвует в round-robin; результаты детерминированы при одинаковом входе/каталоге. Отсечения не маскируются под полный поиск.
- При одном широком запросе и равных рейтингах, если в пуле есть не менее восьми разных одиночных и восьми разных составных кандидатов, начальный shortlist содержит по восемь каждого вида; пары не вытесняются только из-за числа ключей. После бюджетного отсева соотношение финального shortlist зависит от допустимости.
- Пополнение shortlist: большая часть начальных 16 нарушает бюджет, резерв содержит допустимые варианты; проверяются итоговый пул и выбранные наборы, число size/EXPLAIN вызовов, редкий профиль, равные рейтинги, детерминизм, ошибки размера, исчерпание резерва/32 size-вызовов/deadline и сохранение неизвестных оценок. Отдельные точки фиксированного пула не выполняют refill; улучшение качества не является обязательным результатом.
- Артефакты: JSON/HTML/SQL согласованы по run ID, hash и выбранным индексам; отсутствуют секреты; HTML безопасно отображает SQL; ошибка экспорта не выглядит как успешный запуск.

## Дополнение плана #64: ручной набор индексов

Необязательный `manual_indexes` расширяет workload v2 структурированными nonunique
определениями B-tree (1–2 колонки) или BRIN/hash (одна колонка), всего 1–5 индексов. Обычный поиск выполняется первым;
ручной набор получает отдельную полную оценку на том же baseline, SQL, профилях,

Бюджетно недопустимую идею можно измерить, явно сохранив нарушения. Она не становится

Формат входа, правила точных дублей, ошибки и дополнения JSON/HTML зафиксированы в
[контракте ручного сравнения](docs/manual-index-comparison.md). Реальные индексы
не создаются; indexes.sql сохраняет только выбранную автоматическую рекомендацию.

## Дополнение плана #64: сбор исходной статистики

Отдельные команды `stats snapshot` и `stats pair` сохраняют read-only снимки доступной
pg_stat_statements текущей PostgreSQL 16 БД до top-N/ранжирования. Это не команда анализа
и не автоматическое преобразование нормализованных SQL в исполняемый workload.
Версионированный формат snapshot v1, составная идентичность источника/записи, ресурсные
пределы, неполнота и область чтения зафиксированы в
[контракте снимков](docs/statistics-snapshots.md). Каждое чтение имеет собственный deadline;
ожидание между снимками не использует соединение и бюджет поиска индексов. Подготовка
расширения и изменение настроек БД остаются явными административными действиями.

### Импорт наблюдаемого workload (#67)

`import-workload --config <path> --output-dir <new directory>` использует расчёт #66
над 1–3 сохранёнными окнами #65 и явные примеры SQL по полному ключу
`source_id/dbid/userid/queryid/toplevel`. Один пример на запись; исходный search_path
не угадывается. В первом срезе оператор задаёт явный контекст с `pg_catalog` первым;
роль, исходные bind types/значения и generic plan не восстанавливаются из статистики.
AST-сопоставление разрешает только репрезентативные скалярные подстановки параметров,
все имена/типы/операторы примера повторно проверяются существующим анализатором.
Неизвестные данные не заполняются нулями. Разные контексты одинакового queryid не
объединяются; nested-записи не импортируются во избежание двойного учёта.

Отбор до 20 SQL — round-robin очередей всех профилей в порядке конфигурации,
внутри по calls/hour и полному ключу при равенстве. Профили получают полные векторы
общих query IDs; пустой профиль после отбора — неуспешный импорт, а не молчаливое удаление.
Охват считается отдельно по окнам со знаменателем доступных полных matched/stable
top-level наблюдений, включая исключённые SQL; неизвестная часть видна явно.
Исторические миллисекунды не становятся cost, частоты вызовов — write rates.

Выход — workload v2 с существующим `provenance` v1 (#68) и отдельный
манифест v1 с выбором/исключениями, периодами, источниками и хэшами примеров. При
отсутствии пригодного результата сохраняется failed-манифест без workload. Обычный
ручной ввод сохраняется. JSON v3/HTML анализа переносят происхождение из того же
workload, без нового EXPLAIN. Нормативные форматы, контекст, политика неполноты,
resource limits и воспроизведение определены в [контракте импорта](docs/observed-workload-import.md).

### Частоты наблюдаемых окон (#66)

Выход коллектора #65 преобразуется в 1–3 именованных профиля с положительными весами.
Частота — Δcalls×3600/Δseconds по полному ключу источника/записи; представительные
границы — середины неперекрывающихся чтений снимков. Сохраняются исходные интервалы
и диапазон возможной длительности. Общий список SQL формирует импортёр #67;
отсутствующие/недостоверные наблюдения не заполняются нулями. Reset, dealloc,
уменьшение counters и смена ключей дают явные причины неполноты. Исторические времена
отделены от planner cost; ограничение обнаружения адресного reset в PG16 сохраняется.
Нормативные правила неполноты и формат profiles v1 —
[контракт частот](docs/statistics-frequencies.md); workload/report v2 не меняются.


## Дополнение плана #64: серия бюджетов (#75)

Отдельная команда:

```text
indexbudget analyze-series --workload <v2.json> --series <series-v1.json> --output-dir <path> [--analysis-mode fast|normal|deep] [--candidate-ranking frequency|baseline_cost] [--series-timeout-seconds N]
```

Вход workload остаётся v2; JSON серии имеет собственный `schema_version: 1`. Поле `budget` выбирает ровно один бюджет: `storage_budget_bytes` или `write_budget_units_per_hour`. `values` — от 3 до 5 различных неотрицательных чисел в порядке запуска; значения storage — целые в диапазоне Long, write — конечные числа без потери положительного значения при представлении. JSON серии ограничен 64 KiB UTF-8. Строки, явный `null`, повторные ключи и неизвестные поля отклоняются. Различные write-значения должны оставаться различными после преобразования в Double; положительный underflow даёт `NUMERIC_ERROR`. `timeout_seconds` — необязательный целый общий лимит от 1 до 86400 секунд, по умолчанию 600; `--series-timeout-seconds` имеет приоритет над валидным JSON. При изменении write budget требуется полный общий профиль записи. Остальные бюджеты, SQL, профили, objective, candidate ranking и режим поиска фиксируются для всей серии.

Общая подготовка выполняет обычные parse/catalog/resolution/baseline и refill при максимальном значении выбранного бюджета. Она фиксирует исходный пул до 16 допустимых кандидатов и их оценки. Каждая точка использует существующий pipeline с собственными RunContext, выделенной JDBC-сессией, baseline, кэшем и набором ошибок. Генерация, size-вызовы и refill между точками не повторяются; меняется допустимость общего пула и комбинаций по текущему бюджету. Одиночные выигрыши не складываются в эффект набора. Метрики и допустимость используют общую доменную реализацию.

Общий deadline охватывает подготовку и точки; пределы выбранного режима продолжают действовать внутри каждой операции. После остановки новые точки не начинаются, а уже полученный пригодный результат сохраняется обычным механизмом partial. Ошибка одной точки не удаляет ранее опубликованные артефакты и не переносит её кэш/гипотезы/ошибки в следующую. Все сессии освобождаются на успехе, ошибке, deadline и отмене. Экспорт сохранённых данных не требует нового EXPLAIN. JVM shutdown hook инициирует отмену, однако сохранение ещё не опубликованного результата при завершении JVM не гарантируется.

Каждый run публикуется в своём подкаталоге; JSON/HTML/SQL одной точки относятся к её run ID, исходному hash workload и выбранному набору. Машинная сводка серии сохраняет источник, эффективные общие настройки, значения бюджетов, общий пул, условия подготовки, статусы всех точек, индексы, готовые метрики, расходы, счётчики и относительные ссылки на артефакты. Изменение baseline, каталога или доступных версий относительно подготовки отмечается явно. Совпадение наблюдаемых условий не доказывает неизменность всех данных, статистики или настроек планировщика; один общий пул также не означает одинаковый исследованный набор комбинаций. Нет обещания монотонного улучшения от большего бюджета или глобального оптимума. Planner cost, время анализа, размер и write proxy показываются раздельно.

Перед первой публикацией единственный владелец каталога фиксируется атомарно; конкурирующий запуск не может заменить чужую сводку и точки. Неудача подготовки с невалидным/неподдержанным SQL, неизвестным именем или неполным write profile сохраняет failed-сводку и код выхода `2`. Сводка и stderr сохраняют все шесть лимитов, фактические счётчики и ошибки подготовки/каждой начатой точки, в том числе partial. Источник сравнивается по доступным фактам фактически открытого backend, а не списку хостов JDBC URL; недоступная идентичность остаётся неизвестной.

Формат входа/сводки и примеры — [docs/budget-series.md](docs/budget-series.md). Workload v2 и запрос серии v1 не меняют версию; B-tree-only сохраняет сводку v1/report v3, а BRIN использует сводку v2/report v4 (#114).

### Автономная сводка бюджетов (#76)

`analyze-series` публикует корневой автономный `report.html` со сравнением бюджетов и подробностями вариантов, а также `series.html` только со сравнением, рядом с `series.json` из того же снимка, до подготовки, после каждой точки и при завершении. HTML использует готовые метрики domain без повторного расчёта формул или EXPLAIN. Первый экран показывает предлагаемый набор, изменение оценочной стоимости с учётом частот, известные регрессии SQL и существенные ограничения исходных наблюдений выбранного варианта. Завершение поиска не подтверждает репрезентативность нагрузки.

Таблица сохраняет исходный порядок бюджетов и показывает состав набора, готовый процент изменения cost по профилям, расход места и статус точки. Точные costs, M/R, расходы, лимиты, условия, остановки и ошибки доступны в раскрытиях. Повторяющие таблицу диаграммы не выводятся. При одном профиле средний и худший эффекты не дублируются; для двух–трёх сохраняются исходные названия. Failed/skipped, отсутствие данных и неприменимый процент при нулевом baseline не подменяются нулём. Рост, partial и изменившиеся/неизвестные условия различимы без опоры только на цвет. Одинаковые наборы отмечаются явно. Немонотонность эффекта среди сопоставимых рассчитанных точек объясняется ограниченным независимым поиском и компромиссами цели; отсутствие гарантии монотонности сообщается всегда. Неизвестный расход, фактический ноль, отключённая модель записи и отключённый лимит различаются.

Относительные ссылки ведут к опубликованным HTML/JSON/SQL каждой точки; отсутствующие артефакты не получают ссылок. Каталог серии переносится целиком и открывается без сервера/сети; стили встроены, динамический текст экранируется. На узком экране все значения доступны. Ошибка публикации даёт `EXPORT_FAILED` и сохраняет ранее опубликованные точки; устаревший HTML убирается при обработанной ошибке. Три файла заменяются последовательно, поэтому согласованность гарантируется после успешного завершения публикации, а не при аварийном завершении между заменами.

Корневой `report.html` отображает разделы сохранённых `AnalysisReport` через общий renderer, без чтения дочерних файлов, новых EXPLAIN или отдельного расчёта метрик. Переключатель синхронно меняет вывод, запросы, ресурсы и диагностику; полные отчёты не повторяются последовательно. Общие каталоги сохраняют полный SQL, DDL и уникальные планы один раз со ссылками из вариантов. Различающиеся данные разных запусков не объединяются только по ID. По умолчанию открыт пригодный вариант с наибольшим бюджетом, а при отсутствии пригодных — вариант с наибольшим бюджетом, включая failed/skipped. Это правило просмотра, не рекомендация бюджета. Отсутствующий отчёт не получает вымышленных подробностей. ID и ссылки изолированы по варианту; фиксированные скрипты под CSP управляют выбором и сортировкой. Без JavaScript доступны разделы всех вариантов и нативные раскрытия. Все подробности доступны в одном HTML без сети; отдельные JSON/SQL остаются по относительным ссылкам.

### Представление источника записи и DML (#108)

Демо явно выбирает ручной профиль или готовый наблюдаемый профиль из workload v2 после импорта. Копируются только rates и происхождение одного окна; frontend не пересчитывает формулы. Дробные строки/час не ограничиваются лимитом целых вызовов SQL формы. Неполное наблюдение не подменяется manual/нулём и не выключает лимит; при включённом write budget или write-серии оно отклоняется. HTML показывает окно, источник, полноту, ограничения и строки/час отдельно от SQL-частот, исторического времени и физических измерений. Для UPDATE/DELETE сводка и карточки уточняют, что cost оценивает поиск/подготовку строк без фактической модификации таблицы. Серия сохраняет происхождение записи и типы SQL в settings, старые отчёты допускают неизвестные поля. Подробный добавочный контракт и проверки — [docs/write-profile-ui.md](docs/write-profile-ui.md).
