# IndexBudget: спецификация MVP v0.2 для хакатона

Версия 0.2. Статус: черновик для ревью. Заменяет `IndexBudget-spec-v0.1.md`.

IndexBudget подбирает набор дополнительных индексов PostgreSQL для нескольких возможных режимов нагрузки при ограничении места и необязательном ограничении условной стоимости сопровождения записи. Пользователь задаёт общие SQL и несколько профилей их частот, а инструмент показывает лучший найденный набор для худшего сценария, сравнение со средним результатом и цену компромисса.

Главная проверяемая гипотеза MVP: набор, выбранный для усреднённой нагрузки, может давать мало пользы в другом важном режиме; сценарный критерий позволяет выбрать иной компромисс. Ограниченный пересмотр жадного решения проверяется как отдельное улучшение поиска. Продукт не заявляет научную новизну этих методов или превосходство над существующими советчиками без измерений.

Изменения относительно v0.1: Spring Boot CLI и локальный HTML вместо Ktor/React/REST; формат входа v2 с профилями; критерии `robust`/`mean`; повторное использование стоимости каждого SQL; ограниченные замены и пары; ограничения генерации до образования пар для широких таблиц; обновлённые PoC, задачи и проверки. Распределение владельцев сохраняется из [плана #2](https://github.com/ITMO-DevDays-2026-IndexBudget/IndexBudget/issues/2): поиск принадлежит Марату, расчёты и проверочные сценарии — Равилю.

## 1 Пользовательский сценарий и границы обещаний

Основной пользователь — разработчик или инженер БД с репрезентативными запросами и подходящим окружением PostgreSQL. Пример вопроса: «Какие индексы добавить в пределах 64 MiB, если состав запросов различается в обычный день и во время акции?»

1. Поднимает demo DB через Docker Compose; CLI подключается по переменной окружения `INDEXBUDGET_DATABASE_URL`.
2. Передаёт JSON с общим списком SQL, 1–3 профилями частот, бюджетами и выбранным критерием.
3. Запускает анализ из терминала и видит текущую стадию и счётчики.
4. Получает `report.html`, `report.json`, `indexes.sql`: выбранные индексы, расход бюджетов, эффект по профилям/запросам, альтернативу из исследованных наборов и ограничения результата.
5. Проверяет рекомендации на отдельной тестовой БД. Применение SQL — отдельное действие пользователя.

Сценарии описывают разные смеси запросов на одной БД с одной статистикой и одинаковыми настройками планировщика. Они не моделируют конкуренцию запросов, насыщение CPU/I/O, рост данных или неизвестную будущую нагрузку. Устойчивость означает качество оценочной стоимости на переданных профилях; гарантий latency, throughput и SLA нет.

Существующие реальные индексы сохраняются и участвуют в baseline. Бюджеты относятся только к новым индексам. Полное планирование миграций, удаление индексов, автоприменение, публичный сервис произвольного SQL и подключения к недоверенным БД не входят в MVP.

## 3 Входные данные

### Workload и профили

Версия входного формата — `schema_version: 2`; версия документа — 0.2. Формат v1 не принимается молча: CLI возвращает `UNSUPPORTED_SCHEMA_VERSION` с указанием перенести частоты из `queries` в `profiles`. Обратная совместимость до начала реализации не требуется.

```json
{
  "schema_version": 2,
  "objective": "robust",
  "queries": [
    {
      "id": "records_by_group",
      "sql": "SELECT id, value FROM public.records WHERE group_id = 42 ORDER BY created_at DESC LIMIT 20"
    },
    {
      "id": "records_by_value",
      "sql": "SELECT id, value FROM public.records WHERE value = 7 ORDER BY created_at DESC LIMIT 20"
    }
  ],
  "profiles": [
    {
      "id": "normal",
      "weight": 0.9,
      "calls_per_hour": {"records_by_group": 3000, "records_by_value": 100}
    },
    {
      "id": "campaign",
      "weight": 0.1,
      "calls_per_hour": {"records_by_group": 100, "records_by_value": 3000}
    }
  ],
  "table_write_rates": {
    "public.records": {
      "inserts_per_hour": 1000,
      "updates_per_hour": 3000,
      "deletes_per_hour": 100,
      "source": "manual"
    }
  },
  "constraints": {
    "storage_budget_bytes": 67108864,
    "write_budget_units_per_hour": 10000,
    "max_indexes": 5
  }
}
```

- `queries`: 1–20 записей с уникальными `id`. Это объединение SQL всех профилей, включая разные литералы одного шаблона. Нельзя иметь 20 отдельных SQL на каждый профиль сверх общего лимита.
- `profiles`: 1–3 записи с уникальными `id`. Каждый `calls_per_hour` содержит ровно все query IDs; неизвестный или отсутствующий ключ — ошибка. Частоты конечны и неотрицательны; ноль означает отсутствие запроса в этом профиле. В каждом профиле есть хотя бы одна положительная частота, каждый SQL используется хотя бы одним профилем.
- `weight` — положительное конечное относительное значение; для расчётов `p_s = weight_s / sum(weight)`. Вес нужен для среднего и разрешения равенств, но не ослабляет защиту сценария в максимуме `robust`. Это заданная пользователем относительная длительность/вероятность режима, а не частота SQL.
- `objective`: `robust` по умолчанию либо `mean`. При одном профиле критерии совпадают.
- `storage_budget_bytes` — целое число от нуля, `max_indexes` — целое 0–5. Бюджет места обязателен; отчёт показывает байты и MiB. При нулевом месте или `max_indexes: 0` оценивается baseline и возвращается пустой набор без генерации/поиска.
- `write_budget_units_per_hour` — конечное число от нуля либо явный `null`. При включённом лимите нужны rates для всех таблиц workload. Отсутствие данных не считается нулём.
- Каждая запись rates обязана содержать `inserts_per_hour`, `updates_per_hour`, `deletes_per_hour` — конечные неотрицательные числа. Пропуск поля, отрицательное значение и неизвестная таблица — ошибка. `source` в MVP равен `manual`.
- При выключенном лимите записи профиль можно не передавать либо передать целиком. Неполный переданный профиль отклоняется. Без профиля write units индексов и наборов — `null`, с подписью «нет данных»; при полном профиле они рассчитываются и без ограничения.
- Ключ `table_write_rates` — точная строка `schema.name` физических разрешённых имён, с сохранением регистра. SQL-алиасы, кавычки и `search_path` в ключах не интерпретируются. Если разные таблицы workload дают один ключ из-за точек в именах, переданный профиль отклоняется как неоднозначный с `INVALID_WRITE_PROFILE`.
- Профиль записи один, общий для всех сценариев чтения; пользователь задаёт выбранную им нагрузку записи, при необходимости консервативную. MVP не заявляет оптимизацию разных write-профилей.
- Максимум 1 MiB UTF-8 для входного JSON, 64 KiB UTF-8 для одного SQL и 256 единиц сложности WHERE/JOIN на запрос (сравнение/null-test: 1, IN: каждый элемент, BETWEEN: 2). Размер проверяется до разбора; сложность — при проверке AST. Превышение — `INPUT_LIMIT_EXCEEDED`, исходный SQL не обрезается.
- Все расчёты должны оставаться конечными: нечисловой/отрицательный planner cost и переполнение промежуточных сумм дают явную ошибку, а не улучшение, ноль или успешный отчёт. Нормированные веса обязаны оставаться положительными; если при наличии положительного `B_s` вычислен `B_mean = 0`, запуск завершается численной ошибкой. Потеря положительного веса из-за underflow не считается нулевой вероятностью сценария.

Частоты задаются в пересчёте на час; ждать час для анализа не требуется. Несколько значений параметра можно представить отдельными SQL с литералами. Это не точная симуляция выбора generic/custom plan у prepared statements. `pg_stat_statements` обычно заменяет литералы параметрами и не предоставляет репрезентативные исходные значения для этого режима. [pg_stat_statements](https://www.postgresql.org/docs/16/pgstatstatements.html), [EXPLAIN](https://www.postgresql.org/docs/16/sql-explain.html).

### Поддержанный SQL и каталог

Поддерживается один SELECT на запись workload, обычные таблицы, алиасы, до трёх таблиц, INNER JOIN с равенством колонок, WHERE с AND и сравнениями `=`, `<`, `<=`, `>`, `>=`, а также `column IN (literal, ...)`, `column BETWEEN literal AND literal`, `column IS NULL` и `column IS NOT NULL`. ORDER BY — по одной или двум колонкам с ASC или DESC, LIMIT — числовой. В SELECT допускаются колонки и `*`; литералы могут иметь явное приведение к типу, например timestamp.

Расширение #73 сохраняет формат входа v2. Список IN непустой, содержит до 256 поддержанных скалярных литералов, включая NULL и явные casts; значения не подставляются и не переписываются. Общая сложность WHERE + JOIN остаётся ≤256: обычное сравнение или null-test стоит 1, каждый элемент IN — 1 (повторы тоже считаются), BETWEEN — 2. Границы BETWEEN не сортируются, NULL не заменяется нулём/false. В PostgreSQL IN с несколькими литералами может использовать общий тип массива: типы/неявные casts, `pg_type.typarray` и действительная видимая сигнатура равенства проверяются по каталогу. Обе сигнатуры `>=`/`<=` BETWEEN проверяются отдельно; IS NULL/IS NOT NULL не вызывают оператор сравнения.

JOIN ON остаётся равенством колонок. NOT IN, NOT BETWEEN, явные SYMMETRIC/ASYMMETRIC, ISNULL/NOTNULL, IN с подзапросом/колонками/выражениями и null-test над выражением не входят в этот срез. В признаки генератора передаётся один узел на новую форму: IN и IS NULL — equality-like, BETWEEN и IS NOT NULL — range-like. Это эвристика генерации, а не обещание индексного плана: каждое сочетание оценивается целым исходным EXPLAIN. IN не разворачивается в фиктивные совместные AND-условия. См. [NULL-семантику IN](https://www.postgresql.org/docs/16/functions-comparisons.html) и [выбор общего типа](https://www.postgresql.org/docs/16/typeconv-union-case.html).

CTE, подзапросы, OR, GROUP BY, оконные выражения, вызовы функций, views, partitioned tables, пользовательские типы и операторы, параметры `$1`, DML и несколько statements отклоняются с query ID и причиной. Неподдержанный SQL не исчезает из расчёта молча.

SQL разбирается в AST через JSqlParser. Колонки разрешаются через каталог БД, включая алиасы и неоднозначные имена; регулярные выражения не заменяют AST. Проверка корректности SQL использует все его колонки, даже если генератор позже ограничивает признаки. [JSqlParser](https://github.com/JSQLParser/JSqlParser).

Адаптер читает структуру только относящихся к workload таблиц: колонки и типы, оценку числа строк, существующие индексы и доступность статистики. Число колонок таблицы не ограничивается 16: таблица со 100 колонками поддерживается. Demo seed выполняет ANALYZE. CLI не запускает ANALYZE автоматически на целевой БД; отсутствие статистики даёт предупреждение о качестве оценки.

## 4 Метрики, критерии и бюджеты

### Стоимость по сценариям

`S` — набор новых индексов, `cost(q,S)` — корневой `Plan.Total Cost` из EXPLAIN, `f_s(q)` — частота в профиле `s`. Реальные индексы доступны при любой оценке.

```text
C_s(S) = sum(f_s(q) * cost(q,S))
B_s = C_s(empty)
gain_s(S) = B_s - C_s(S)
gain_percent_s(S) = 100 * gain_s(S) / B_s       # только если B_s > 0

C_mean(S) = sum(p_s * C_s(S))
B_mean = C_mean(empty)
M(S) = C_mean(S) / B_mean                     # если B_mean > 0
R(S) = max(C_s(S) / B_s for s where B_s > 0)
```

`M` — отношение ожидаемой стоимости к её baseline; оно не равно среднему отношений сценариев. `R` — худшая нормированная стоимость среди переданных сценариев, не regret относительно неизвестного оптимума. Все сценарии участвуют в `R` независимо от `weight`.

При `B_s = 0` процент и отношение этого профиля — `null`; абсолютная стоимость сохраняется. Такие профили не входят в максимум, но допустимый набор обязан сохранять для них `C_s(S) = 0`; иначе причина отказа — `ZERO_BASELINE_REGRESSION`. Если все `B_s = 0`, возвращается baseline и пустой набор, `M`/`R` — `null`, поиск не запускается: неотрицательную стоимость уже не уменьшить.

Для детерминированного сравнения конечные `R` и `M` округляются до 9 десятичных знаков с HALF_EVEN; обозначим их `r` и `m`. Отчёт хранит и исходные значения. Сравнение выполняется по округлённым значениям, без нетранзитивного компаратора «разница меньше epsilon».

```text
robust: минимум лексикографического ключа (r, m, bytes, writes?, sorted_ids)
mean:   минимум лексикографического ключа (m, r, bytes, writes?, sorted_ids)
```

`bytes` — сумма размеров с запасом; `writes` участвует в ключе только при полном профиле записи, иначе пропускается для всех наборов. `sorted_ids` — лексикографический список стабильных candidate IDs. Критерий `robust` может пожертвовать средним эффектом ради худшего сценария: в отчёте эта цена должна быть видна.

Метрика называется «снижение взвешенной стоимости планов». Cost — условные единицы PostgreSQL, не миллисекунды; корневой Total Cost уже включает дочерние узлы. Нельзя переводить процент изменения cost в процент реального ускорения. Отдельный запрос может ухудшиться; такие строки выделяются. Ограничения SLA и регрессии каждого запроса не входят в MVP. [Using EXPLAIN](https://www.postgresql.org/docs/16/using-explain.html).

### Место

```text
estimated_bytes(i) = hypopg_relation_size(i)
budgeted_bytes(i) = ceil(1.2 * estimated_bytes(i))
sum(budgeted_bytes(i) for i in S) <= storage_budget_bytes
```

Коэффициент 1.2 сохраняется в отчёте. Показываются исходная оценка и объём с запасом. Это ограничение оценки; фактический размер после построения может отличаться.

### Сопровождение записи

```text
row_changes(t) = inserts_per_hour(t) + updates_per_hour(t) + deletes_per_hour(t)
write_units(i) = row_changes(table(i)) * (number_of_key_columns(i) + number_of_include_columns(i))
sum(write_units(i) for i in S) <= write_budget_units_per_hour  # если лимит включён
```

Единица — «условные единицы сопровождения индексов в час». Например, 4100 изменяемых строк дают 8200 единиц для двухколоночного индекса. Это вспомогательная эвристика, не прогноз WAL, I/O, throughput или замедления INSERT/UPDATE. Все UPDATE учитываются; ширина ключа, HOT, bloat и отложенная очистка DELETE не моделируются. Каждая INCLUDE-колонка также стоит одну единицу на изменение строки; payload не бесплатен. Например, один ключ + две INCLUDE-колонки при 4100 изменениях дают 12300 units/час. При одной таблице модель различает кандидаты по общему числу ключевых и INCLUDE-колонок.

Нулевой write budget допускает только индексы с нулевыми write units. Модель записи и planner cost не складываются в одну сумму с произвольным коэффициентом. При будущем импорте счётчиков нужны разности между наблюдениями и обработка сбросов; текущую долю HOT нельзя переносить на новые индексы. [Статистика PostgreSQL](https://www.postgresql.org/docs/16/monitoring-stats.html), [HOT](https://www.postgresql.org/docs/16/storage-hot.html).

## 5 Ограниченная генерация кандидатов и широкие таблицы

Генератор рассматривает неуникальные B-tree на 1–2 ключевых обычных колонках и до двух дополнительных колонок INCLUDE (#79). Ключи берутся только из WHERE, JOIN и ORDER BY поддержанных SQL. Явная проекция SELECT может дополнить существующий ключевой вариант payload, но сама не создаёт ключи. `SELECT *`, `table.*` и смешанная проекция со звёздочкой не порождают INCLUDE-вариантов. Полный перебор всех колонок схемы запрещён.

### Ограничение признаков до образования пар

Для каждого `(query_id, table)` собираются различные физические колонки условий и сортировки. Нормированная частота `u_s(q) = f_s(q) / sum_q f_s(q)` используется только для отбора кандидатов, не заменяет частоты в целевой функции. Поддержка колонки в сценарии — сумма `u_s(q)` по различным запросам, использующим её в условиях/сортировке.

Оставляем до **16 разных колонок на `(query, table)`**:

1. Сначала колонки ORDER BY этого запроса в исходном порядке (их не более двух).
2. Остальные — по убыванию максимальной поддержки колонки среди сценариев.
3. При равенстве: колонки равенств WHERE/JOIN перед диапазонами, затем стабильный идентификатор `schema/table/column`.

Это ограничение генератора, а не изменение SQL: все исходные условия остаются в EXPLAIN. Если участвовало больше 16 колонок, отчёт содержит `COLUMN_SHORTLIST_TRUNCATED`, query ID, таблицу, обнаруженное и сохранённое число и список исключённых колонок.

### Локальные кандидаты

На оставшихся колонках генерируются:

- Одноколоночные индексы с ASC и стандартным NULLS LAST. PostgreSQL может сканировать B-tree в обратном направлении; все варианты направления одного ключа не перечисляются.
- Двухколоночные варианты на одной таблице из одного запроса: равенство перед диапазоном; равенство перед колонкой сортировки; две колонки равенства в обоих порядках; пара ORDER BY в исходном порядке и направлениях. Для ключей без явной сортировки — ASC; для ключей из ORDER BY — направление запроса и соответствующее стандартное NULLS.
- Повторяющиеся признаки одного столбца предварительно объединяются. Каждая упорядоченная пара разных колонок обходится один раз; для неё создаются только направления, вытекающие из правил, максимум четыре. Нельзя перечислять пары заново для каждого повторного предиката.

После локальной канонизации и удаления точных реальных дублей сохраняется не более **32 кандидатов на `(query, table)`**. Для INCLUDE резервируется до восьми мест; остальные места (не менее 24) занимают обычные кандидаты: сначала все одноколоночные (до 16), затем составные. Неиспользованные INCLUDE-места доступны обычным индексам; более восьми INCLUDE не сохраняются даже при свободных местах. INCLUDE-очередь сортируется так же: число ключей, лучший приоритет пары, ID. Приоритет составных: точная пара ORDER BY, равенство + сортировка, равенство + диапазон, два равенства. Кандидат из нескольких групп получает наивысший приоритет; внутри группы порядок по стабильному ID. При отсечении — `LOCAL_CANDIDATE_LIMIT` с числами и областью.

Точный дубль проверяется только против валидного готового доступного обычного B-tree без predicate и expressions. Должны совпасть ключи, порядок, направления, NULLS, collation, opclass и множество INCLUDE-колонок. Порядок payload канонизируется по имени; payload отличается от ключей. Обычный `(a)`, `(a,b)` и `(a) INCLUDE (b)` — разные определения, ни одно не удаляется как точный дубль другого. Partial index `(a) WHERE ...` не заменяет общий `(a)`; наличие `(a,b)` не даёт основания удалить `(a)`. Существующие индексы других видов не удаляются и остаются доступны планировщику.

### Ограниченные INCLUDE-варианты (#79)

Для каждого уже перечисленного ключевого определения берётся вся явная проекция данной таблицы без ключей, в порядке физических имён. Если она пуста, дополнительный вариант не нужен; если в ней больше двух колонок, вариант не генерируется (`INCLUDE_PAYLOAD_LIMIT`). Подмножества проекции не перебираются. Если ключи и payload не покрывают все ссылки на эту таблицу в исходном SQL (включая условия и сортировку), покрывающий вариант также не предлагается. Проверка использует полный ResolvedQuery, а не обрезанные признаки. Звёздочка в любой части проекции отключает INCLUDE для всего запроса.

Порядок базовых определений детерминирован: одиночные по физическому имени, затем упорядоченные пары имён и направления ASC/DESC. Добавляется не более `min(16, 976 − ordinary_count)` покрывающих определений на область; остальные подходящие варианты отражаются как `INCLUDE_VARIANT_LIMIT`. Поэтому общий предел **976 на область / 58 560 на запуск**, caps **16/32/16**, число SQL и EXPLAIN не растут. Для каждого варианта сохраняются query IDs, исходные причины ключей и `COVERING_PROJECTION`. Локальные счётчики отдельно содержат перечисленные и оставленные INCLUDE; `LOCAL_CANDIDATE_LIMIT` также сообщает `include_before`, `include_after`, `include_limit`.

INCLUDE не добавляет сортировку, collation или opclass payload. Канонизация проверяет существование колонок, отсутствие повторов/пересечения с ключами и принадлежность одной таблице; DDL экранирует каждый идентификатор. ID обычных индексов не меняются; непустой канонический payload расширяет кодируемую структуру перед SHA-256.

Размер и полный cost-вектор получаются обычным путём через HypoPG. Payload влияет на размер и write proxy; он не получает бесплатного бюджета. INCLUDE допускает index-only scan, но не гарантирует выбор такого плана или отсутствие heap fetches: это зависит в том числе от visibility map. Planner cost не является измерением времени. [PostgreSQL 16: index-only scans](https://www.postgresql.org/docs/16/indexes-index-only-scans.html).

### Общий shortlist с учётом сценариев

Варианты с ключом без подходящего default B-tree opclass и без явно заданного opclass
исключаются до канонизации с `NO_BTREE_OPERATOR_CLASS` и warning, а не превращают корректный
каталог в `CATALOG_ERROR`. Это относится и к `json IS NULL` / `IS NOT NULL`: исходный SQL
остаётся целым, индексируемые колонки продолжают участвовать в генерации/поиске. Сохраняется
фактическое число исключённых перечисленных вариантов; им не назначаются ID/DDL/size/cost.

Локальные списки объединяются по канонической структуре с объединением породивших query IDs. Для каждого сценария рейтинг кандидата — сумма `u_s(q)` по различным породившим его запросам. У каждого сценария две очереди: с одним и с двумя ключами, включая INCLUDE-варианты соответствующей арности. Payload не считается дополнительным ключом. Обе сортируются по убыванию рейтинга; для пар при равенстве используется приоритет группы из локальной генерации (лучший из породивших запросов), затем стабильный ID; для одиночных при равенстве — ID.

Начальные **до 16 кандидатов** выбираются внешним round-robin по profile ID. Каждый сценарий за ход добавляет первый ещё не выбранный кандидат с положительным рейтингом из своей текущей очереди, пропуская уже выбранные. Внутри сценария очереди чередуются после каждого успешного выбора, начиная с одноколоночной; если нужная очередь исчерпана, используется другая. Первые 16 образуют начальный shortlist. Затем обход продолжается с сохранёнными позициями очередей до ещё **48 резервных кандидатов** либо исчерпания всех списков; всего хранится до 64 различных кандидатов. Поэтому равные рейтинги одного широкого запроса не отдают все места одиночным индексам. `weight` не используется для распределения. Это уменьшает риск подавления редкого режима абсолютным объёмом другого, но не гарантирует покрытие каждого SQL или качество каждого сценария. Кандидаты вне ограниченной очереди из 64 получают `GLOBAL_CANDIDATE_LIMIT`; попадание в резерв само по себе не означает отказ.

Подготовка проходит начальный shortlist и затем резерв в том же порядке, пока не накопит **16 индивидуально допустимых кандидатов** либо не достигнет ограничений. Дедупликация, представительство профилей и чередование одиночных/пар сохраняются; SQL и локальная генерация не расширяются. После бюджетного отказа или локальной ошибки гипотезы берётся следующий кандидат. Отсев по доступному write budget выполняется общим модулем метрик **до запроса размера**; неизвестный размер при этом остаётся `null`, а не подменяется нулём. После успешного размера допустимость проверяется общим расчётом бюджетов, включая `ceil(1.2 × estimated_bytes)`.

На всю подготовку разрешено не более **32 вызовов `estimateSize`**, включая неуспешные. Пределы подготовки — 16/48/32; она использует общий эффективный deadline команды/поиска без нового отсчёта. Уже измеренный кандидат повторно не измеряется. Размеры и write units непроверенного остатка неизвестны. Кандидатная `HYPOTHETICAL_INDEX_ERROR` допускает продолжение только после успешной очистки сессии и отражается отдельно от бюджетного отказа. Потеря сессии, deadline и отмена прекращают подготовку: полный baseline позволяет сохранить `partial` без нового EXPLAIN; численная ошибка остаётся `failed`.

Остановка подготовки различает `SHORTLIST_FULL`, `RESERVE_EXHAUSTED`, `SIZE_LIMIT`, `DEADLINE_EXCEEDED`, `CANCELLED`, `CONNECTION_LOST` и `FAILED`. Исчерпание резервной очереди или лимита размеров не запускает новую генерацию. `SIZE_LIMIT` сопровождается warning; поиск выполняется на уже подготовленных кандидатах и может завершиться `completed`, как при других candidate caps. Эти пределы ограничивают затраты и не гарантируют улучшение качества.

Для последующей серии бюджетов предусмотрен общий путь подготовки: один финальный пул до 16 кандидатов готовится с refill при наибольшем бюджете серии. Отдельные точки фильтруют этот фиксированный пул по своим бюджетам в памяти; независимые запросы размеров, refill и изменение исходного пула запрещены. Этот стык не означает наличия пакетной CLI-команды #75.

ID определяется канонической структурой `schema, table, method, ordered keys, directions, nulls, collation, opclass, sorted included columns`; имя `ib_<hash>` стабильно, идентификаторы экранируются средствами драйвера. Для финальных кандидатов сохраняются DDL, происхождение, размер, write units и состояния рассмотрения. Структурные ограничения порядка ключей и сортировки описаны в [Multicolumn indexes](https://www.postgresql.org/docs/16/indexes-multicolumn.html), [Indexes and ORDER BY](https://www.postgresql.org/docs/16/indexes-ordering.html).

### Границы работы и диагностика

До 20 запросов × 3 таблицы дают не более 60 локальных областей. После ограничения колонок локальная генерация рассматривает не более `16 + 4 * 16 * 15 = 976` определений на область, то есть до **58 560 событий генерации** всего. Обрабатывается одна область за раз; после shortlist в общем пуле не более **1920 локальных записей** до дедупликации. Лимиты проверяются до создания больших списков; deadline действует и на AST/генерацию. Эти границы не включают внутреннюю работу планировщика PostgreSQL.

Для каждой области сохраняются число обнаруженных/оставленных колонок, фактически перечисленных/дедуплицированных/оставленных определений. Для общего пула — число до/после дедупликации, начальный shortlist, размер резерва, проверенные кандидаты, size-вызовы, бюджетные отказы, кандидатные ошибки, допустимые пополнения из резерва, итоговый размер shortlist и причина остановки подготовки. В отчёте сохраняется вся ограниченная очередь, включая нерассмотренный остаток; она не означает, что поиск получил больше 16 кандидатов. Условное «полное число всех возможных индексов» не вычисляется: для неперечисленной части оно `null`. Формулировка — «часть пространства не генерировалась», а не «все остальные бесполезны».

Таблица со 100 колонками и фильтрами по двум не вызывает перебора 100 колонок. Если запрос использует все 100 в условиях, применяются ограничения с предупреждениями. Даже 100 одиночных и 100 × 99 упорядоченных двухколоночных определений дали бы 10 000 кандидатов без дополнительных направлений. После shortlist из 16 полный перебор наборов размера 0–5 всё ещё равен 6885; он не используется в рабочем анализе.

## 6 Оценка наборов через HypoPG

Один запуск владеет одним физическим PostgreSQL connection. HypoPG хранит гипотетические индексы в backend session и использует их для EXPLAIN без ANALYZE. Оценка размера — `hypopg_relation_size`. [HypoPG usage](https://hypopg.readthedocs.io/en/rel1_stable/usage.html).

Контракт `evaluate(S)`:

1. Очистить предыдущие гипотезы через `hypopg_reset()`.
2. Создать ровно индексы набора `S` через `hypopg_create_index()`.
3. Для каждого query ID общего workload выполнить `EXPLAIN (FORMAT JSON)` и прочитать корневой Total Cost; запросы идут в порядке query ID.
4. Вернуть `cost_by_query_id` и планы только после успеха всех SQL. Отдельные профили не вызывают повторного EXPLAIN: метрики считаются над этим вектором в памяти.
5. В `finally` очистить гипотезы; после сбоя транзакции сначала rollback. Закрытие соединения завершает сессию.

Baseline оценивает пустой набор гипотез. Все оценки используют одну БД и одинаковые настройки планировщика; `enable_seqscan=off` ради красивого эффекта не включается. Изменение схемы/данных/статистики во время анализа может менять результаты: воспроизводимое демо выполняется без параллельных изменений и с сохранённым seed/ANALYZE. Одна сессия не обещает неизменность внешней БД.

Кэш живёт только внутри запуска; ключ — отсортированные candidate IDs, значение — полный вектор стоимости. Baseline и планы текущих лучших `robust`/`mean` наборов сохраняются при оценке; промежуточные планы остальных наборов можно освобождать. Финальный экспорт не запускает EXPLAIN заново. Ошибочные наборы помечаются отдельно и не повторяются в этом запуске.

Нельзя суммировать одиночные выигрыши и выдавать их за эффект комбинации: каждый рассмотренный набор оценивается целиком. [Combining indexes](https://www.postgresql.org/docs/16/indexes-bitmap-scans.html).

Extension устанавливается при подготовке контейнера. Runtime role получает доступ на чтение demo schema и функции HypoPG. Анализ не создаёт реальные индексы и не исполняет пользовательский SQL через ANALYZE. Фактические измерения — отдельный явно запускаемый эксперимент на тестовой БД.

## 7 Алгоритм поиска

Поиск отделён от evaluator и критерия сравнения. MVP не гарантирует глобальный оптимум; возвращает лучший полностью оценённый допустимый набор для выбранного `objective`. При любом успешном `evaluate` обновляются оба лучших набора (`robust` и `mean`) среди общего пула исследованных конфигураций, включая baseline и одиночные индексы.

### Жадный этап

1. Полностью оценить baseline. Если поиск не нужен из-за нулевого места, `max_indexes` или всех нулевых baseline costs, завершить с пустым набором.
2. Сгенерировать начальный shortlist и ограниченный резерв; подготовить до 16 индивидуально допустимых кандидатов по правилам §5 с размерами/write units и причинами отказов. Поиск получает только подготовленный финальный shortlist.
3. Начать цепочку с `S = empty`. Для каждого допустимого добавления `i` полностью оценить `S + i`, включая нулевую/отрицательную одиночную пользу.
4. Для движения по цепочке пригодны только добавления, лексикографически улучшающие первые два компонента критерия: `(r,m)` для `robust`, `(m,r)` для `mean`. Равный худший результат и лучшее среднее — разрешённое продвижение; меньшие bytes сами по себе не являются пользой добавления.
5. Из пригодных добавлений выбрать результат с минимальным полным ключом выбранного objective из раздела 4. Место и запись определяют допустимость и разрешают равенства; в v0.2 старый скалярный score «выигрыш / доля бюджета» не используется. Так критерий выбора шага совпадает с критерием итогового результата.
6. Добавить выбранный индекс и повторять до отсутствия положительного допустимого добавления или достижения `max_indexes`. Кандидат с нулевой одиночной пользой не объявляется глобально бесполезным: он остаётся доступен repair-этапу.

### Один ограниченный проход пересмотра

После greedy фиксируется `S0` — лучший допустимый набор для выбранного критерия среди всех уже полных оценок. До **28 новых попыток оценки наборов** используются для одного прохода по соседям этого фиксированного набора; очередь не перестраивается рекурсивно после улучшения.

Три очереди:

1. `0→2`: `S0 + {j,k}` при наличии двух свободных слотов; в том числе пары из пустого набора.
2. `1→1`: `(S0 - {i}) + {j}`.
3. `1→2`: `(S0 - {i}) + {j,k}`.

`i` берётся из `S0`, `j,k` — разные кандидаты финального shortlist вне `S0`. Проверяются max_indexes, бюджеты и известные ошибки. Объединённый список имеет не более `120 + 55 + 275 = 450` структур до фильтрации — это консервативная граница для 16 кандидатов и 5 выбранных. Полные наборы дедуплицируются.

Порядок детерминирован: для `robust` выбирается худший положительный-baseline профиль `S0` (при равенстве — profile ID), для `mean` используется ожидаемая стоимость. Входящие кандидаты ранжируются по убыванию известной одиночной пользы на этой метрике, затем по размеру и ID. Кандидаты без успешной одиночной оценки идут после известных, в порядке ID; нулевая польза не исключает кандидата. Для пары используется лексикографическая пара рангов её членов, для замен последним ключом — ID удаляемого индекса. Эти ранги задают только порядок проверки, не оценку эффекта сочетания.

Очереди обходятся round-robin в порядке `0→2`, `1→1`, `1→2`, пропуская пустые. Кэшированные оценки переиспользуются без расхода слота; ранее ошибочные конфигурации пропускаются. Неудачный новый вызов `evaluate` расходует один из 28 слотов. После каждого полного результата обновляются incumbents. Лучший итог не обязан совпадать с последним звеном greedy или первым улучшением repair.

Один проход не гарантирует нахождение всех полезных пар, выхода из любого локального решения или покрытия всего соседства. Он должен исправлять предусмотренную фикстурами бюджетную ловушку, где замена одного индекса парой даёт лучший допустимый результат.

### Лимиты, ошибки и статусы

Общий лимит — **2000 попыток EXPLAIN**, включая неуспешные, baseline и все этапы; кэш не расходует EXPLAIN. При `Q≤20`, `N≤16`, `K≤5` greedy делает не более `Q * (1 + 16 + 15 + 14 + 13 + 12) = 1420` вызовов. Repair добавляет не более `28 * Q = 560`; нормальная верхняя оценка — **1980**, оставшиеся 20 не используются как обещание дополнительного поиска. Профили не умножают число вызовов. Переоценка финальных планов не нужна.

До 60 секунд на поиск вместе с baseline, генерацией и подготовкой кандидатов; до 90 секунд на весь анализ с начала команды, включая валидацию и introspection. До baseline фиксируется `search_started_at`; для baseline/candidates/greedy/repair действует `effective_deadline = min(command_started_at + 90s, search_started_at + 60s)`. Подготовка до baseline использует общий deadline. Часы монотонные; оставшееся время проверяется перед каждой операцией.

Effective deadline передаётся всем CPU-проходам и операциям адаптера соответствующей стадии. Один EXPLAIN — не дольше меньшего из двух секунд и оставшегося времени. Другие SQL получают statement_timeout по оставшемуся времени; подключение — не более пяти секунд и оставшегося времени. Deadline проверяется до/после вызова парсера и между проходами AST/генерации; принудительное прерывание внутри стороннего парсера не обещается, а превышение обнаруживается при его возврате. По окончании незавершённый SQL отменяется, соединение очищается или закрывается. Ограничения — бюджет анализа, а не обещание точной длительности при задержке стороннего вызова, отказе сети/драйвера или записи отчёта. Экспорт результата использует оставшееся общее время, если оно есть; минимальный partial сохраняется и при исчерпании бюджета поиска.

Кооперативная отмена обозначается `CANCELLED`: новый SQL не запускается, активная операция отменяется и сессия закрывается. При полном baseline и пригодном сохранённом результате возвращается partial, иначе failed. Обработчик SIGINT инициирует отмену и освобождение сессии; сохранение отчёта при завершении JVM не гарантируется.

- `completed`: предусмотренный ограниченный поиск завершён; candidate caps сами по себе не превращают статус в partial, но всегда дают warnings.
- `partial`: есть полный baseline и пригодный результат, но выполнению мешал временной/EXPLAIN/repair лимит, потеря соединения, кооперативная отмена или неполные/ошибочные оценки. При достижении 28 новых repair-попыток и оставшихся непроверенных допустимых соседях — `partial`, причина `REPAIR_LIMIT`. В отчёте видны завершённые этапы.
- `failed`: нет полного baseline либо вход/каталог/численные расчёты не позволяют получить корректный сравнимый результат.

Ошибка создания конкретного кандидата исключает его из дальнейшего поиска с причиной, анализ остальных продолжается; кандидатная ошибка даёт warning. В данных отчёта остаётся полная запись отклонённого кандидата: определение, DDL, происхождение и причина отказа; не полученные оценки остаются `null`. Ошибка EXPLAIN обесценивает весь рассматриваемый набор: запрещено подменять его нулевым cost или суммой по оставшимся SQL. Потеря соединения и общий deadline не маскируются под ошибку отдельного кандидата. Неполный набор не участвует в incumbents.

## 8 Архитектура, CLI и отчёты

Стек: Kotlin/JVM на JDK 25 LTS (уточнено 10 ноября 2026 при создании каркаса), Spring Boot в режиме CLI (`WebApplicationType.NONE`), PostgreSQL JDBC, Gradle Kotlin DSL. Сериализация JSON — Jackson. PostgreSQL 16 с HypoPG и demo seed поднимается через Docker Compose. React, HTTP API, worker-сервер и polling не требуются.

Контракт команды: `indexbudget analyze --workload <path> --output-dir <path>`. Настройки подключения берутся из окружения; DSN и пароли не попадают в отчёт, SQL и логи. Примеры входа хранятся в репозитории. Каждая команда выполняет один анализ и использует одну выделенную JDBC-сессию.

```text
CLI/JSON → CatalogSnapshot + AST → ResolvedWorkload → ограниченные кандидаты
        → Search(objective, budgets) ↔ HypoPG evaluator → cost_by_query_id
        → расчёты профилей/выбор → AnalysisReport → HTML / JSON / SQL
```

Модули обмениваются `WorkloadInput`, `Profile`, `CatalogSnapshot`, `ResolvedWorkload`, `IndexCandidate`, `EvaluationResult`, `SearchResult`, `AnalysisReport` и общим `RunContext` с deadline/счётчиками. `EvaluationResult` содержит стоимость по каждому query ID; средние и сценарные метрики вычисляются модулем расчётов, не адаптером БД. Search использует единый компаратор и не содержит второй независимой реализации формул.

Стадии в stderr: validation, introspection, baseline, candidates, greedy, repair, report. Показываются число EXPLAIN, полных наборов и попаданий в кэш, без выдуманного процента прогресса. Ошибка содержит `code`, `message`, при необходимости `query_id`, `profile_id`, `details`. Сохранённые ошибки результата `partial` также выводятся в stderr, каждая отдельной строкой `CODE: JSON`; после успешного сохранения такого результата код выхода остаётся 3.

Коды выхода: `0` — completed, `2` — невалидный/неподдержанный вход, `3` — partial с сохранённым результатом, `1` — прочий failed или ошибка записи артефактов. При failed успешный `indexes.sql` не создаётся. Вывод сначала записывается во временные файлы с run ID; на ошибке нельзя оставлять смесь старого SQL и нового отчёта. Непустой output-dir на начальной валидации отклоняется с `OUTPUT_DIRECTORY_NOT_EMPTY` и кодом 2. Если повторная проверка каталога на стадии экспорта обнаруживает появившиеся файлы, это ошибка публикации `EXPORT_FAILED` с кодом 1; существующие файлы сохраняются. Для каждого запуска пользователь задаёт отдельный каталог.

`report.json` имеет `schema_version: 3`, `spec_version: "0.2"`, run ID, hash входа, версии окружения, длительность, objective, нормированные веса, budgets, write profile, baseline, выбранный набор и costs/plans по SQL, метрики каждого профиля, обе оценки объёма, warnings и статистику отсечений/поиска. Hash — SHA-256 от UTF-8 JSON с рекурсивной сортировкой ключей, без пробелов, с сохранением строк SQL и порядка массивов. Нормализация для hash не подменяет исходные SQL.

Диагностика подготовки #70 добавляет поля к выходному JSON v3 без изменения смысла прежних полей. `shortlisted_candidates` по-прежнему означает число первоначально отобранных кандидатов и равен новому `initial_shortlisted_candidates`; итог подготовки хранится только в новом `preparation.final_shortlisted_candidates`. У прежнего отчёта без новых полей сведения о refill неизвестны.

Имена и вложенность полей выходного JSON v3, единицы измерения и nullable-значения зафиксированы в [контракте отчёта v3](docs/report-v3.md). `selected_objective` задаёт критерий запуска; `incumbents_coincide` явно отмечает совпадение наборов. Сохранённые планы представлены JSON-значениями, неизвестные версии БД и неисследованные количества — `null`.

Расширение #79 версионирует выходной отчёт как **v3**: `definition.included_columns` — обязательный массив физических колонок (пустой для обычного индекса), `write_proxy_model: "row_changes_times_key_and_include_columns"` явно задаёт модель записи. Старый reader отчётов v2 должен отклонить v3 либо обновиться с поддержкой payload; игнорировать INCLUDE и воспроизводить только keys нельзя. Вход workload остаётся **v2**, параметры CLI не меняются. HTML и SQL используют те же определения и выбранные IDs, что JSON.

Сохраняются `best_robust` и `best_mean` из **одного общего пула полностью оценённых наборов**, `comparison_scope: "evaluated_sets"` и `selected_objective`. Это не два независимо завершённых поиска и не глобально лучшие решения. В HTML явно указывается, какой критерий управлял исследованием пула. Если наборы совпали, отчёт так и сообщает. Сравнение содержит среднюю/худшую стоимость, эффекты всех профилей, место и write units; цена устойчивости — `C_mean(best_robust) - C_mean(best_mean)` среди этого пула.

Причины различаются: точный дубль, отсечение колонок/локального/общего shortlist, превышение бюджета, ошибка гипотезы, отсутствие предельной пользы на конкретном шаге, не выбран поиском, не проверен из-за лимита. Слово «бесполезный» не используется как глобальный вывод. Кандидаты, не дошедшие до HypoPG, не получают вымышленных размеров и cost.

`report.html` — автономный файл без внешних CDN: сводка решения, сравнение профилей и двух incumbents, per-query таблица с регрессиями, бюджеты, индексы, ограничения модели и поиска. SQL/идентификаторы экранируются как текст HTML. `indexes.sql` содержит только выбранный набор с полностью квалифицированными таблицами и стабильными именами; другие рассмотренные индексы туда не попадают. В шапке SQL — run ID и hash входа. Автоматического выполнения нет.

## 9 Демо и проверка гипотез

Все реальные измерения выполняются отдельно от команды анализа на воспроизводимой тестовой БД. Оценка planner cost, фактическое время, фактический размер и write units показываются раздельно.

1. **Сценарный критерий:** один список SQL, одинаковые кандидаты и бюджеты, два разных профиля частот. Сравнить `mean` и `robust` при одинаковой стратегии и лимитах поиска; показать среднее и худшее отношение к baseline. Дополнительные заранее зафиксированные профили частот не используются для настройки выбора, а служат проверкой чувствительности.
2. **Поиск:** при одном фиксированном objective сравнить greedy и greedy+repair. Показать качество, время, число EXPLAIN и расхождение с эталоном. Нельзя приписывать эффект одновременно изменённых objective и стратегии только новой эвристике.
3. **Малый эталон:** для до восьми кандидатов и максимум пяти выбранных полный перебор в отдельном проверочном инструменте рассматривает до 219 наборов (657 EXPLAIN для трёх SQL). Это оптимум только в фиксированном пространстве кандидатов по модели. Инструмент не входит в рабочую команду и не наследует её 90-секундное обещание; имеет собственный явно заданный предел времени.
4. **Фактическая проверка:** построить выбранные финальные наборы на отдельной demo DB, измерить размеры и времена запросов с повторениями и одинаковыми условиями; зафиксировать прогрев, порядок прогонов, число повторений и разброс. При демонстрации влияния записи — отдельный write benchmark с восстановлением одинакового состояния между вариантами.
5. **Бюджетные профили:** изменение ненулевых бюджетов должно менять допустимость и на подготовленном примере рекомендацию. Для демонстрации модели записи полного MVP использовать две таблицы с разными частотами изменений; одностабличный PoC остаётся допустим.

Успех сценарного эксперимента — обнаруженный и объяснённый компромисс на реальных оценках/измерениях, а не заранее назначенный процент выигрыша. Если наборы совпали или ремонт не помог, это фиксируется. Синтетические evaluator-фикстуры проверяют алгоритм, но не заменяют PostgreSQL и не доказывают рыночное преимущество. Идея нескольких сценариев имеет исследовательские предшественники: [Robust Index Selection](https://link.springer.com/article/10.1007/s42979-022-01473-7), [Index Selection Evaluation](https://github.com/hyrise/index_selection_evaluation).

## 10 Обязательные проверки

- Валидация query/profile IDs, нулевых частот, весов, лимитов входа, неизвестных SQL-конструкций, отсутствующих/отрицательных/нечисловых write rates, отключённого/нулевого write budget и v1 input.
- Метрики: разные baseline profiles; различие `sum(p*C)/sum(p*B)` и `sum(p*C/B)`; нулевой baseline; конечность чисел; один профиль; plateau по `R` с улучшением `M`; детерминированные равенства.
- Поиск: взаимодействие индексов без сложения одиночных выгод; бюджетная ловушка 1→2; 0→2 из пустого набора; сохранение лучшего полного результата при ошибке/timeout; оба incumbents из одного пула; cache hit; repair cap и точные счётчики.
- HypoPG: изоляция сессии, создание ровно набора, cleanup после успеха/ошибки, rollback, cancellation, повторный запуск, реальные существующие индексы в baseline.
- Широкая таблица: 100 колонок, `SELECT *`, условия/сортировка на двух — остальные 98 не порождают кандидатов. Добавление неиспользуемых колонок не меняет генерируемые структуры, хотя costs из-за ширины строки могут измениться.
- Широкий workload: запрос со 100 колонками условий остаётся целым в EXPLAIN; ограничения 16/32/16 срабатывают до раздувания списков и сопровождаются диагностикой. До 1920 локальных записей, до 58 560 событий генерации, до 2000 EXPLAIN.
- Сценарный shortlist: профиль с малым абсолютным трафиком и собственными кандидатами участвует в round-robin; результаты детерминированы при одинаковом входе/каталоге. Отсечения не маскируются под полный поиск.
- При одном широком запросе и равных рейтингах, если в пуле есть не менее восьми разных одиночных и восьми разных составных кандидатов, начальный shortlist содержит по восемь каждого вида; пары не вытесняются только из-за числа ключей. После бюджетного отсева соотношение финального shortlist зависит от допустимости.
- Пополнение shortlist: большая часть начальных 16 нарушает бюджет, резерв содержит допустимые варианты; проверяются итоговый пул и выбранные наборы, число size/EXPLAIN вызовов, редкий профиль, равные рейтинги, детерминизм, ошибки размера, исчерпание резерва/32 size-вызовов/deadline и сохранение неизвестных оценок. Отдельные точки фиксированного пула не выполняют refill; улучшение качества не является обязательным результатом.
- Артефакты: JSON/HTML/SQL согласованы по run ID, hash и выбранным индексам; отсутствуют секреты; HTML безопасно отображает SQL; ошибка экспорта не выглядит как успешный запуск.

## Дополнение плана #64: сбор исходной статистики

Отдельные команды `stats snapshot` и `stats pair` сохраняют read-only снимки доступной
pg_stat_statements текущей PostgreSQL 16 БД до top-N/ранжирования. Это не команда анализа
и не автоматическое преобразование нормализованных SQL в исполняемый workload.
Версионированный формат snapshot v1, составная идентичность источника/записи, ресурсные
пределы, неполнота и область чтения зафиксированы в
[контракте снимков](docs/statistics-snapshots.md). Каждое чтение имеет собственный deadline;
ожидание между снимками не использует соединение и бюджет поиска индексов. Подготовка
расширения и изменение настроек БД остаются явными административными действиями.
