# IndexBudget

Подбор дополнительных индексов PostgreSQL для нескольких сценариев нагрузки под заданные бюджеты.

Репозиторий содержит CLI с валидацией JSON v2 и orchestration запуска: общий RunContext, стадии, владение сессией и сохранение пригодного результата при остановке. Есть AST-валидация и разрешение имён SQL, чтение JDBC-каталога и полный ограниченный генератор кандидатов: канонизация, удаление точных реальных дублей, до 32 локальных и до 16 общих через сценарный round-robin. Реализованы общие метрики/компаратор и жадный поиск с ограниченным repair, двумя incumbents и кэшем одного запуска. Выделенная JDBC-сессия HypoPG получает каталог, размеры и полные оценки наборов. Добавлены сборка отчёта v2 и согласованный экспорт JSON/SQL с вызовом HTML-renderer. Генератор, метрики, поиск и фабрика сессии зарегистрированы в CLI; HTML-renderer (#20) ещё не подключён к рабочей команде. Orchestration, поиск и экспорт проверяются с подставными компонентами. Требования к MVP описаны в [спецификации v0.2](IndexBudget-spec-v0.2.md).

Порядок работы для агентов — в [AGENTS.md](AGENTS.md). В [ai/](ai/README.md) описаны целевая архитектура, контракты, соглашения разработки и [ревью PR без запуска тестов](ai/review.md).

## Требования и сборка

- JDK **25 LTS** (например, Eclipse Temurin), доступный через `JAVA_HOME` или `PATH`.
- Gradle устанавливать не нужно: в репозитории есть Wrapper **9.7.0** с проверкой SHA-256 дистрибутива.
- При первой сборке нужен доступ к Maven Central, Gradle Plugin Portal и дистрибутиву Gradle.
- Для сборки, тестов и `--help` база данных и Docker не нужны.

```sh
java -version
./gradlew build installDist
build/install/indexbudget/bin/indexbudget --help
build/install/indexbudget/bin/indexbudget --version
```

На Windows используйте `gradlew.bat` и `build\install\indexbudget\bin\indexbudget.bat`.
Для запуска из IDE выберите JDK 25 как Project SDK и Gradle JVM, импортируйте проект через Gradle и запускайте `IndexBudgetApplicationKt`.

Версии закреплены: Kotlin **2.4.21**, Spring Boot **4.1.2**, Gradle **9.7.0**. Spring Boot работает с `WebApplicationType.NONE`: HTTP-сервер не запускается. Jackson 3 и PostgreSQL JDBC управляются BOM Spring Boot; доменные контракты не зависят от этих библиотек.

## CLI

После `installDist` можно добавить `build/install/indexbudget/bin` в `PATH` и использовать имя `indexbudget`.

```sh
build/install/indexbudget/bin/indexbudget analyze \
  --workload demo/workload-poc.json \
  --output-dir reports/run-001
```

В [demo/workload-poc.json](demo/workload-poc.json) — три SQL, два профиля частот, ручной профиль записи и оба бюджета. **После успешной валидации команда пока возвращает код 1 и `NOT_IMPLEMENTED`.** Диагностика перечисляет отсутствующие компоненты в `details.missing_components`. Команда не открывает БД и не создаёт каталог или отчёты. Spring собирает `AnalysisPipeline`, когда доступны все его зависимости; до этого используется `UnavailableAnalysisRunner`. Фикстуры не используются как результат реального анализа.

До подключения к БД проверяются:

- JSON v2 в UTF-8 размером до 1 MiB; SQL до 64 KiB UTF-8 каждый, без обрезания. Неизвестные поля, повторяющиеся ключи, неверные типы и лишнее содержимое после JSON отклоняются. Строки не преобразуются в числа, дроби — в целые, значения enum регистрозависимы.
- 1–20 SQL и 1–3 профиля с уникальными непустыми IDs. `calls_per_hour` содержит ровно все query IDs; частоты конечны и неотрицательны, в каждом профиле и для каждого SQL есть положительное использование.
- Положительные конечные веса и возможность их нормирования без переполнения суммы или потери положительного веса. Исходные относительные веса сохраняются.
- `objective`: `robust` по умолчанию либо `mean`; целый неотрицательный `storage_budget_bytes`, целый `max_indexes` от 0 до 5 (по умолчанию 5). `write_budget_units_per_hour` обязателен: неотрицательное конечное число, включая 0, либо явный `null` для отключения лимита.
- При включённом write budget требуется `table_write_rates`. Каждая переданная запись содержит все три неотрицательных конечных rate; `source` может быть только `manual`, при отсутствии используется это значение. При выключенном лимите профиль можно не передавать. `ResolvedWorkloadValidator` после SQL resolution проверяет точное покрытие всех физических workload-таблиц; неполный или лишний переданный профиль отклоняется и при выключенном лимите. Ключи — точные `schema.name` с сохранением регистра, без интерпретации SQL-алиасов и кавычек.
- `output-dir` должен быть новым или пустым каталогом. Непустой каталог при начальной валидации отклоняется с `OUTPUT_DIRECTORY_NOT_EMPTY` (exit 2); существующие файлы сохраняются. Неоднозначный путь с `..` после ещё не созданного каталога отклоняется с `INVALID_INPUT`. Экспорт повторяет проверку перед публикацией; отказ этой повторной проверки обрабатывается как `EXPORT_FAILED` (exit 1).

В [examples/](examples/) есть варианты с двумя SQL для `robust` и `mean`, включая выключенную модель записи. SQL-анализатор проверяет поддержанный AST и лимит 256 сравнений WHERE/JOIN, разрешает имена через CatalogSnapshot и передаёт полный ResolvedWorkload генератору (#8/#9). DSN PostgreSQL-адаптера задаётся через `INDEXBUDGET_DATABASE_URL`; `.env.example` служит шаблоном, автоматическое чтение `.env` не реализовано.

В stderr выводятся стадии `validation/introspection/baseline/candidates/greedy/repair/report` и реальные счётчики EXPLAIN, полных оценок и cache hits по мере выполнения; процент готовности не вычисляется. Каждая ошибка — отдельная строка `CODE: {"code":"CODE","message":"..."}` с необязательными `query_id`, `profile_id` и `details`; для ошибок полей `details.field` указывает место во входе. Это относится и к сохранённым ошибкам partial: они выводятся в stderr, а итоговый код остаётся 3 после успешного экспорта. Управляющие символы экранируются, исходный SQL, пути с секретами и сообщения JSON-парсера не выводятся. Например, вход `{"schema_version":1}` даёт exit code 2:

```text
UNSUPPORTED_SCHEMA_VERSION: {"code":"UNSUPPORTED_SCHEMA_VERSION","message":"Expected schema_version: 2. Migrate v1 frequencies from queries to profiles.calls_per_hour.","details":{"field":"schema_version"}}
```

Коды выхода MVP: `0` — completed/help/version, `2` — невалидный или неподдержанный вход, `3` — partial с сохранённым результатом, `1` — failed. CLI переводит результат подключённого pipeline в эти коды; в текущей сборке доступны help/version, валидация и явный отказ из-за отсутствующих компонентов анализа. Ошибки полей дают `INVALID_INPUT` или `INVALID_WRITE_PROFILE` с кодом 2; переполнение суммы весов и потеря положительного числа при представлении или нормировании дают `NUMERIC_ERROR` с кодом 1. Ошибка доступа к output-dir даёт `EXPORT_FAILED` с кодом 1.

## Структура и параллельная работа

Один Gradle-проект с пакетами `ru.itmo.indexbudget`:

| Пакет | Назначение |
| --- | --- |
| `cli` | Аргументы, сообщения и коды выхода |
| `application` | Входной JSON, проверка разрешённого write profile, orchestration и владение ресурсами |
| `domain` | Модели v2, общие метрики, бюджеты и компаратор, результаты, лимиты и ошибки без Spring/JDBC/AST |
| `sql` | AST-валидация и разрешение имён через CatalogSnapshot; полный ResolvedWorkload для генератора |
| `candidates` | Ограниченный перечислитель, канонизация/точные дубли, сценарный shortlist 16/32/16 и общий DDL |
| `optimizer` | Greedy, ограниченный repair, кэш, два incumbents и причины partial; интерфейс оценки конфигураций |
| `postgres` | JDBC-каталог, выделенная сессия HypoPG, размеры и evaluator |
| `report` | Общая модель отчёта v2, JSON/SQL, атомарная публикация и интерфейс HTML-рендеринга |

[Контракты и владение ресурсами](docs/contracts.md) описывают стыки для пяти участников. Общие фикстуры лежат в `src/testFixtures/kotlin`, тесты — в `src/test/kotlin`. Оценки и планы в фикстурах синтетические и не подтверждают качество оптимизации.

## Поиск greedy + repair (#17, #18)

`LimitedRepairOptimizer` зарегистрирован в Spring и использует готовый полный baseline, shortlist с известными размерами, единые метрики и компаратор. Жадный этап оценивает каждый допустимый набор целиком и обновляет `bestRobust` и `bestMean` из одного исследованного пула. Выбранный objective определяет продвижение цепочки; отсутствие одиночной пользы не исключает кандидата из repair.

После greedy фиксируется лучший для выбранного objective набор `S0`. Repair один раз обходит очереди `0→2`, `1→1`, `1→2` в порядке round-robin и не перестраивает соседство после улучшений. Ранги входящих кандидатов используют известную одиночную пользу, размер и ID; для robust польза берётся на худшем positive-baseline профиле `S0`. Бюджеты и `max_indexes` проверяются до evaluator, эффект сочетания не складывается из одиночных эффектов.

Кэш внутри запуска хранит полные costs/plans по отсортированным candidate IDs. Cache hit не расходует EXPLAIN или repair slots; ошибочные наборы повторно не оцениваются. Максимум 28 новых repair-попыток включает неудачные. При 16 кандидатах, `max_indexes = 5` и 20 SQL нормальная верхняя граница вместе с baseline — 99 оценок / 1980 EXPLAIN; дополнительные профили её не увеличивают. Действуют общие лимиты 2000 EXPLAIN, 60 секунд с начала baseline и 90 секунд с начала команды.

Неполный или ошибочный вектор не обновляет incumbents. Локальная ошибка гипотезы исключает кандидата с warning; ошибка EXPLAIN сохраняется отдельно и допускает дальнейший поиск с итоговым `partial`. Потеря соединения, отмена и общие лимиты останавливают поиск с сохранением обоих полных результатов. Если после 28 попыток остались допустимые непроверенные соседи, результат — `partial/REPAIR_LIMIT`; если предусмотренный проход завершён, результат — `completed`. Отсечения shortlist сами по себе дают warnings. Планы baseline и incumbents экспортируются без новых EXPLAIN.

`GreedyOptimizer` остаётся отдельной стратегией для проверки только жадного этапа. Его `search(...)` возвращает конец цепочки, `S0`, полные оценки с планами и zero-baseline отказы; `Completed` этой стратегии отмечает завершённый `GREEDY`, без `REPAIR`.

Проверки алгоритма и pipeline без БД:

```sh
./gradlew --no-daemon test --tests 'ru.itmo.indexbudget.optimizer.*' --tests '*LimitedRepairPipelineTest'
```

Проверка на настоящих PostgreSQL/HypoPG costs и сверка бюджетных сценариев остаются в [#45](https://github.com/ITMO-DevDays-2026-IndexBudget/IndexBudget/issues/45) и общей приёмке PoC [#22](https://github.com/ITMO-DevDays-2026-IndexBudget/IndexBudget/issues/22). Тестовые cost vectors не заменяют эту интеграцию. HTML-renderer ещё не подключён, сквозной `analyze` по-прежнему возвращает `NOT_IMPLEMENTED`.

## Отчёт и экспорт (#19)

`DefaultReportBuilder` собирает общий `AnalysisReport` из сохранённых baseline и обоих incumbents. Метрики и цена устойчивости используют domain; JSON и HTML получают те же данные. Формат, значения `null` и стык renderer описаны в [контракте отчёта v2](docs/report-v2.md).

`AtomicReportExporter` готовит `report.json`, `report.html` и выбранный `indexes.sql` во временном каталоге с run ID рядом с назначением, повторно проверяет назначение и публикует каталог одним атомарным переименованием. Для `failed` сохраняются JSON/HTML без SQL. При ошибке возвращается `EXPORT_FAILED` (exit 1), чужие файлы сохраняются. Файловая система должна поддерживать атомарное перемещение каталогов; права нужны также на родительский каталог. Существующая ссылка на пустой каталог сохраняется, публикация идёт в её цель.

`ReportConfiguration` подключает builder; exporter регистрируется при наличии `ReportRenderer` из #20. До подключения HTML CLI остаётся `NOT_IMPLEMENTED`. Проверки экспорта используют тестовый renderer и не подтверждают готовность HTML-вёрстки либо настоящего анализа с HypoPG.

```sh
./gradlew --no-daemon test --tests 'ru.itmo.indexbudget.report.*' --tests '*ReportIntegrationTest' --tests '*ReportConfigurationTest'
```

## Оценка наборов через HypoPG (#13, #15)

`JdbcAnalysisSessionFactory` открывает одно физическое соединение из `INDEXBUDGET_DATABASE_URL`
(формат `jdbc:postgresql://host:port/database?user=...&password=...`). Переменная читается
только при открытии сессии; `.env` автоматически не загружается. URL и сообщения драйвера
не включаются в диагностику. Расширение HypoPG должно быть установлено заранее.

`JdbcAnalysisSession` на этом соединении читает каталог, получает сырой размер через
`estimateSize` и оценивает точный набор индексов через `evaluate`. DDL строится общим renderer,
SQL передаются целиком в `EXPLAIN (FORMAT JSON)` по query ID. Возвращаются только полный
вектор корневых costs и сохранённые планы. Профили частот не добавляют EXPLAIN. Сессия
очищает гипотезы до/после операции, восстанавливает транзакцию после ошибки и физически
закрывает соединение при отмене или исчерпании времени. Реальные индексы и настройки
планировщика сохраняются; `ANALYZE` и реальные CREATE INDEX адаптер не выполняет.

Все операции используют общий `RunContext`: 90 секунд на команду, минимум остатка
команды и 60 секунд с начала baseline для поиска, до 2 секунд на EXPLAIN, до 5 секунд
на подключение и до 2000 фактически начатых EXPLAIN, включая неуспешные. Клиентский
контроль deadline отменяет активный SQL и прерывает соединение. Отдельный timeout
EXPLAIN обесценивает весь набор; продолжение возможно после восстановления сессии.
При полном baseline остановка сохраняет лучший полный результат как `partial`,
без полного baseline получается `failed`. Ошибки отдельного кандидата и потери
соединения имеют разные коды; JDBC-сообщения с секретами в отчёт не попадают.

Интеграционные проверки на собственной одноразовой PostgreSQL 16 + HypoPG:

```sh
bash demo/check-hypopg.sh
```

Нужны Docker и JDK 25. Скрипт собирает существующий образ, создаёт отдельную БД на случайном
loopback-порту, запускает тесты и удаляет только свои контейнер и тег образа. Секреты и
данные общего стенда не используются. Без `INDEXBUDGET_HYPOPG_TEST_URL` обычный `test`
пропускает этот integration-класс. Детали контрактов — в [docs/contracts.md](docs/contracts.md#сессия-hypopg-лимиты-и-отмена-13-15).

## HTML-отчёт (#20)

`HtmlReportRenderer` отображает готовый `AnalysisReport v2`: выбранный набор,
сравнение robust/mean из общего пула, профили, бюджеты, SQL и сохранённые планы,
регрессии, отсечения и диагностику запуска. Метрики и цена устойчивости берутся
из модели. HTML автономен: CSS встроен, JavaScript и внешних ресурсов нет;
раскрываемые детали работают при открытии файла без сервера.

Для проверки оформления на синтетических данных:

```sh
./gradlew reportPreview
```

Команда перезаписывает `index.html` в корне и создаёт варианты в
`build/report-previews/`: `different`, `same`, `mean`, `partial`, `failed`,
`no-write`, `zero-baseline`, `wide`, `regression`, `missing` (расширение `.html`).
`index.html` — генерируемый локальный предпросмотр, исключённый из Git.
Откройте его в браузере и проверьте оформление, раскрытие SQL/планов и узкое окно.
Числа, планы и метаданные помечены как синтетические; это не запуск `analyze`.

Проверки рендерера: `./gradlew test --tests 'ru.itmo.indexbudget.report.*'`.
Они проверяют выбор набора, готовые метрики, статусы, неизвестные значения,
регрессии, длинный SQL, отсечения и экранирование текста. Визуальное согласование
с пользователем и проверка реального отчёта остаются отдельными этапами приёмки.
`ReportBuilder` и публикация согласованных JSON/HTML/SQL относятся к #19;
сквозная проверка с PostgreSQL — к #22/#21. Их готовность эта команда не подтверждает.

## CI

Workflow `CI` запускает `build-and-test` на PR в `main` и push в `main`: JDK 25, сборка, тесты и запуск установленного CLI без БД. После первого успешного запуска этот check можно сделать обязательным в ruleset `review`.

## Стенд и автоматическое обновление

Локальная PostgreSQL 16 + HypoPG, детерминированный seed, роль анализа и
workload для PoC находятся в [demo/](demo/README.md). Запуск из корня:

```sh
sh demo/init-env.sh
docker compose up --build --detach --wait --wait-timeout 180
sh demo/check.sh
```

Это стенд уровня 1 (#4); smoke check проверяет реальную БД через psql.
Фабрика сессии HypoPG зарегистрирована в Spring; сквозной CLI ещё ожидает остальные зависимости. Workflow `Demo DB` проверяет
сборку образа, seed, HypoPG и повторный запуск проверки отдельно от JVM CI.

Для установки CLI из `main` на стенд предусмотрены скрипты в `deploy/`.
После установки cron раз в минуту проверяет новый коммит, собирает его и запускает
тесты; успешный релиз активируется атомарно. Установка, запуск и диагностика описаны
в [инструкции деплоя](docs/deployment.md).

## Почему JDK 25

Для нового каркаса выбрана JDK 25 LTS вместо первоначальной JDK 21. Она поддерживается закреплёнными версиями Kotlin, Gradle и Spring Boot. JDK 26 — промежуточный релиз, поэтому для общей среды команды предпочтён актуальный LTS. Решение принято 10 ноября 2026; спецификация в репозитории обновлена в части версии JDK.

## Сравнение своей идеи индексов

Необязательный `manual_indexes` в workload v2 добавляет отдельную оценку ручного набора
после обычного поиска. JSON/HTML показывают эффекты и нарушения бюджетов, сохраняя
исходный смысл автоматических best_robust/best_mean. Формат и проверка:
[docs/manual-index-comparison.md](docs/manual-index-comparison.md).
