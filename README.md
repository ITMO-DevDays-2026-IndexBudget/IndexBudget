# IndexBudget

Демонстрационный веб-интерфейс: [frontend](frontend/README.md) — шаблоны БД,
фиксированные датасеты, редактор SQL и нагрузки, запуск CLI и публикация отчётов. Локально порт 8090,
на стенде установщик использует порт 3000.

Расчёт частот по окнам pg_stat_statements (#66): [контракт, примеры и проверки](docs/statistics-frequencies.md).

Ограниченные UPDATE/DELETE и смешанные workloads (#103): [синтаксис, безопасность, роли и смысл cost](docs/dml-analysis.md), [пример JSON v2](examples/workload-v2-dml.json). Данные при анализе не изменяются; DML требует отдельной opt-in роли, SELECT-only demo role не расширяется.

Подбор дополнительных индексов PostgreSQL для нескольких сценариев нагрузки под заданные бюджеты.

Репозиторий содержит CLI с валидацией JSON v2 и orchestration запуска: общий RunContext, стадии, владение сессией и сохранение пригодного результата при остановке. Есть AST-валидация и разрешение имён SQL, чтение JDBC-каталога и полный ограниченный генератор кандидатов: канонизация, удаление точных реальных дублей, до 32 локальных и до 16 общих через сценарный round-robin. Реализованы общие метрики/компаратор и жадный поиск с ограниченным repair, двумя incumbents и кэшем одного запуска. Выделенная JDBC-сессия HypoPG получает каталог, размеры и полные оценки наборов. Добавлены сборка отчёта v3 и согласованный экспорт JSON/SQL с вызовом HTML-renderer. Генератор, метрики, поиск, фабрика сессии и HTML-renderer (#20) подключены к рабочей команде. Orchestration, поиск и экспорт проверяются с подставными компонентами. Требования к MVP описаны в [спецификации v0.2](IndexBudget-spec-v0.2.md).

Порядок работы для агентов — в [AGENTS.md](AGENTS.md). В [ai/](ai/README.md) описаны целевая архитектура, контракты, соглашения разработки и [ревью PR без запуска тестов](ai/review.md).

## Требования и сборка

- JDK **25 LTS** (например, Eclipse Temurin), доступный через `JAVA_HOME` или `PATH`.
- Gradle устанавливать не нужно: в репозитории есть Wrapper **9.7.0** с проверкой SHA-256 дистрибутива.
- При первой сборке нужен доступ к Maven Central, Gradle Plugin Portal и дистрибутиву Gradle.
- Для сборки, тестов и `--help` база данных и Docker не нужны.

```sh
java -version
./gradlew build installDist
build/install/indexbudget/bin/indexbudget --help
build/install/indexbudget/bin/indexbudget --version
```

На Windows используйте `gradlew.bat` и `build\install\indexbudget\bin\indexbudget.bat`.
Для запуска из IDE выберите JDK 25 как Project SDK и Gradle JVM, импортируйте проект через Gradle и запускайте `IndexBudgetApplicationKt`.

Версии закреплены: Kotlin **2.4.21**, Spring Boot **4.1.2**, Gradle **9.7.0**. Spring Boot работает с `WebApplicationType.NONE`: HTTP-сервер не запускается. Jackson 3 и PostgreSQL JDBC управляются BOM Spring Boot; доменные контракты не зависят от этих библиотек.

## BRIN для диапазонов

По умолчанию подбираются прежние B-tree. Для явного сравнения методов добавьте
`"index_methods": ["btree", "brin"]` в workload v2. BRIN предлагается только на одной
колонке диапазонного WHERE, без INCLUDE и настройки параметров; оба метода делят
прежние caps и бюджеты. Ручной набор принимает `"method": "brin"` независимо от
автоматических методов. Write proxy не доказывает равную цену записи разных методов.

[Входной пример](examples/workload-v2-brin.json), [контракт, версии отчётов и реальный
прогон на миллионе строк](docs/brin.md). Воспроизведение на отдельном локальном Docker:

```sh
bash demo/check-brin.sh
```

Скрипт готовит данные и статистику только в собственном одноразовом контейнере;
обычный анализ не создаёт физические индексы. Артефакты сохраняются в
`build/brin-verification/run-*/`. При BRIN используются report v4 / сводка серии v2;
прежние B-tree-only запуски сохраняют v3/v1.

## Hash для простого равенства

Явный `"index_methods": ["btree", "hash"]` добавляет одноколоночный hash для
скалярного WHERE `=`. Без INCLUDE, пар и сортировки; лимиты и бюджеты общие,
B-tree остаётся default. [Пример](examples/workload-v2-hash.json),
[контракт, ограничения и реальная проверка](docs/hash.md).

## CLI

После `installDist` можно добавить `build/install/indexbudget/bin` в `PATH` и использовать имя `indexbudget`.

```sh
build/install/indexbudget/bin/indexbudget analyze \
  --workload demo/workload-poc.json \
  --output-dir reports/run-001
```

В [demo/workload-poc.json](demo/workload-poc.json) — три SQL, два профиля частот, ручной профиль записи и оба бюджета. После валидации команда открывает выделенную сессию PostgreSQL/HypoPG, формирует ограниченный shortlist, выполняет greedy + repair с выбранными ресурсными пределами и сохраняет `report.json`, автономный `report.html` и выбранный `indexes.sql`. Для запуска нужны подготовленная БД и `INDEXBUDGET_DATABASE_URL`; фикстуры не используются как результат реального анализа.

Режим глубины задаётся необязательным полем JSON `"analysis_mode": "normal"` или флагом `--analysis-mode fast|normal|deep`. Флаг имеет приоритет; прежние JSON без поля и запуск без флага используют `normal` с прежними пределами. Неверное значение, иной тип и явный `null` в JSON отклоняются; CLI-переопределение не скрывает ошибки JSON. Например, быстрый запуск того же входа:

```sh
build/install/indexbudget/bin/indexbudget analyze \
  --workload demo/workload-poc.json \
  --output-dir reports/run-fast \
  --analysis-mode fast
```

| Режим | Вся команда, с | Поиск с baseline, с | Попытки EXPLAIN | Новые repair-попытки |
| --- | --- | --- | --- | --- |
| `fast` — быстрый | 30 | 20 | 500 | 8 |
| `normal` — обычный, default | 90 | 60 | 2000 | 28 |
| `deep` — глубокий | 300 | 240 | 10000 | 256 |

Во всех режимах один EXPLAIN ограничен минимумом 2 секунд и остатка времени, подключение — минимумом 5 секунд и остатка. Режимы используют тот же пул до 16 кандидатов и тот же greedy/fixed-`S0` repair. `deep` разрешает больше работы и может вернуть тот же набор; улучшение и точная длительность не обещаются. Выбранный режим, шесть эффективных лимитов, реальные counters и причины остановки видны в stderr, JSON и HTML. Исходный JSON hash сохраняется и при переопределении режима флагом. [Сравнение режимов и затрат](docs/analysis-modes.md).

Рейтинг общего shortlist выбирается независимо от глубины: необязательное JSON-поле `"candidate_ranking": "frequency"` или флаг `--candidate-ranking frequency|baseline_cost`. По умолчанию используется прежний `frequency`; `baseline_cost` — экспериментальная сумма нормированной частоты SQL × его сохранённый baseline planner cost. Флаг имеет приоритет над валидным JSON и не меняет hash исходного файла; `null`, неизвестное значение, неверный тип и повтор флага отклоняются. Выбранная стратегия видна в CLI/JSON/HTML. Например:

```sh
build/install/indexbudget/bin/indexbudget analyze \
  --workload demo/workload-poc.json \
  --output-dir reports/run-baseline-cost \
  --candidate-ranking baseline_cost
```

Рейтинг меняет только порядок сценарных очередей начального shortlist и его резерва. Квоты профилей, арность ключей, INCLUDE/OR, caps и критерии robust/mean сохраняются; дополнительных EXPLAIN для рейтинга нет. [Формула, числовые границы и сравнение стратегий](docs/candidate-ranking.md).

После локального отбора генератор сохраняет начальные 16 и резерв до 48 кандидатов, продолжая тот же round-robin профилей и чередование арности ключей, в том числе для INCLUDE. Подготовка передаёт поиску до 16 индивидуально допустимых кандидатов: write budget по keys + INCLUDE проверяется до оценки размера, storage — после неё. Разрешено до 32 size-вызовов, включая ошибки, и действует общий deadline. Отказы, пополнения, неизвестные оценки и причина остановки видны в JSON v3 и HTML. [Правила и числовой пример refill](docs/candidate-refill.md). Для серии бюджетов доступна отдельная команда `analyze-series` с общей подготовкой пула; [формат и область сравнения](docs/budget-series.md).

До подключения к БД проверяются:

- JSON v2 в UTF-8 размером до 1 MiB; SQL до 64 KiB UTF-8 каждый, без обрезания. Неизвестные поля, повторяющиеся ключи, неверные типы и лишнее содержимое после JSON отклоняются. Строки не преобразуются в числа, дроби — в целые, значения enum регистрозависимы.
- 1–20 SQL и 1–3 профиля с уникальными непустыми IDs. `calls_per_hour` содержит ровно все query IDs; частоты конечны и неотрицательны, в каждом профиле и для каждого SQL есть положительное использование.
- Положительные конечные веса и возможность их нормирования без переполнения суммы или потери положительного веса. Исходные относительные веса сохраняются.
- `objective`: `robust` по умолчанию либо `mean`; целый неотрицательный `storage_budget_bytes`, целый `max_indexes` от 0 до 5 (по умолчанию 5). `write_budget_units_per_hour` обязателен: неотрицательное конечное число, включая 0, либо явный `null` для отключения лимита.
- При включённом write budget требуется `table_write_rates`. Каждая переданная запись содержит все три неотрицательных конечных rate; `source` может быть только `manual`, при отсутствии используется это значение. При выключенном лимите профиль можно не передавать. `ResolvedWorkloadValidator` после SQL resolution проверяет точное покрытие всех физических workload-таблиц; неполный или лишний переданный профиль отклоняется и при выключенном лимите. Ключи — точные `schema.name` с сохранением регистра, без интерпретации SQL-алиасов и кавычек.
- Необязательные `constraints.query_cost_guards` (#78) отмечают критические SQL и задают максимальное отношение final/baseline planner cost (не проценты, ≥ 1.0; равенство порогу проходит). Набор с превышением отклоняется целиком с `CRITICAL_QUERY_REGRESSION` и не обновляет incumbents; при нулевом baseline отношением не считается ноль, а любой положительный cost нарушает guard. Это ограничение planner cost, не latency/SLA; прежний вход без поля сохраняет поведение. Пример — [workload-v2-guards.json](examples/workload-v2-guards.json).
- `output-dir` должен быть новым или пустым каталогом. Непустой каталог при начальной валидации отклоняется с `OUTPUT_DIRECTORY_NOT_EMPTY` (exit 2); существующие файлы сохраняются. Неоднозначный путь с `..` после ещё не созданного каталога отклоняется с `INVALID_INPUT`. Экспорт повторяет проверку перед публикацией; отказ этой повторной проверки обрабатывается как `EXPORT_FAILED` (exit 1).

В [examples/](examples/) есть варианты с двумя SQL для `robust` и `mean`, включая выключенную модель записи. SQL-анализатор проверяет поддержанный AST и лимит 256 сравнений WHERE/JOIN, разрешает имена через CatalogSnapshot и передаёт полный ResolvedWorkload генератору (#8/#9). DSN PostgreSQL-адаптера задаётся через `INDEXBUDGET_DATABASE_URL`; `.env.example` служит шаблоном, автоматическое чтение `.env` не реализовано.

В stderr выводятся стадии `validation/introspection/baseline/candidates/greedy/repair/report` и реальные счётчики EXPLAIN, полных оценок и cache hits по мере выполнения; процент готовности не вычисляется. Каждая ошибка — отдельная строка `CODE: {"code":"CODE","message":"..."}` с необязательными `query_id`, `profile_id` и `details`; для ошибок полей `details.field` указывает место во входе. Это относится и к сохранённым ошибкам partial: они выводятся в stderr, а итоговый код остаётся 3 после успешного экспорта. Управляющие символы экранируются, исходный SQL, пути с секретами и сообщения JSON-парсера не выводятся. Например, вход `{"schema_version":1}` даёт exit code 2:

```text
UNSUPPORTED_SCHEMA_VERSION: {"code":"UNSUPPORTED_SCHEMA_VERSION","message":"Expected schema_version: 2. Migrate v1 frequencies from queries to profiles.calls_per_hour.","details":{"field":"schema_version"}}
```

Коды выхода MVP: `0` — completed/help/version, `2` — невалидный или неподдержанный вход, `3` — partial с сохранённым результатом, `1` — failed. CLI возвращает код результата pipeline после сохранения отчётов; для help/version и начальной валидации БД не требуется. Ошибки полей дают `INVALID_INPUT` или `INVALID_WRITE_PROFILE` с кодом 2; переполнение суммы весов и потеря положительного числа при представлении или нормировании дают `NUMERIC_ERROR` с кодом 1. Ошибка доступа к output-dir даёт `EXPORT_FAILED` с кодом 1.

### Поддержанный SQL

Поднабор WHERE включает AND/OR со скобками, сравнения, `IN` с 1–256 литералами, обычный положительный
`BETWEEN`, `IS NULL` и `IS NOT NULL`. Каждый элемент IN, обе границы BETWEEN и null-test
участвуют в общем лимите сложности 256 вместе с JOIN. Пример для таблицы demo:
[workload-v2-predicates.json](examples/workload-v2-predicates.json). SQL и NULL передаются
планировщику без переписывания; NOT, NOT IN/NOT BETWEEN, подзапросы и выражения вместо
колонки/литерала в новых формах пока отклоняются. Подробности — в
[спецификации](IndexBudget-spec-v0.2.md#поддержанный-sql-и-каталог).

[Пример OR-workload](examples/workload-v2-or.json) сохраняет структуру условий. Пары индексов
не объединяют взаимоисключающие ветви; происхождение ветвей и ограничения стратегии показаны
в JSON/HTML. DNF не разворачивается; действует общий лимит 256 единиц сложности, дополнительно
до 1024 узлов условий и глубина 512. Полный исходный SQL остаётся в EXPLAIN.

## Поиск greedy + repair (#17, #18)

`LimitedRepairOptimizer` зарегистрирован в Spring и использует готовый полный baseline, shortlist с известными размерами, единые метрики и компаратор. Жадный этап оценивает каждый допустимый набор целиком и обновляет `bestRobust` и `bestMean` из одного исследованного пула. Выбранный objective определяет продвижение цепочки; отсутствие одиночной пользы не исключает кандидата из repair.

После greedy фиксируется лучший для выбранного objective набор `S0`. Repair один раз обходит очереди `0→2`, `1→1`, `1→2` в порядке round-robin и не перестраивает соседство после улучшений. Ранги входящих кандидатов используют известную одиночную пользу, размер и ID; для robust польза берётся на худшем positive-baseline профиле `S0`. Бюджеты и `max_indexes` проверяются до evaluator, эффект сочетания не складывается из одиночных эффектов.

Кэш внутри запуска хранит полные costs/plans по отсортированным candidate IDs. Cache hit не расходует EXPLAIN или repair slots; ошибочные наборы повторно не оцениваются. Новые неудачные repair-попытки расходуют выбранный предел 8/28/256. При 16 кандидатах, `max_indexes = 5` и 20 SQL только для `normal` верхняя граница вместе с baseline — 99 оценок / 1980 EXPLAIN; дополнительные профили её не увеличивают. Пределы обычного режима — 2000 EXPLAIN, 60 секунд с начала baseline и 90 секунд с начала команды. Для `deep` прежняя граница 1980 не заявляется.

Неполный или ошибочный вектор не обновляет incumbents. Локальная ошибка гипотезы исключает кандидата с warning; ошибка EXPLAIN сохраняется отдельно и допускает дальнейший поиск с итоговым `partial`. Потеря соединения, отмена и общие лимиты останавливают поиск с сохранением обоих полных результатов. Если после исчерпания выбранного repair-лимита остались допустимые непроверенные соседи, результат — `partial/REPAIR_LIMIT`; если предусмотренный проход завершён, результат — `completed`. Отсечения shortlist сами по себе дают warnings. Планы baseline и incumbents экспортируются без новых EXPLAIN.

`GreedyOptimizer` остаётся отдельной стратегией для проверки только жадного этапа. Его `search(...)` возвращает конец цепочки, `S0`, полные оценки с планами и zero-baseline отказы; `Completed` этой стратегии отмечает завершённый `GREEDY`, без `REPAIR`.

Проверки алгоритма и pipeline без БД:

```sh
./gradlew --no-daemon test --tests 'ru.itmo.indexbudget.optimizer.*' --tests '*LimitedRepairPipelineTest'
```

Проверка на настоящих PostgreSQL/HypoPG costs и сверка бюджетных сценариев остаются в [#45](https://github.com/ITMO-DevDays-2026-IndexBudget/IndexBudget/issues/45) и общей приёмке PoC [#22](https://github.com/ITMO-DevDays-2026-IndexBudget/IndexBudget/issues/22). Тестовые cost vectors не заменяют эту интеграцию. Подключённый HTML-renderer отображает сохранённый результат `analyze`; воспроизводимое сравнение режимов на одной нагрузке описано в [режимах анализа](docs/analysis-modes.md).

## Отчёт и экспорт (#19)

`DefaultReportBuilder` собирает общий `AnalysisReport` из сохранённых baseline и обоих incumbents. Метрики и цена устойчивости используют domain; JSON и HTML получают те же данные. Формат, значения `null` и стык renderer описаны в [контракте отчёта v3](docs/report-v3.md).

`AtomicReportExporter` готовит `report.json`, `report.html` и выбранный `indexes.sql` во временном каталоге с run ID рядом с назначением, повторно проверяет назначение и публикует каталог одним атомарным переименованием. Для `failed` сохраняются JSON/HTML без SQL. При ошибке возвращается `EXPORT_FAILED` (exit 1), чужие файлы сохраняются. Файловая система должна поддерживать атомарное перемещение каталогов; права нужны также на родительский каталог. Существующая ссылка на пустой каталог сохраняется, публикация идёт в её цель.

`ReportConfiguration` подключает builder и exporter; штатный `HtmlReportRenderer` зарегистрирован как Spring-компонент. Проверки экспортёра с тестовым renderer проверяют публикацию артефактов; настоящий анализ с HypoPG проверяется отдельно.

```sh
./gradlew --no-daemon test --tests 'ru.itmo.indexbudget.report.*' --tests '*ReportIntegrationTest' --tests '*ReportConfigurationTest'
```

## Оценка наборов через HypoPG (#13, #15)

`JdbcAnalysisSessionFactory` открывает одно физическое соединение из `INDEXBUDGET_DATABASE_URL`
(формат `jdbc:postgresql://host:port/database?user=...&password=...`). Переменная читается
только при открытии сессии; `.env` автоматически не загружается. URL и сообщения драйвера
не включаются в диагностику. Расширение HypoPG должно быть установлено заранее.

`JdbcAnalysisSession` на этом соединении читает каталог, получает сырой размер через
`estimateSize` и оценивает точный набор индексов через `evaluate`. DDL строится общим renderer,
SQL передаются целиком в `EXPLAIN (FORMAT JSON)` по query ID. Возвращаются только полный
вектор корневых costs и сохранённые планы. Профили частот не добавляют EXPLAIN. Сессия
очищает гипотезы до/после операции, восстанавливает транзакцию после ошибки и физически
закрывает соединение при отмене или исчерпании времени. Реальные индексы и настройки
планировщика сохраняются; `ANALYZE` и реальные CREATE INDEX адаптер не выполняет.

Все операции используют общий `RunContext` с пределами выбранного режима: в `normal`
90 секунд на команду, минимум остатка команды и 60 секунд с начала baseline для поиска,
до 2000 фактически начатых EXPLAIN, включая неуспешные. Для `fast`/`deep` действуют
значения из таблицы режимов выше; во всех пресетах до 2 секунд на EXPLAIN и до 5 секунд
на подключение с ограничением оставшимся временем. Клиентский
контроль deadline отменяет активный SQL и прерывает соединение. Отдельный timeout
EXPLAIN обесценивает весь набор; продолжение возможно после восстановления сессии.
При полном baseline остановка сохраняет лучший полный результат как `partial`,
без полного baseline получается `failed`. Ошибки отдельного кандидата и потери
соединения имеют разные коды; JDBC-сообщения с секретами в отчёт не попадают.

Интеграционные проверки на собственной одноразовой PostgreSQL 16 + HypoPG:

```sh
bash demo/check-hypopg.sh
```

Нужны Docker и JDK 25. Скрипт собирает существующий образ, создаёт отдельную БД на случайном
loopback-порту, запускает тесты и удаляет только свои контейнер и тег образа. Секреты и
данные общего стенда не используются. Без `INDEXBUDGET_HYPOPG_TEST_URL` обычный `test`
пропускает этот integration-класс. Детали контрактов — в [docs/contracts.md](docs/contracts.md#сессия-hypopg-лимиты-и-отмена-13-15).

## Сводка рекомендации и происхождение (#68)

Общий отчёт показывает снижение взвешенной стоимости планов, M/R, выбранные индексы,
расходы бюджетов и число SQL с ростом стоимости. JSON содержит готовые серии сравнений
baseline/selected/best_robust/best_mean для профилей и отдельных SQL; HTML использует ту же
модель. Неизвестные показатели, нулевой baseline, отключённый лимит записи и фактический
ноль различаются. Сборка сводки не выполняет новых EXPLAIN.

Для сохранённых наблюдений можно передать необязательное `provenance` во входном JSON v2:
[пример](examples/workload-v2-provenance.json), [контракт](docs/report-v3.md#происхождение-нагрузки-68).
Источник, окна, охват и примеры параметров появятся в JSON/HTML; историческое время
останется отдельными данными. Поля поддержаны в обычном `analyze`; автоматическое получение
нагрузки из окон относится к #66/#67. Ручные файлы продолжают работать без метаданных.
[Пример отчёта](examples/report-v3-provenance.json) синтетический, воспроизводится через `reportPreview`.

Проверка сводки с настоящим результатом импортёра #67: `bash demo/check-import.sh`
(JDK 25 и Docker). Два окна наблюдения проходят импорт, обычный `analyze` и экспорт;
источник, периоды, охват, примеры и числа сводки сверяются с манифестом и общей моделью.
Отчёт строится после закрытия JDBC-сессии без дополнительных EXPLAIN. Реальные примеры
файлов сохраняются в `build/report-import-verification/`; CI прикладывает их к
`observed-import-test-results`. [Описание комплекта](examples/observed-import/README.md).

## HTML-отчёт (#20, #69)

`HtmlReportRenderer` отображает сохранённый `AnalysisReport v3`: рекомендацию,
изменения запросов, ресурсы и индексы, происхождение нагрузки и следующие шаги.
Вместо повторяющихся графиков используются таблицы. При одном профиле средний и
худший эффект не дублируются; для двух–трёх сохраняются исходные названия.
Сравнение robust/mean из общего пула, методика и диагностика доступны в раскрытиях.

Рядом с выводом указаны исходные данные и ограничения наблюдений. Planner cost —
оценка затрат PostgreSQL, не время выполнения; write proxy — условная модель
сопровождения индексов, не измеренное замедление записи. SQL с ухудшениями стоят
первыми. Полные SQL, DDL, планы и точные значения доступны в подробностях.

HTML автономен: CSS и фиксированный JavaScript встроены, сетевых обращений нет.
CSP разрешает только скрипт с точным SHA-256; динамические значения экранируются.
Без JavaScript доступны таблицы и нативные раскрытия. Сортировка и копирование
меняют только просмотр; метрики и выбранный набор не пересчитываются.

Для проверки оформления на синтетических данных:

```sh
./gradlew reportPreview
```

Команда перезаписывает `index.html` в корне и создаёт варианты в
`build/report-previews/`: `different`, `same`, `mean`, `partial`, `failed`,
`no-write`, `zero-baseline`, `wide`, `regression`, `missing`, `include`, `imported`, `fractional`,
`one-profile`, `three-profiles`, `empty`, `tiny-decrease`, `tiny-increase`, `long-names`,
`recorded-import`, `recorded-series-0/1/2`
(согласованные файлы `.html` и `.json`).
`index.html` — генерируемый локальный предпросмотр, исключённый из Git.
Откройте его в браузере и проверьте оформление, раскрытие SQL/планов и узкое окно.
Обычные варианты помечены как синтетические; это не запуск `analyze`.
`recorded-import` и `recorded-series/recorded-series.html` воспроизводят сохранённые
факты предоставленных HTML без нового анализа БД. У записанной серии один профиль
`default`, бюджеты записи 0/1/2, ручной ввод без provenance; чужие окна наблюдения
ей не приписываются. Исходный JSON не восстанавливается, недоступные hashes остаются
неизвестными. [Ресурсы фикстур](src/testFixtures/resources/report/) сохраняют источник,
его SHA-256 и ограничения реконструкции.

Проверки рендерера: `./gradlew test --tests 'ru.itmo.indexbudget.report.*'`.
Они проверяют выбор набора, готовые метрики, статусы, неизвестные значения,
регрессии, длинный SQL, отсечения и экранирование текста.

Локальная сортировка и переходы к SQL проверяются без браузера:
`node src/test/javascript/report-controls.test.js` (либо JavaScriptCore `jsc` на macOS).
Этот тест использует минимальную подставную DOM-модель. В CI после `reportPreview`
обязательно запускается `bash demo/check-report-ui.sh`: одноразовый контейнер с Node
и Chromium выполняет тот же JS-тест, затем проверяет таблицы и взаимодействия
при ширине окна 1440, 900, 390 и 320 px, без сети. Сверяются сохранённые значения
с JSON, 1–3 профиля, состояния без данных, раскрытые SQL/планы, отсутствие
горизонтального переполнения и разрешённое CSP выполнение скрипта. Для локального
повтора нужны Docker и предварительный `./gradlew reportPreview`.
Среда браузерного теста — закреплённый [официальный образ Playwright](https://playwright.dev/docs/docker).

Визуальное согласование
с пользователем и проверка реального отчёта остаются отдельными этапами приёмки.
`ReportBuilder` и публикация согласованных JSON/HTML/SQL относятся к #19;
сквозная проверка с PostgreSQL — к #22/#21. Их готовность эта команда не подтверждает.

## Почему JDK 25

Для нового каркаса выбрана JDK 25 LTS вместо первоначальной JDK 21. Она поддерживается закреплёнными версиями Kotlin, Gradle и Spring Boot. JDK 26 — промежуточный релиз, поэтому для общей среды команды предпочтён актуальный LTS. Решение принято 10 ноября 2026; спецификация в репозитории обновлена в части версии JDK.

## Серия бюджетов (#75)

`analyze-series` последовательно рассчитывает 3–5 значений одного бюджета. Workload v2 задаёт общие SQL, профили, objective, write profile и второй бюджет; отдельный JSON серии выбирает изменяемый бюджет и значения. Режим и рейтинг можно переопределить теми же CLI-флагами, что у `analyze`.

```sh
build/install/indexbudget/bin/indexbudget analyze-series \
  --workload demo/workload-poc.json \
  --series examples/budget-series-storage.json \
  --output-dir reports/budget-series-001 \
  --analysis-mode normal \
  --series-timeout-seconds 600
```

Пул до 16 кандидатов готовится один раз при максимальном бюджете серии, включая общий refill. Каждая точка имеет свои RunContext, JDBC-сессию, baseline и кэш поиска; точки только фильтруют общий пул по бюджету. Общий deadline ограничивает подготовку и все точки. Ранее опубликованные результаты сохраняются при ошибке точки или остановке серии; совпавшие рекомендации также являются результатом.

Откройте корневой `report.html`: таблица сравнивает бюджеты, индексы, эффект,
расходы и статусы. Переключатель синхронно меняет вывод и разделы SQL/ресурсов.
Одинаковые SQL, DDL и планы находятся в общих каталогах; точные метрики и диагностика —
в раскрытиях. Совпавшие наборы, немонотонный эффект, partial/failed/skipped и изменения
условий обозначены явно. По умолчанию показан пригодный вариант с наибольшим бюджетом;
это выбор для просмотра, не рекомендация повысить лимит. Файл работает без сервера
и сети, без JavaScript доступны все варианты. Для ссылок на отдельные JSON/SQL
переносите весь каталог серии.

Рядом сохраняются машинная сводка `series.json` v1 и прежний `series.html` только со сравнением. Сводки фиксируют условия общей подготовки и обнаруженное изменение baseline/каталога: такой результат нельзя без оговорки объяснять только изменением бюджета. [Вход, поля сводки, статусы и ограничения сопоставимости](docs/budget-series.md).

`./gradlew reportPreview` создаёт синтетические примеры в `build/report-previews/series-{mixed,same,nonmonotonic,zero-baseline,no-write,write,regression}/report.html` с соответствующими JSON и артефактами точек. `bash demo/check-report-ui.sh` проверяет их в Chromium без сети на ширинах 1440/900/390/320 px, сверяет сохранённые данные таблиц и каталогов с JSON и открывает ссылки после переноса каталога. Скриншоты сохраняются в `build/report-ui-verification/`. Это проверка отображения и публикации через настоящий pipeline серии с подставными оценками, без PostgreSQL.

## Сбор наблюдаемой нагрузки

После снимков можно построить обычный workload v2:

```text
indexbudget import-workload --config import-config.json --output-dir imported
indexbudget analyze --workload imported/workload.json --output-dir analysis
```

Импорт требует 1–3 окна, явные SQL-примеры с литералами и исходный контекст схем,
проверяет AST/типы/имена и отбирает до 20 SQL по всем профилям. UNKNOWN не становится
нулём. Workload и отдельный манифест сохраняют периоды, отбор и репрезентативность
примеров; provenance переносится в JSON/HTML анализа. Бюджеты/write rates остаются
ручными. [Форматы и ограничения #67](docs/observed-workload-import.md),
[синтетический комплект](examples/observed-import/import-config.json).

Реальный маршрут на одноразовой PostgreSQL/HypoPG проверяется `bash demo/check-import.sh`
и CI `postgres-observed-import`; требуется работающий Docker Engine.

`indexbudget stats --help` описывает отдельные команды `stats snapshot` и `stats pair`
для read-only снимков pg_stat_statements в PostgreSQL 16. Они не запускают подбор индексов,
не устанавливают расширение и не меняют общую БД. Формат снимков v1, лимиты, права и
одноразовая интеграционная проверка — в [docs/statistics-snapshots.md](docs/statistics-snapshots.md).

## Покрывающие индексы INCLUDE (#79)

К ключам из условий и сортировки генератор может добавить до двух колонок явной проекции. Звёздочка отключает INCLUDE; подмножества широкой проекции не перебираются. Caps 16/32/16 и 976 определений на область сохранены, отсечения и происхождение видны в отчёте. Payload участвует в оценке размера и write proxy: изменения строк × (число ключей + число INCLUDE-колонок).

Выходной `report.json` теперь имеет `schema_version: 3` с `included_columns` и `write_proxy_model`; reader v2 требует обновления. Вход workload по-прежнему v2, CLI не меняется. HTML/SQL показывают тот же INCLUDE; index-only scan не гарантирует отсутствие heap fetches. [Контракт v3](docs/report-v3.md), [реальный пример и команды](demo/include/README.md).
