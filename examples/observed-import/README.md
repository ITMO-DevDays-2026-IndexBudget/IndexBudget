# Примеры импорта и сводки #67/#68

Файлы `before.json`, `after.json`, `examples.json` и `import-config.json` в этом каталоге
**синтетические**: database OID 42 и идентичности предназначены для unit-тестов.
Они не являются выгрузкой стенда и не подтверждают сквозную интеграцию.

Для получения настоящего комплекта из одноразовой PostgreSQL 16 с HypoPG и
pg_stat_statements выполните из корня репозитория (JDK 25 и Docker):

```sh
bash demo/check-import.sh
```

Сценарий #68 создаёт таблицу из 5000 строк и наблюдает три запроса. В первом окне
числа вызовов равны 7/3/5, во втором — 2/9/4. Для первых двух запросов переданы
репрезентативные литералы; третий исключается с `MISSING_EXAMPLE`. Он остаётся
в знаменателе охвата доступных полных записей вместе с прочими наблюдаемыми SQL.
В анализ попадают два общих SQL и профили `normal`/`campaign` с весами 3/1.
Частоты рассчитываются по реальной длительности окон. Профиль записи отсутствует,
поэтому write units остаются неизвестными, а лимит записи отключён.

После успешной проверки каталог `build/report-import-verification/` содержит:

| Файлы | Назначение |
| --- | --- |
| `before.json`, `middle.json`, `after.json` | Три настоящих снимка, образующие два окна |
| `config.json`, `examples.json` | Вход импортёра с явными литералами и контекстом разрешения имён |
| `workload.json`, `import-manifest.json` | Настоящий выход импортёра; SHA-256 манифеста включён в provenance |
| `report.json`, `report.html`, `indexes.sql` | Результат обычного analyze, одна сводка и один выбранный набор |

Скрипт удаляет свой контейнер. Сохранённые отчёты можно изучать без БД;
повторный импорт/анализ требует исходного каталога и его идентичностей, поэтому
для нового окружения повторно запускайте сценарий целиком. UUID схемы, OID, моменты
снимков, частоты, историческое время, costs и размеры могут различаться между запусками.
Не заменяйте OID в примере ради проверки на другой БД.

Тест сверяет источник, правило отбора и хэш, окна/полноту, охват calls/исторического
времени и происхождение каждого примера с манифестом. Исключение третьего SQL проверяется
по полному ключу; знаменатели calls и времени независимо суммируются из допустимых
дельт снимков, включая служебные SQL коллектора. Числа сводки и четырёх серий
cost в JSON проверяются по `AnalysisReport`, HTML — по той же модели с учётом
форматирования, с извлечением всех шести карточек сводки из готового HTML.
SQL содержит ровно выбранные определения. Сессия уже закрыта
перед построением отчёта, счётчики EXPLAIN и оценок при экспорте не меняются.
Исторические миллисекунды не превращаются в ожидаемое время после добавления индексов.

Комплект остаётся вне Git и публикуется CI в `observed-import-test-results`.
Фиксированный [синтетический отчёт](../report-v3-provenance.json) сохраняется отдельно.
Форматы: [импорт](../../docs/observed-workload-import.md),
[сводка и provenance](../../docs/report-v3.md#происхождение-нагрузки-68).
