# Общая demo-БД: карта для команды и агентов

Всё находится в IndexBudget. Ansible и отдельный infra-репозиторий не используются.
Этот каталог управляет только общей PostgreSQL/HypoPG. CLI развёртывается прежними
скриптами в deploy/ и имеет своё cron-задание.

**Статус:** подготовлено локально; установка на WSL и новый CI persistence test
ещё не подтверждены. До этих изменений разработчик подтвердил сборку Gradle
на JDK 25 и два smoke check на PostgreSQL 16.15/HypoPG 1.4.2. После этого
пароли seed параметризованы и добавлен механизм сохранения БД при деплое.

проверять на отдельной БД, чтобы не менять baseline команды.

## Что делает CI и что делает сервер

CI собирает временную БД, запускает smoke test, затем на отдельном runner
проверяет сохранение контрольной записи после замены контейнера, отсутствие
перезапуска при изменении только приложения, миграции и читаемость backup.
CI не подключается к реальному серверу и не получает его пароль.

На WSL cron каждые пять минут читает main этого публичного репозитория.
Изменения `demo/postgres` или `deploy/db` приводят к новой сборке образа,
backup, обновлению контейнера и применению миграций. Остальные изменения
приложения не перезапускают БД. Деплой может кратко разорвать подключения.

Poller не ожидает результат GitHub CI: перед слиянием настройте обязательный
check `database-checks` в защите main (вместо `stand-persistence`). Прямые push в main обходят эту
организационную гарантию. Как и CLI, сервер читает только main, не PR-ветки.

Workflow запускается на каждом PR в main. Job `changes` выбирает Docker-проверки
только при изменениях БД/деплоя; ручной запуск выполняет их всегда. Итоговый
`database-checks` запускается с `always()`: для изменений БД требует успеха
обоих jobs, а для остальных PR разрешает их ожидаемый пропуск. Ошибка определения
изменений, ошибка тестов или отмена не превращаются в успешную проверку.

## Ограничения WSL

Стенд работает на компьютере коллеги, доступно 10 потоков, 10 GiB RAM, 100 GB SSD.
БД ограничена 2 CPU, 2 GiB RAM без дополнительного swap и 256 PID. Логи Docker
ограничены тремя файлами по 10 MiB. Docker build может временно потреблять
дополнительные ресурсы; make в Dockerfile запускается без параллельных jobs.

Никаких изменений Windows, WSL, SSH, firewall, Docker daemon и существующих
пробросов портов. Никаких глобальных prune, удаления чужих контейнеров/volume.
Установщик не использует sudo и не устанавливает пакеты. Docker и cron должны
уже работать; их автозапуск после рестарта WSL остаётся у владельца машины.

## Первый запуск

Сначала merge изменений #4 с этим каталогом в main. На сервере нужны Linux,
Bash, Python 3, Git, Docker/Compose v2 с доступом текущего пользователя,
cron, flock, timeout, sha256sum. Сначала подключитесь через привычный SSH-алиас
и проверьте fingerprint у владельца. Адреса и пароли здесь не хранятся.

На сервере склонируйте или обновите отдельную рабочую копию репозитория,
не меняя управляемые каталоги CLI releases/current:

```sh
git clone https://github.com/ITMO-DevDays-2026-IndexBudget/IndexBudget.git ~/indexbudget-db-bootstrap
cd ~/indexbudget-db-bootstrap
bash deploy/db/inspect.sh
```

Проверьте занятость порта 55432, существующие контейнеры и свободное место.
Затем:

```sh
bash deploy/db/install.sh
```

Он создаст только `~/indexbudget-db`, сгенерирует случайные пароли, выполнит
первый deploy и лишь после успеха добавит собственную строку cron. Чужие
задания, включая CLI, сохраняются. Повторная установка не меняет пароли.
Изменение установленного launcher `update.sh` требует повторного install;
deploy.sh, Compose и миграции читаются автоматически из main.

## Подключение

Откройте туннель с локальной машины (вместо `stand` — ваш SSH-алиас):

```sh
ssh -N -L 55432:127.0.0.1:55432 stand
```

Клиент: host 127.0.0.1, port 55432, database indexbudget, user indexbudget_reader.
Reader-пароль выдаёт владелец установки через приватный канал. При занятом
локальном порте используйте `-L 55433:127.0.0.1:55432` и порт 55433 в клиенте.
Не публикуйте DSN с паролем. HypoPG-гипотезы принадлежат конкретному соединению.

## Секреты

SSH-пароль/ключ не хранится в Git, inventory, workflow или GitHub Variables.
GitHub Secrets тоже не нужны для server-pull: репозиторий публичный.
Пароли БД генерируются только на сервере в `~/indexbudget-db/db.env` с правами
0600, родительский каталог — 0700. Не пересылайте файл целиком, он содержит
также пароль администратора. CI использует свои случайные временные пароли.
Локальные `.env` исключены из Git, шаблон `.env.example` не содержит паролей.

Не выводите полный docker inspect или compose config на стенде: они содержат
переменные окружения. Используйте config --quiet или узкие format-шаблоны.
Backup тоже приватен; не прикладывать к PR. Если репозиторий станет приватным,
read-only доступ сервера настраивается отдельно, без токена в URL репозитория.

## Данные, миграции и backup

Живые данные: external volume **indexbudget-stand-pg16-data**. Compose не
удаляет его при замене контейнера. Seed на существующем volume не запускается.
Для схемы добавляйте `migrations/002_description.sql` и далее. Уже применённые
файлы не менять: SHA-256 хранится в `demo_meta.schema_migrations`.

Каждый файл и его отметка применяются одной транзакцией, lock_timeout 5s,
statement_timeout 30s. Не писать внутри BEGIN/COMMIT, не использовать
CONCURRENTLY, DROP/TRUNCATE или повторный seed. Пароли ролей не меняются
редактированием db.env: ротация — отдельная согласованная процедура.

Перед обновлением работающей БД сохраняется pg_dump -Fc; ошибка backup
останавливает deploy. Дамп содержит таблицы, но не пароли ролей. Volume и
локальные дампы находятся на одной машине и не защищают от потери её диска.
Внешнее копирование backup пока не автоматизировано.

Дампы, releases и образы автоматически не удаляются. При свободном месте
менее 10 GiB в файловой системе установки новые deploy останавливаются.
Если Docker data root на другом диске/VHD, его место проверяется отдельно.
Это не квота БД и не ограничение пользовательских INSERT.

## Диагностика

| На сервере | Содержимое |
| --- | --- |
| `~/indexbudget-db/update.log` | Журнал, ротация в .1 при 10 MiB |
| `~/indexbudget-db/current` | Последний успешно проверенный релиз |
| `~/indexbudget-db/pending-release` | Целевой релиз незавершённого deploy; удаляется после успеха |
| `~/indexbudget-db/current/APP_REVISION` | SHA приложения |
| `~/indexbudget-db/current/CONFIG_REVISION` | SHA, из которого взят deploy/db |
| `~/indexbudget-db/releases/<hash>` | Compose и исходники образа точной версии |
| `~/indexbudget-db/backups/*.dump` | Резервные копии перед обновлениями |
| `~/indexbudget-db/app.git`, `snapshots/` | Служебные клоны и версии для updater |

```sh
tail -100 ~/indexbudget-db/update.log
docker ps --filter label=com.docker.compose.project=indexbudget-stand
df -h "$HOME"
du -sh ~/indexbudget-db/backups ~/indexbudget-db/releases
```

Для немедленного обновления:

```sh
timeout --kill-after=30s 20m bash ~/indexbudget-db/update.sh
```

При ошибке после up контейнер может уже быть новым, хотя current остался
прежним. Перед заменой контейнера сохраняется `pending-release`. Повтор того же
релиза разрешён; переход к другому релизу (включая возврат к A после ошибки B)
останавливается с `manual recovery required`. Даже без pending-маркера пропуск
обновления требует совпадения образа контейнера с current, состояния running/healthy
и ожидаемого volume.

Автоотката данных нет. Не удаляйте pending-маркер ради зелёного updater:
сначала приостановите cron обновления, проверьте фактический образ, журнал миграций
и состояние данных. После согласования способа восстановления оператор может
сохранить маркер отдельно и разрешить новый deploy; это не откатывает уже
применённые миграции. Сначала смотрите журнал и контейнеры;
восстанавливать dump только в отдельный тестовый экземпляр, затем планировать
переключение. Не выполнять pg_restore --clean поверх общей БД.

Для паузы обновлений через crontab -e закомментируйте только строку с маркером
`# indexbudget-database-update`. Это не останавливает БД и не затрагивает CLI.

## Проверки для агентов

`bash -n` для каждого shell-файла и `docker compose config --quiet` проверяют
только конфигурацию. Реальный integration test — `tests/persistence.sh`,
**только одноразовый Linux CI runner**: он использует имена ресурсов стенда.
Не запускать его на WSL коллеги. Не выдавать локальную syntax-проверку за
успешный deploy или подтверждённое сохранение реальных данных.

Persistence test добавляет новую SQL-миграцию после первого deploy и проверяет
изменение данных, точный список имён/checksum из файлов и отсутствие повторного
применения при новом запуске migration runner. Отдельно воспроизводится
A → ошибка проверки после up B → возврат конфигурации A: ожидается явный отказ,
сохранение current=A и pending=B. Smoke проверяет имя созданной гипотезы в дереве
плана; CI также проверяет отказ при `hypopg.enabled=off` без привязки к cost.
