# Автодеплой frontend из проверенного CLI

Frontend следует за **успешно установленным CLI-релизом**, а не за произвольным
HEAD Git. Существующий CLI updater собирает `main`, проверяет его и переключает
`~/indexbudget/current`. Пользовательский timer frontend проверяет этот указатель
через минуту после окончания предыдущего прохода. Для Python/HTML/CSS/JS не нужен
отдельный npm build или доступ GitHub Actions к SSH.

## Установка

На Linux нужны уже работающие user-systemd, Python 3.10+, Docker Compose v2 и
успешный CLI-деплой с JDK 25. Пакеты, sudo, Linger, WSL, firewall и чужие сервисы
установщик не настраивает. Перед изменением окружения прочитайте
[ограничения общего стенда](../db/README.md).

Из актуальной рабочей копии репозитория на сервере:

```sh
python3 deploy/frontend/install.py
```

Исходники самого updater устанавливаются отдельно от управляемых релизов.
При изменении `deploy/frontend/` повторите установку; обычные изменения frontend
подхватываются автоматически после обновления CLI. Новые исходники приложения
берутся из `current/source`, поэтому незакоммиченные изменения рабочей копии
или PR-ветки не попадают на стенд. CLI updater не ждёт GitHub Actions: проверки
`main`, включая `frontend-contract-and-smoke`, должны быть обязательными перед merge.

Перед первым релизом с библиотекой SQL-примеров нужно установить updater с
поддержкой bundle v2: он переносит `demo/scenarios/` из того же проверенного CLI
вместе с frontend. Прежний updater этот каталог не копирует. Версия bundle входит
в identity релиза, поэтому повторная установка создаёт полный каталог даже для
того же CLI SHA, если прежний updater уже подготовил неполный кандидат. Старые
CLI без `demo/scenarios/` остаются совместимыми. История в `shared/` при этом не
перекопируется и не очищается.

По умолчанию используются `~/indexbudget` для CLI, `~/indexbudget-frontend` для
frontend, порт HTTP 3000, loopback PostgreSQL 55433, Compose-проект
`indexbudget-frontend`. Настройки сохраняются в `config.json`; повторный install
сохраняет существующие значения, если не переданы переопределения. Доступные
параметры — `python3 deploy/frontend/install.py --help`.

## Что происходит при обновлении

1. Updater берёт `update.lock`, сначала восстанавливает незавершённое переключение
   из `pending.json`, затем один раз разрешает реальный путь успешного CLI-релиза.
2. Подготавливает отдельный каталог с frontend, `demo/scenarios/` (если он есть
   в исходном CLI), Docker build context, точным SHA
   и абсолютным путём к CLI. Из исходников не копируются `.local` и Python caches.
   Настройки портов/образа и версия состава bundle также входят в идентификатор релиза.
3. Запускает Python-тесты frontend, CLI `--help`/`--version`, Compose validation.
   Installer дополнительно проверяет units через `systemd-analyze --user verify`
   до остановки действующего сервиса.
   Если установлен Node.js, выполняет и браузерные unit-тесты; без Node.js этот
   шаг явно пропускается, Node-тесты остаются в CI. Образ БД получает тег по hash
   всего build context и собирается до остановки работающего сервиса.
4. Если CLI успел смениться во время подготовки, переключение откладывается.
   При неизменившемся SHA и успешном health процесс и контейнер не перезапускаются.
5. Записывает журнал восстановления, штатно останавливает frontend и ждёт его
   полной остановки. Только после этого меняет **собственную** временную БД frontend.
6. Атомарно переключает frontend `current`, запускает сервер и проверяет главную
   страницу, шаблоны и поля `database`/`cli` health. Если сервер сообщает
   `deployment_revision`, она должна совпадать с выбранным SHA.
7. После успеха сохраняет `deployed.json`. При ошибке возвращает предыдущие код,
   закреплённый CLI, настройки и образ. Отчёты не откатывает и не удаляет.
   Если откат не завершён, `pending.json` остаётся для следующего прохода.

Веб-процесс закрепляет один CLI и JDK на весь срок своей работы. Переключение
CLI `current` не меняет executable для уже принятых заданий. Новые серверные
версии закрывают приём заданий при SIGTERM (HTTP 503 для поздних POST), завершают
принятую очередь и только затем освобождают lock общего каталога данных.
`TimeoutStopSec=infinity` запрещает systemd убивать очередь по прежним 420 секундам.
Проход updater ограничен отдельно; его прерывание не удаляет журнал и не даёт
разрешения менять БД до полной остановки frontend.

Обновление — последовательное, с коротким перерывом обслуживания. Это не rolling
deployment: для рабочей demo-БД одновременно допускается только один исполнитель.

## Сохранение истории и первая миграция

Все `jobs/`, `reports/` и `server.lock` находятся в постоянном `shared/` вне
`current` и `releases`. Новый сервер использует `FRONTEND_DATA_DIR`; совместимость
с прежним `main` обеспечивает ссылка `source/frontend/.local` на тот же каталог.

При миграции ручной установки installer сначала проверяет кандидата, сохраняет
конфигурацию службы, останавливает её, затем переносит историю с проверкой
содержимого. Старый `.local` сохраняется как резервная копия и заменяется ссылкой
на shared: даже откат прежнего unit продолжает видеть новые отчёты. Два разных
непустых каталога автоматически не объединяются. Повторная установка не копирует
историю поверх уже перенесённой. Порт и Docker volume общей БД не затрагиваются.

Старый релиз без нового drain-контракта лучше переводить при пустой очереди;
миграция не заменяет его код неподтверждённой локальной версией. Его сохранённые
артефакты остаются совместимыми. Общая БД не используется для этой проверки.

## Диагностика и управление

```sh
systemctl --user status indexbudget-frontend.service --no-pager
systemctl --user list-timers indexbudget-frontend-update.timer
journalctl --user -u indexbudget-frontend-update.service -n 100 --no-pager
cat ~/indexbudget-frontend/deployed.json
cat ~/indexbudget/current/REVISION
curl --fail --silent http://127.0.0.1:3000/api/health
```

HTTP 200 без `database: true` и `cli: true` не считается успешной проверкой.
У старого сервера поле SHA отсутствует; закреплённые пути доступны в
`~/indexbudget-frontend/current/metadata.json`.

Немедленная проверка обновления:

```sh
systemctl --user start indexbudget-frontend-update.service
```

Приостановка новых автоматических обновлений:

```sh
systemctl --user stop indexbudget-frontend-update.timer
```

Это не останавливает уже выполняющийся update или frontend. Перед ручным
вмешательством дождитесь завершения updater; `pending.json` не удаляйте ради
повторного запуска. Для возобновления: `systemctl --user start indexbudget-frontend-update.timer`.

| Каталог / файл | Содержимое |
| --- | --- |
| `bin/` | Установленные updater, launcher и installer |
| `config.json` | Настройки установки без паролей |
| `current` | Ссылка на активный frontend-релиз |
| `releases/<sha>-<settings-hash>/` | Исходники и metadata с закреплённым CLI |
| `shared/` | Все задания и отчёты, общий lock |
| `pending.json` | Состояние незавершённого переключения |
| `deployed.json` | Последний подтверждённый релиз |

Релизы, образы и резервные копии автоматически не удаляются. При ручной очистке
нельзя удалять CLI-релиз, указанный в metadata работающего frontend или возможного
отката. После прерывания самого installer остаётся `install-pending.json`:
повторите `install.py`, чтобы восстановить прежнюю установку. Обычный timer
не продолжает обновление поверх незавершённой установки.
Хранение отчётов вне релиза защищает от переключения кода, но не заменяет
резервное копирование диска. [Семантика timer](https://www.freedesktop.org/software/systemd/man/latest/systemd.timer.html)
и его работа после выхода пользователя зависят от user-systemd/Linger; установщик
не меняет системные настройки машины.

## Проверки

```sh
python3 -m unittest discover -s deploy/frontend/tests -v
python3 -m unittest discover -s frontend/tests -v
```

Тесты deployment работают на временных каталогах с подставными systemctl/Docker:
переключение, отказ до остановки, rollback, восстановление после прерывания,
неизменность отчётов, миграция, повторная установка и закрепление CLI. Они не
меняют пользовательский systemd и не запускают общую БД. Process-тест frontend
проверяет настоящий SIGTERM и освобождение файлового lock после публикации очереди.

Проверено 12.11.2026: 27 тестов deployment и 26 unit/HTTP/process-тестов frontend
прошли локально; deployment-тесты также выполнены на Linux. На стенде установлены
сервис и timer, проверены автоматические проходы без лишнего перезапуска,
совпадение frontend/CLI SHA, перенос 15 отчётов (90 файлов с неизменными SHA-256)
и создание нового отчёта в shared через настоящий HTTP/CLI/PostgreSQL.
Восстановление прежнего сервиса после ошибки первоначальной установки также
проверено на стенде. Развёрнуто приложение текущего `main` — `c13e5d6`; локальная
реализация #101 и новый drain-контракт попадут в приложение после merge и успешной
сборки CLI. Сбой health при переходе A→B проверен подставными тестами, не намеренным
сбоем работающего приложения. Полный GitHub Actions workflow в этой проверке
не запускался. Настройка Linger не изменялась.
