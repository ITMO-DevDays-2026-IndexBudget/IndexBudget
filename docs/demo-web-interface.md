# Демонстрационный веб-интерфейс IndexBudget v0.3

Статус: **спецификация демонстрационного расширения**. Реализация и команды запуска
находятся в [frontend/README.md](../frontend/README.md). Локальный сервер по умолчанию
доступен на 127.0.0.1:8090; установка на стенд использует 0.0.0.0:3000.

Версия 0.2 ([#101](https://github.com/ITMO-DevDays-2026-IndexBudget/IndexBudget/issues/101))
заменяет редактируемые DDL/seed фиксированными серверными датасетами и ограничивает
ручные частоты SQL в веб-демо. Старые запросы с DDL/seed отклоняются;
workload CLI остаётся JSON v2 без новых ограничений.

Версия 0.3 подключает библиотеку SQL [#106](../demo/scenarios/README.md)
к экрану настройки и убирает отдельное действие «Проверить схему».
Формат workload v2 и существующий HTTP-конверт не меняются.

Предлагается один экран настройки, небольшая серверная обёртка над существующим
CLI и общая папка опубликованных отчётов. Анализ и генерация отчёта переиспользуют
существующие компоненты IndexBudget.

Это расширение границ [спецификации MVP v0.2](../IndexBudget-spec-v0.2.md):
HTTP/GUI остаются за рамками ядра MVP, а [архитектура](../ai/architecture.md)
описывает frontend как отдельную обёртку. Расширение не меняет требования
к анализатору и критерии приёмки
[основного плана #2](https://github.com/ITMO-DevDays-2026-IndexBudget/IndexBudget/issues/2)
и [MVP #21](https://github.com/ITMO-DevDays-2026-IndexBudget/IndexBudget/issues/21).

## 1. Назначение и пользовательский сценарий

Пользователь выбирает демо-базу, меняет запросы и параметры, нажимает «Анализ»
и автоматически переходит на готовый HTML-отчёт.

Предусмотрен один экран настройки, без регистрации, личных кабинетов и
разграничения доступа. Все опубликованные результаты доступны по прямым ссылкам.

Различаются два понятия:

- **Демо-шаблон** — база, данные, схема, существующие индексы и стартовые настройки.
- **Профиль нагрузки** — частоты общих SQL и вес сценария внутри одного анализа.
  По текущему контракту анализ содержит 1–3 профиля нагрузки.

## 2. Демо-шаблоны

Шаблоны хранятся в репозитории. Добавление шаблона не требует изменения интерфейса.

Каждый шаблон содержит:

- стабильный `id`, `version`, название и краткое описание демонстрируемого сценария;
- DDL таблиц, связей и существующих индексов;
- воспроизводимый скрипт заполнения данными;
- стартовый workload JSON v2: запросы, профили частот, бюджеты и остальные параметры;
- сведения для начального отображения схемы.

Доступны пять шаблонов:

1. «Чтение и запись» (`04-scenarios`, версия 1) объединяет прежний «Каталог записей»
   и библиотеку девяти SELECT/UPDATE/DELETE на `public.records` и `public.groups`
   из seed v1, с профилями «Обычный день» и «Пик». При первом открытии выбран этот
   шаблон. Стартовые запросы — `records_by_group`, `records_by_value` и
   `category_join`; остальные добавляются из библиотеки.
2. «Интернет-магазин» (`02-shop`, версия 3): 7 таблиц, 8 внешних ключей и 2 050 100
   строк. Покупатели, категории, товары, заказы, позиции, платежи и доставки.
   12 SELECT (10 с JOIN), три профиля: обычный день, распродажа и обработка
   доставок. При исходном бюджете 8 MiB вместе с B-tree выбирается BRIN по времени
   заказа для выборки за сутки. [Данные, частоты и бюджеты](../frontend/README.md#интернет-магазин).
3. Широкая таблица для демонстрации ограничения кандидатов.
4. Журнал из миллиона упорядоченных событий: диапазонный запрос и чтение всех строк.
   При 64 KiB выбирается BRIN, при 64 MiB доступен B-tree; полное чтение сохраняет
   отрицательный пример без пользы индекса. Датасет не содержит исходных индексов.
5. Поиск по строковому ключу v2: 200 тысяч 160-символьных ключей, точное равенство,
   последние 50 записей по `created_at DESC` и чтение всех строк. При 8 MiB
   выбирается hash по ключу, при 16 MiB — hash и B-tree по времени (`max_indexes = 2`).
   B-tree по длинному ключу не помещается. Все методы включены; равенство и
   сортировка сами по себе не порождают BRIN.

По возможности используются существующие демонстрационные данные и фикстуры
проекта. Все шаблоны явно задают `index_methods: ["btree", "brin", "hash"]` для одиночного
анализа и серий. При восстановлении старого черновика без поля добавляется тот же
список; явно заданные методы сохраняются. Сводка формы и скачиваемый JSON показывают
методы. Это default веб-демо; отсутствие поля в самостоятельном CLI-входе по-прежнему
означает только B-tree. Наличие метода не гарантирует его генерацию или выбор.

Выбор шаблона заполняет всю форму. Предусмотрено действие «Сбросить
изменения к шаблону».

DDL и заполнение берутся только из доверенных источников на сервере:
`frontend/templates/*.json` для прежних шаблонов и фиксированного seed v1 для
«Чтение и запись». SQL, частоты и пояснения библиотеки читаются из
`demo/scenarios/workload.json` и `catalog.json` без копирования SQL во frontend.
Изменение датасета требует изменения шаблона и его `version`;
старая версия запроса отклоняется с предложением загрузить шаблон заново.

## 3. Экран настройки

На широком экране слева располагаются настройки и редакторы, справа — закреплённая
при прокрутке сводка «Твоя нагрузка». Схема и существующие индексы находятся во
вкладке настроек. Кнопка «Показать диаграмму» открывает отдельное окно со статической
горизонтальной SVG-схемой выбранного датасета, масштабом 100% и прокруткой.
Окно закрывается кнопкой или Escape; фокус возвращается к кнопке открытия.
Сверху находится выбор шаблона, снизу — заметная кнопка «Анализ». Дополнительные
настройки сворачиваются.

При первом открытии интерфейс предлагает пошаговое обучение с подсветкой текущего
блока и затемнением остальных. В любой момент доступны «Пропустить» и Escape;
есть переходы назад и вперёд. Пропуск или завершение запоминается в браузере,
повторный запуск доступен через «Как это работает». Обучение не изменяет workload
и восстанавливает исходную вкладку. Для отдельных параметров используются короткие
подсказки по наведению, фокусу или нажатию.

Экран начинается с выбора базы, без промоблока и слогана. На карточке под описанием
указано только число таблиц. Объяснения частот, цели и глубины доступны через `?`,
без повторяющихся подписей под полями; у просмотра схемы нет дополнительной подсказки.
Нормальное подключение не занимает отдельную строку; недоступность окружения
по-прежнему показывается. Просмотр JSON не сопровождается поясняющим абзацем.

| Блок | Содержимое |
| --- | --- |
| Шаблон | Название, описание, выбор демо-базы |
| Запросы | Список 1–20 SQL, редактор выбранного запроса, добавление и удаление |
| Примеры | Названия, смысл, поддержанный синтаксис, SQL и частоты сценариев #106; «Добавить в нагрузку» |
| Нагрузка | Матрица «запрос × профиль» с частотами в вызовах/час, названия и веса 1–3 профилей |
| Бюджеты | Место в MiB, максимальное число новых индексов 0–5, включаемый бюджет записи |
| Запись | INSERT/UPDATE/DELETE в час для таблиц |
| Цель и глубина | `robust` / `mean`, `fast` / `normal` / `deep` |
| База | Просмотр фиксированной схемы, колонок и индексов |
| Дополнительно | Рейтинг кандидатов, ограничения ухудшения отдельных запросов, ручной набор индексов для сравнения |
| Вход анализа | Просмотр и скачивание сформированного workload JSON |

Для числовых параметров используются поля точного ввода; слайдеры добавляются
там, где они удобны. Нулевой бюджет и отключённый бюджет записи — разные состояния.

У весов показывается нормированная доля в процентах. Рядом размещается пояснение:
вес влияет на средний результат; маленький вес не исключает профиль из критерия
`robust`.

Ручные частоты SQL — целые **0–1 000 000 вызовов/час** включительно. Браузер и
сервер отклоняют дроби, отрицательные/избыточные и пустые значения, строки вместо
чисел и нечисловые значения. Число `1.0` допустимо: оно имеет целое значение.
В каждом из 1–3 профилей нужна положительная частота, каждый из 1–20 SQL должен
использоваться хотя бы в одном профиле. Частоты задают модель нагрузки: анализ
не выполняет указанное число запросов. Ограничение относится только к ручным
частотам SQL веб-демо, не к весам, CLI или частотам изменения строк, включая #108.

### Библиотека примеров

Вкладка «Примеры» и ссылка из редактора открывают девять поддержанных примеров
для «Чтение и запись». Название, назначение и подсказка синтаксиса поступают из
каталога #106; SQL и исходные частоты — из общего workload. INSERT и отрицательные
примеры каталога не добавляются в анализ. Для остальных датасетов вкладка показывает
их собственные стартовые SQL и исходные частоты из выбранного шаблона. Чужие SQL
не предлагаются и датасет не переключается при открытии вкладки.

«Добавить в нагрузку» сохраняет существующие SQL, частоты, бюджеты и профиль
изменения строк. Для `normal`/`peak` берутся соответствующие исходные частоты;
новые пользовательские профили получают исходную частоту обычного дня либо первого
профиля шаблона, если `normal` отсутствует; подстановка явно обозначается в UI.
Тот же SQL повторно не добавляется; коллизия ID с отредактированным запросом
разрешается новым ID без перезаписи запроса. Действует общий предел 20 SQL.
Guard конкретного примера переносится вместе с ним; guard и ручной набор исходного
шаблона сохраняются при формировании JSON. Удаление или переименование запроса
не оставляет guard со старым ID.

Если источник записи ручной и каждый SQL точно совпадает с опубликованным примером,
экспорт включает write rates только таблиц выбранных примеров. Значения остаются в форме и
возвращаются в JSON при повторном добавлении JOIN. Это не разбор пользовательского
SQL: для отредактированных или произвольных запросов таблицы не угадываются,
согласованность полного профиля записи проверяет CLI.
Наблюдаемые rates и provenance загруженного окна не фильтруются и не заменяются;
согласованность покрытия выбранных SQL проверяет общий контракт CLI.

## 4. Фиксированные датасеты и подготовка PostgreSQL

Диаграмма и анализ описывают один выбранный серверный датасет.

Предлагается одна отдельная рабочая demo-БД и последовательное выполнение запусков:

1. Проверить ID/версию и взять неизменяемый снимок доверенного серверного шаблона.
2. При изменении шаблона подготовить один эталон `indexbudget_frontend_seed`:
   создать таблицы и прежние индексы, отключить обычный autovacuum/autoanalyze на
   его таблицах, загрузить seed и выполнить `VACUUM (FREEZE, ANALYZE)`.
3. Закрыть подключения к эталону и клонировать его в новую `frontend_demo`.
   Повторный запуск того же шаблона не выполняет seed/ANALYZE заново.
4. Проверить отпечаток статистики и visibility map клона, затем запустить обычный анализ.

Сохраняется только один эталон: смена датасета заменяет его. Ключ подготовки включает
ID/версию, schema/seed, роль, версию процедуры, PostgreSQL и доступную версию HypoPG.
Маркер готовности записывается последним; после ошибки неполный эталон пересоздаётся.
Уровень БД не наследует ACL шаблона: запрет TEMP повторяется на рабочем клоне.
`schema.json.dataset_snapshot` содержит `preparation_key`, `statistics_hash` и
`preparation_version`; это добавочные поля, прежний каталог таблиц сохраняется.

Повторяемость относится к одному эталону. После его пересборки ANALYZE может получить
другую выборку. Отпечаток статистики позволяет отличить такие условия. Сбои и остановки
по времени также могут ограничить исследованный пул: таймауты не отключаются ради
совпадения рекомендаций. При неизменных условиях и одинаковой последовательности
оценок выбор детерминирован. Причина partial доступна по ссылке «Есть ограничения данных: подробности» в «Основе вывода».

Это подготовка демо, отдельная от `analyze`. Сам анализ по-прежнему не создаёт
реальные рекомендуемые индексы. Общая командная БД не используется как
перезаписываемая рабочая область. При реализации подготовки учитываются
[правила серверного окружения](../deploy/db/README.md).

Редакторов DDL/seed и соответствующего шага тура нет. Передача `schema_sql` или
`seed_sql` в любом из двух POST endpoints даёт HTTP 400 до создания job и обращения
к PostgreSQL, даже если значение совпадает с шаблоном. Запрет проверяется на сервере.

Диаграмма показывает таблицы, колонки, PK/FK и существующие индексы. Изначально
отображается схема доверенного шаблона.
Отдельного действия «Проверить схему» в интерфейсе нет. «Анализ» автоматически
подготавливает БД и читает её каталог; начальная схема не требует ручной проверки.
Совместимый endpoint `/api/schema-previews` остаётся для прежних клиентов и проверок.

Для «Чтение и запись» подготовка собственной demo-БД создаёт отдельную роль
`frontend_scenarios`: SELECT и только UPDATE(payload)/DELETE для records,
с `default_transaction_read_only=on`. Прежняя `frontend_reader` остаётся SELECT-only.
Роль выбирается серверным шаблоном, клиент её не задаёт. CLI анализирует исходные
UPDATE/DELETE через EXPLAIN без выполнения записи; planner cost не является
измерением фактического времени изменения строк. Общая БД и её роли не меняются.

## 5. Запуск и ожидание

При нажатии «Анализ»:

1. Интерфейс проверяет обязательные поля и формирует существующий workload JSON v2.
2. Сервер сохраняет неизменяемый снимок всех настроек запуска и выдаёт `run_id` — UUID.
3. Запуск попадает в общую очередь.
4. Единственный исполнитель подготавливает БД и вызывает CLI.
5. Интерфейс опрашивает состояние и после публикации результата открывает отчёт.

Во время ожидания показывается состояние: «В очереди», «Подготовка базы», «Анализ»,
«Публикация». Более подробная стадия показывается только если она доступна от CLI;
выдуманного процента выполнения нет.

Повторное нажатие во время отправки заблокировано. Перезагрузка страницы
восстанавливает наблюдение за запуском по `run_id`. Черновик формы сохраняется
в браузере. Из старого черновика можно восстановить только workload при совпадении
ID/версии: пользовательские DDL/seed и сохранённый каталог не восстанавливаются.
Исходный SQL не переписывается; сброс возвращает workload и схему выбранного шаблона.

Ошибки полей показываются рядом с полями. Ошибки подготовки или запуска — на этом
же экране, с сохранением введённых настроек.

## 6. Результаты и публикация

Каждый запуск получает отдельный каталог:

```text
reports/<run_id>/
  report.html
  report.json
  indexes.sql
  workload.json
  demo-config.json
```

`demo-config.json` сохраняет ID/версию и доверенный снимок схемы/наполнения запуска.
`run_id` веб-задания связан с `analysis_run_id` исходного отчёта CLI. Пользовательский
workload сохраняется отдельно без изменения SQL. Подключение остаётся на сервере.

Каталог автоматически доступен по адресу:

```text
/reports/<run_id>/report.html
```

Общая папка `/reports/` может иметь обычный статический список каталогов.
Отдельный экран истории не нужен. Ссылки постоянные, результаты разных запусков
не перезаписываются; автоматическое удаление в первой версии не требуется.

Каталог публикуется после завершения экспорта, чтобы пользователь не открывал
недописанный отчёт.

- `completed` → автоматический переход на отчёт.
- `partial` с опубликованным отчётом → такой же переход; причины неполноты
  остаются в отчёте.
- Ошибка без пригодного отчёта → сообщение на экране настройки.

## 7. Минимальная серверная часть

Предлагаются следующие операции:

| Метод и адрес | Назначение |
| --- | --- |
| `GET /api/templates` | Список демо-шаблонов; у `04-scenarios` также каталог `examples` и описание `example_profiles` |
| `GET /api/templates/{id}` | Содержимое шаблона |
| `POST /api/schema-previews` | Совместимость прежнего API: подготовить схему, вернуть данные диаграммы; кнопки в UI нет |
| `POST /api/runs` | Принять конфигурацию, вернуть `run_id` и адрес состояния |
| `GET /api/runs/{id}` | Вернуть состояние, ошибку или ссылку на отчёт |
| `GET /reports/...` | Раздать опубликованные файлы |

Подготовка схемы и анализ используют одну очередь, чтобы не менять рабочую БД
во время другого запуска. Достаточно одного процесса сервера, одного исполнителя
и файлового хранения состояний; отдельный брокер очередей не нужен.

Оба POST endpoints принимают конверт `{template_id, template_version, workload}`
с дополнительными полями `series` и `write_source` по контрактам
[серий бюджетов](demo-budget-series.md) и [источника записи](write-profile-ui.md).
Например, `template_id: "04-scenarios"`, `template_version: 1` и полный workload v2
из выбранного шаблона. Поля `schema_sql`/`seed_sql` запрещены, версия проверяется
до очереди. Присланные настройки подключения, пути и статусы не используются.
Формат входа самого
анализатора остаётся JSON v2; формулы и расчёты во фронтенд не переносятся.
Существующие контракты описаны в [docs/contracts.md](contracts.md), пример входа —
в [examples/workload-v2.json](../examples/workload-v2.json).

## 8. Критерии приёмки

- Каждый встроенный шаблон проходит путь от выбора до реального отчёта.
- Изменённые SQL, частоты, веса и бюджеты доходят до анализатора без потерь.
- Прямой POST с клиентскими DDL/seed не создаёт job и не меняет схему.
- Все четыре датасета восстанавливаются только из серверных источников; схема
  доступна для просмотра, её отдельной проверки в UI нет.
- Все девять примеров #106 доступны с названиями/пояснениями; добавление сохраняет
  отредактированный workload, согласованные частоты и guards, учитывает дубли и 20 SQL.
- Полный смешанный набор проходит настоящий анализ; строки и реальные индексы
  после SELECT/UPDATE/DELETE не меняются, прежняя SELECT-only роль не расширяется.
- Границы частот 0/1 000 000, дроби, отрицательные/избыточные значения, пустой
  профиль, неиспользуемый SQL и старый localStorage проверены в браузере и API.
- Два отправленных запуска выполняются последовательно и получают разные
  постоянные ссылки.
- `partial` открывает отчёт; ошибки оставляют доступной заполненную форму.
- Перезагрузка страницы не теряет текущий запуск.
- Отчёт и его JSON/SQL доступны без авторизации.

## A2 / #105: серии из той же формы

Необязательный series в POST /api/runs включает существующий analyze-series вместо
analyze. Dataset, очередь, подготовка и workload общие; меняется только один бюджет.
Выбор сохраняется, статусы точек берутся из CLI summary, единый report.html публикуется
с series.json и вложенными артефактами. Точный конверт, границы, восстановление job и
команды проверки — [demo-budget-series.md](demo-budget-series.md). Данные наблюдаемой
записи передаются через workload; пользовательский выбор observed-источника — #108.

## Наблюдаемый источник записи (#108)

В дополнительных параметрах доступен явный выбор manual/observed и загрузка рассчитанного workload.json #107. Переносятся только rates и origin; смена источника очищает профиль. API принимает необязательный `write_source`, старый ручной запрос совместим. Дробные строки/час не подчиняются лимиту ручных SQL calls/hour. Неполнота блокирует включённый лимит и write-серию без fallback. [Поля и проверки](write-profile-ui.md).
