# Контроль рейтинга shortlist #72

Это детерминированный синтетический эксперимент, а не измерение PostgreSQL. Он
проверяет влияние одного фактора — `frequency` или `baseline_cost` — на состав
shortlist и результат обычного поиска. Каталог, разрешённые SQL, размеры и полные
векторы стоимости заданы фикстурами; генерация, поиск, метрики и бюджетный
компаратор используют production-код.
Подстановка размеров следует стыку `AnalysisPipeline`: оценка каждого кандидата,
`assessBudget` и сохранение обоих размеров/write units. Refill в этом срезе нет.

Воспроизведение из корня репозитория в новый каталог:

```sh
./gradlew candidateRankingExperiments --args='--output-dir /tmp/indexbudget-candidate-ranking'
```

Сохранённый [summary.json](results/summary.json) содержит вход, все справочники
полных векторов, состав обоих shortlist, разницу списков, выбранные IDs,
planner costs, оба отношения, расходы, эффективные лимиты и фактические счётчики.
Контрольный `CandidateRankingExperimentsTest` проверяет заранее рассчитанные
отношения и побайтовое равенство двух повторов.

[workload-v2.json](results/workload-v2.json) — пример входа v2 с явным
`candidate_ranking: "baseline_cost"`. Его SQL относятся к синтетическим таблицам
`public.cheap` и `public.rare` с колонками `c1`–`c16`; для отдельного запуска
`analyze` эти таблицы должны существовать в выбранной demo/test БД. Сам
эксперимент получает их каталог из фикстуры и не создаёт таблицы.

Оба SQL фильтруют 16 колонок своей таблицы. После локального ограничения каждый
даёт 32 кандидата. `cheap` вызывается 1000 раз в час с baseline cost 1, `rare` —
один раз с cost 10 000. Профиль один, его вес 1; baseline cost профиля — 11 000.
У старого рейтинга выше `cheap`, у нового — `rare`.

Во всех четырёх запусках одинаковые SQL, профиль, baseline, бюджеты
1 000 000 байт / 100 write units в час / 2 индекса и все шесть лимитов `normal`.
Финальный пул содержит 16 допустимых кандидатов: 8 одиночных и 8 пар.
Выполняется 16 синтетических запросов размера по 100 байт каждый.
Между рейтингами меняется содержимое пула, сохраняя его мощность и арность.

| Контрольный случай | Рейтинг | Выбранный набор | Средний cost | M = R | Размер с запасом | Write units/ч |
| --- | --- | --- | ---: | ---: | ---: | ---: |
| Индекс помогает редкому SQL | `frequency` | 1 индекс на `cheap` | 10 100 | 0,918182 | 120 байт | 3 |
| Индекс помогает редкому SQL | `baseline_cost` | 1 индекс на `rare` | 1 500 | 0,136364 | 120 байт | 3 |
| Индекс не помогает редкому SQL | `frequency` | 1 индекс на `cheap` | 10 010 | 0,91 | 120 байт | 3 |
| Индекс не помогает редкому SQL | `baseline_cost` | Пустой набор | 11 000 | 1 | 0 байт | 0 |

Полные векторы заданы для пустого набора, наборов только на `cheap`, только на
`rare` и на обеих таблицах. Сочетание имеет собственный вектор, а не сумму
одиночных выгод. В первом случае стоимость редкого SQL падает до 500, во втором
остаётся 10 000. Высокая исходная стоимость сама по себе не доказывает
пригодность кандидата.

В `normal` ограниченный repair сохраняет `partial` с `REPAIR_LIMIT`. В первых
трёх строках поиск выполняет 60 полных синтетических оценок, в последней — 45,
включая baseline; в каждом случае использует 28 новых repair-попыток. Реальных
EXPLAIN и подключений к PostgreSQL нет. Время зафиксировано тестовыми часами,
поэтому длительность не используется для сравнения производительности.

Результаты показывают и улучшение, и ухудшение нового отбора. По этому контролю
default остаётся `frequency`, `baseline_cost` — экспериментальный режим. Для
выбора нового default нужны отдельные наблюдения на репрезентативных нагрузках
PostgreSQL; синтетические planner costs не являются измеренным временем
выполнения SQL.
