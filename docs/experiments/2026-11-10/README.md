## Planner-эксперименты

[Исходный вход](source-workload.json), [заранее зафиксированный holdout](sensitivity-workload.json),
[сводка](summary.json), отдельные `*-input.json` и `*/report.json` сохраняют
точные частоты, бюджеты, hash/run ID, версии, планы и costs. `*/indexes.sql`
содержит выбранный набор соответствующего запуска. Файлы HTML остаются в
локальном `reports/issue21-verified`; они проверены тем же экспортом и тестами.

Пул один: три одиночных кандидата (`records.group_id`, `records.value`,
`groups.category`), `max_indexes=1`. Нормальные лимиты каждого анализа:
90/60 секунд, 2000 EXPLAIN, 28 repair attempts. Baseline costs у раздельных
сравниваемых запусков совпали. Holdout не участвовал в выборе.

| Запуск | Выбранный индекс | M | R | EXPLAIN | Время анализа, ms |
| --- | --- | ---: | ---: | ---: | ---: |
| robust + repair | records(group_id) | 0.212902968 | 0.970956193 | 12 | 4883 |
| mean + repair | records(group_id) | 0.212902968 | 0.970956193 | 12 | 2163 |
| robust + greedy | records(group_id) | 0.212902968 | 0.970956193 | 12 | 2110 |

| write disabled, профиль отсутствует | records(group_id) | 0.212902968 | 0.970956193 | 12 | 1568 |

Все девять запусков `completed`. Robust и mean выбрали одинаковый набор;
repair не улучшил greedy. При `max_indexes=1` и трёх кандидатах все допустимые
одиночные наборы уже проверены greedy, поэтому данный эксперимент не показывает
преимущества repair. Его взаимодействия 0→2 и 1→2 проверены отдельно scripted
evaluator тестами, не выдаются за эффект на этой БД.

Ограничения места и записи менялись по отдельности и оба изменили рекомендацию.
Write rates различаются: records — 4100, groups — 41 changes/hour. Для выбранного
records(group_id): HypoPG estimate 4 644 864 bytes, бюджет 5 573 837 bytes,
write proxy 4100 units/hour. Для groups(category): 16 384 / 19 661 bytes и 41 unit/hour.
При отсутствии write profile units остаются `null`.

## Физические измерения

[physical.json](physical.json) содержит все raw планы `EXPLAIN (ANALYZE, BUFFERS,
FORMAT JSON)`, размеры, порядок, sample IDs и сводки. Два раунда:
baseline → robust-repair → mean-repair → robust-greedy, затем обратный порядок.
В каждом варианте/раунде два прогрева и семь измерений каждого SQL: 14 измеряемых
samples на ячейку. Финальные наборы совпадают; различие их времени отражает шум.

| SQL | Baseline median, ms | records(group_id), robust-repair median, ms | Диапазон выбранного набора, ms |
| --- | ---: | ---: | ---: |
| by_group | 58.2615 | 0.9275 | 0.598–1.848 |
| by_value | 57.7470 | 60.1715 | 50.414–77.486 |
| groups_by_category | 0.3510 | 0.4085 | 0.304–0.987 |

Фактический размер нового индекса — 1 384 448 bytes, он отличается от HypoPG
estimate и бюджетного значения. Исходные два реальных индекса сохранились;
после benchmark число физических индексов снова равно двум. Обычный анализ
не создавал физические индексы. Тестовые контейнеры после проверки удалены.

Это чтение с прогретым кешем и instrumentation overhead в локальной VM;
фоновая нагрузка хоста не изолирована. Замеры не устанавливают SLA или общий
процент ускорения, особенно для неизменившихся SQL. Write benchmark не запускался;
выводов о реальной скорости записи нет. Будущий write benchmark требует
восстановления свежего состояния между вариантами для сильных выводов.

[sha256.json](sha256.json) содержит контрольные суммы сохранённых файлов.
SQL-копии в Git имеют один завершающий перевод строки; DDL и заголовки сохранены.
Перед сохранением проверено отсутствие DSN и временных паролей в артефактах.
