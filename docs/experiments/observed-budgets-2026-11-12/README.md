# Наблюдаемая запись и бюджеты (#109)

Эксперимент использует [общий сценарий #106](../../../demo/scenarios/README.md),
настоящий коллектор табличных снимков #102 и `WriteProfileCalculator` из #107.
Обычный production pipeline получает workload v2 с `source: observed`; алгоритм,
формулы, caps и публичные форматы не меняются. Сравниваются сохранённые
`best_robust` / `best_mean` **одного запуска**, а не результаты двух поисков.

Сохранённый реальный прогон **12.11.2026** подтвердил смену набора по обеим осям
между ненулевыми бюджетами. Во всех девяти запусках robust/mean совпали,
цена устойчивости — **0 planner-cost units** в исследованных пулах. Main и четыре
точки серий завершились `partial / REPAIR_LIMIT`; остальные четыре точки — completed.
Это результат ограниченного поиска, не доказательство оптимальности.

[Машинная сводка](results/summary.json), [исходные снимки](results/write-before.json),
[второй снимок](results/write-after.json), [эффективный вход](results/workload.json),
[полные отчёты JSON/HTML/SQL](results/reports.zip), [SHA-256 файлов](results/manifest.json).
Архив содержит неизменённые файлы `main/`, `storage/`, `write/`; распаковка в одну
папку сохраняет локальные ссылки серий. Откройте `main/report.html`,
`storage/report.html` и `write/report.html` без сервера и сети.

`manifest.source_files_revision` указывает коммит исходников первоначального runner;
SHA-256 в `source_files` сверяются с файлами этого коммита, а не текущей ветки.
Исправления проверок после ревью не перезаписывают исторические результаты.

## Воспроизведение

Нужны Docker, Bash и JDK 25, как для общего сценария:

```sh
bash demo/check-scenarios.sh --observed-budgets
```

Команда создаёт собственный контейнер PostgreSQL 16.15 / HypoPG 1.4.2, загружает
точный seed v1 и отдельную read-only роль DML-анализа. В конце удаляет только свой
контейнер и образ. Общая БД, `.env` и её volume не используются.

Артефакты каждого запуска находятся в новом `build/observed-budget-runs-*/`;
`build/observed-budget-latest.txt` указывает последний успешно проверенный запуск.
CI выполняет ту же команду и публикует каталог как `observed-budget-experiment`.
Неудачный прогон сохраняет уже полученные файлы, но не обновляет указатель успеха.

## Что наблюдается

1. Сохраняется первый реальный `pg_table_statistics_snapshot` всей БД.
2. Администратор одноразовой БД исполняет девять SQL сценария по одному разу,
   затем [фиксированные дополнительные записи](../../../demo/scenarios/observe-writes.sql).
   Семь SELECT действительно читают строки; UPDATE меняет 17 строк records,
   DELETE удаляет две. Дополнительно вставляются 10 records; для groups выполняются
   INSERT одной строки, UPDATE трёх и DELETE одной.
3. После окна не короче пяти секунд сохраняется второй снимок. При задержке
   публикации counters допускается ещё до пяти секунд ожидания; точное время берётся
   из снимков, не подменяется круглым числом. Проверяются приращения
   records `(10,17,2)` и groups `(1,3,1)` по INSERT/UPDATE/DELETE.
4. #107 вычисляет `Δrows × 3600 / Δseconds`. В workload переходят rates ровно двух
   участвующих таблиц; полные исходные снимки всех таблиц остаются в артефактах.
   HOT сохраняется как историческая диагностика и не вычитается из proxy.
5. Владелец один раз выполняет ANALYZE records/groups **после окна**, до всех
   анализов. Далее main и обе серии работают с одним состоянием данных. Сохраняются
   fingerprints строк, реальные индексы, настройки planner и версии. После всех
   анализов проверяется неизменность данных/индексов и закрытие сессий.

Это реальные наблюдения **искусственно заданного короткого burst** на seed v1.
Они не характеризуют промышленный поток. Два профиля `normal`/`peak`, их частоты
SELECT/DML и веса 9/1 сохраняются из #106: они заданы, а не измерены этим окном.
Нельзя называть их наблюдаемыми частотами запросов или выводить rates из calls.
Единый write profile учитывается один раз для каждого ключа/INCLUDE-колонки индекса.
Проверка отдельно подтверждает, что умножение calls на 100 не меняет write budget,
а те же численные rates с `source: manual` дают те же расходы и допустимость.

Окно сохранённого прогона: **14:46:48.640953–14:46:53.790408 UTC**, 5.149455 секунды.
Изменения rows и единицы бюджета не округляются при расчёте; здесь числа сокращены
только для чтения.

| Таблица | INSERT rows/час | UPDATE rows/час | DELETE rows/час | Всего rows/час |
| --- | ---: | ---: | ---: | ---: |
| records | 6991.031090 | 11884.752852 | 1398.206218 | 20273.990160 |
| groups | 699.103109 | 2097.309327 | 699.103109 | 3495.515545 |

Повторное наблюдение даст немного другую длительность и rates. Точные сохранённые
входы доступны отдельно, а новый запуск сохраняет собственные timestamps, результаты
и настройки. Seed детерминирован; ANALYZE и выбор планов не обещаются побайтово
одинаковыми между окружениями.

## Независимые оси бюджетов

Обозначим `r` максимальную сумму INSERT+UPDATE+DELETE rates одной таблицы в окне.
Бюджеты записи выбираются до поиска по наблюдению, без подбора по выигрышу:

| Запуск | Меняется | Зафиксировано |
| --- | --- | --- |
| main | ничего | 64 MiB, `ceil(20r)+1` write units/час |
| storage, 4 точки | 0 / 4 / 16 / 64 MiB | `ceil(20r)+1` write units/час |
| write, 4 точки | 0 / `ceil(1.1r)` / `ceil(3.1r)` / `ceil(20r)+1` | 1 GiB |

`20r` покрывает пять индексов по максимум четыре key+INCLUDE-колонки каждый.
Для каждой серии дополнительно проверяется, что сумма пяти самых дорогих
кандидатов **по другой оси** меньше фиксированного бюджета. Таким образом,
плато storage нельзя объяснить скрытым write cap и наоборот.
SQL, заданные профили, guard, ручной набор, `normal`, `frequency`, B-tree и
`max_indexes=5` остаются неизменными. Внутри каждой серии пул готовится один раз;
условия каждой точки сравниваются с подготовкой. Между сериями отдельные подготовки,
кэши и запуски; общий исследованный набор комбинаций между точками не обещается.

Нулевые точки проверяют baseline-only. Критерий приёмки дополнительно требует
изменения рекомендации **между ненулевыми точками** по каждой оси и выбора 2+
индексов в последней точке. Увеличение бюджета само по себе не обещает монотонности
эвристического поиска или глобального оптимума.

## Полученные решения

Сокращения используются только в таблицах ниже; полные стабильные IDs и DDL есть
в JSON/SQL. Все индексы — B-tree, направления ASC, если не указано иначе.

| Обозначение (начало ID) | Определение |
| --- | --- |
| G (`5d770c03`) | groups(category) |
| A (`d2e9c413`) | records(group_id) |
| B (`6b42a625`) | records(value) |
| T (`03dfa4d6`) | records(created_at) |
| C (`36da7cec`) | records(group_id, value) INCLUDE(id) |
| D (`760a8e60`) | records(value) INCLUDE(id, payload) |
| E (`13506513`) | records(group_id, value) |
| F (`1f493139`) | records(group_id, created_at) |
| H (`2c5f7c85`) | records(created_at) INCLUDE(id, value) |

**Место:** write budget фиксирован на 405481 units/час. Даже пять самых дорогих
по записи кандидатов пула требуют только 283835.862242 units/час: запись не является
причиной отсечения. Размеры в таблице — оценки с запасом 1.2, не физические размеры.

| MiB | Набор обоих incumbents | M | R | Худший профиль | Bytes с запасом | Write units/час | Статус |
| ---: | --- | ---: | ---: | --- | ---: | ---: | --- |
| 0 | ∅ | 1 | 1 | оба | 0 | 0 | completed |
| 4 | G | 0.999986 | 0.999987 | normal | 19661 | 3495.516 | completed |
| 16 | C, B | 0.046435 | 0.116303 | peak | 15325594 | 81095.961 | partial |
| 64 | C, D | 0.035121 | 0.039546 | peak | 63750145 | 121643.941 | partial |

При 4 MiB даже простой records(value) требует 5573837 bytes и не помещается.
Улучшение от G всего около 0.00144% среднего planner cost — практически плато,
которое здесь объясняется местом. При 16 MiB доступны C+B; замена B на покрывающий
D поднимает расходы набора до 63750145 bytes и становится допустимой только в
следующей точке. Число индексов остаётся два, но состав меняется. Большой payload
в INCLUDE оплачивается и местом, и write proxy.

**Запись:** storage budget фиксирован на 1 GiB. Верхняя граница места для любых
пяти кандидатов данного пула — 93005416 bytes, значительно меньше лимита.

| Write budget/час | Набор обоих incumbents | M | R | Худший профиль | Bytes с запасом | Write units/час | Статус |
| ---: | --- | ---: | ---: | --- | ---: | ---: | --- |
| 0 | ∅ | 1 | 1 | оба | 0 | 0 | completed |
| 22302 | A | 0.255253 | 0.879987 | peak | 5573837 | 20273.990 | completed |
| 62850 | T, B, A | 0.105961 | 0.106339 | normal | 18107598 | 60821.970 | partial |
| 405481 | E, F, H, C, D | 0.006740 | 0.010963 | peak | 90213583 | 263561.872 | partial |

В первой ненулевой точке хватает на одну колонку records, но две требуют
40547.980320 units/час и не проходят. Следующая точка допускает три одиночных
индекса (60821.970480 units/час), но набор C+D требует шесть колонок ×
20273.990160 = 121643.940961 units/час и ещё недопустим. При максимальном бюджете
есть пять индексов; срабатывают `MAX_INDEXES` и `REPAIR_LIMIT`, а не нехватка места
или записи. Это не утверждение, что шестой индекс бесполезен или пять глобально оптимальны.

**Main, 64 MiB:** C+D — одновременно best_robust и best_mean. Общий `C_mean`
меняется с 24599474.56 до 863948.025; M=0.035120589, R=0.039545975.
Для normal стоимость 24554074.8 → 850056.85, отношение 0.034619787;
для peak 25008072.4 → 988968.6, отношение 0.039545975. Цена устойчивости 0:
в этом исследованном пуле дополнительной платы за robust не обнаружено.

Ручной `(group_id, created_at DESC)` + `(value)` допустим и полностью оценён:
M=0.132676491, R=0.132750483, худший normal; 13929677 budgeted bytes и
60821.970480 write units/час. Он дешевле C+D по обоим ресурсам, но хуже по обоим
критериям. Это отдельная оценка идеи пользователя, не третий incumbent.

Массовый `all_records` сохранил **7152.1 → 7152.1** во всех выбранных наборах и у
обоих incumbents; ручной набор тоже не дал пользы этому SQL. Guard важного
`records_by_group` в main: **6713.61 → 11.53**, отношение 0.001717407 ≤ 1.05.
Отказов по guard **0** во всех запусках: ограничение проверено и соблюдено,
предотвращённая регрессия на этих данных не наблюдалась.

Main выполнил 594 EXPLAIN / 66 полных оценок / 13 cache hits / 28 repair attempts
за 22180 ms. Для storage по точкам EXPLAIN: 18 / 207 / 549 / 594;
для write: 18 / 180 / 477 / 855. В эти счётчики точек входит отдельная оценка
ручного набора; затраты общей подготовки серии сохранены в её `series.json`.
Не следует называть все оценки счётчика исключительно автоматическим пулом.
Все partial здесь имеют `REPAIR_LIMIT`, полного перебора не было. Наблюдаемые
baseline/plans/catalog/версии внутри обеих серий совпали с подготовкой.

## Артефакты и проверка

В каталоге запуска сохраняются `source-workload.json`, точный `seed.sql`, его SHA-256,
`catalog.json`, `observe-writes.sql`, `write-before.json`, `write-after.json`,
`settings.json`, эффективные `workload.json` / `write-workload.json`, оба файла серий
и `summary.json`. `main/`, `storage/`, `write/` содержат настоящие JSON/HTML/SQL,
включая планы, оба incumbents, ручной набор, guards и причины остановки.

Сводка проецирует готовые метрики из production-отчёта без другой реализации M/R
или цены устойчивости. Для каждого запуска есть состав наборов, costs, метрики
обоих профилей, худший профиль, расходы, цена устойчивости, counters и причины
остановки. Интеграционная проверка сопоставляет run ID/hash трёх файлов;
IDs, определения и DDL в JSON и полный список SQL-команд проверяются независимо
по сохранённым `result.selected` / `report.candidates`, включая пустой набор.
IDs в сводках серий сверяются с результатом каждой точки. Дополнительно проверяются
полный вектор девяти SQL и допустимость обоих incumbents.

Runner разделён на подготовку фикстуры, наблюдение, подготовку входов/БД, main,
серии, проверку неизменности и сохранение доказательств. Обе оси описаны `SeriesCase`.
При ошибке чтения версий фабрика закрывает ещё не переданную pipeline сессию;
ошибка закрытия сохраняется как suppressed у исходного исключения. Освобождение
после анализа подтверждается закрытием фактических connections; пустой HypoPG
нового соединения не используется как доказательство очистки предыдущего.

Регрессионные проверки обвязки без БД:

```sh
./gradlew test --tests 'ru.itmo.indexbudget.experiments.ObservedBudgetVerificationTest'
```

Они проверяют сбой/дедлайн чтения версий и ошибку close, согласованную подмену или
добавление индекса в JSON/SQL, неверное определение при прежнем ID, постороннюю
SQL-команду при пустом наборе и подмену IDs точки серии.

Массовый фильтр `all_records` должен сохранить baseline cost для обоих incumbents.
Ручной `(group_id, created_at DESC)` + `(value)` оценивается отдельно, не добавляется
к автоматическому пулу; в main проверяется его успешная оценка и допустимость.
Guard `records_by_group ≤ 1.05 × baseline` проверяется для выбранного набора;
сводка также сохраняет число реальных отказов по guard. Отсутствие отказов нельзя
выдавать за демонстрацию предотвращённой регрессии.

Режим normal может закончиться `partial / REPAIR_LIMIT`. Проверка принимает только
completed или такой пригодный partial с полными результатами; ошибки SQL/БД,
дедлайны и неполные векторы не считаются успешным экспериментом.

## Границы выводов

Planner cost — не миллисекунды; DML cost описывает поиск/подготовку строк, не цену
их физической записи. Write units — proxy, не WAL/TPS. Здесь не строятся реальные
рекомендованные индексы и не измеряется их влияние на runtime. Смешанный benchmark
[#110](https://github.com/ITMO-DevDays-2026-IndexBudget/IndexBudget/issues/110)
самостоятельно фиксирует рекомендацию и восстанавливает состояние для повторов.

Качество greedy/repair и малого полного перебора рассматривается отдельно в
[эксперименте #104](../search-comparison-2026-11-12/README.md). Его результаты не
приписываются различию robust/mean здесь. Совпадение criteria и отсутствие пользы
сохраняются; синтетическая разница не добавляется для украшения результата.
Обнаружение адресных сбросов статистики PostgreSQL 16 остаётся best-effort;
проверка счётчиков не превращает короткое окно в прогноз будущей нагрузки.
