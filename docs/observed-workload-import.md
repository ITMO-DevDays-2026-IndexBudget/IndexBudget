# Импорт наблюдаемой нагрузки (#67)

Маршрут: read-only снимки #65 → частоты #66 → `import-workload` → обычный `analyze`.
Импорт не исполняет наблюдаемые SQL, не вызывает EXPLAIN/HypoPG, не создаёт индексы,
не сбрасывает статистику и не меняет общую БД. Для проверки типов и имён требуется
подключение `INDEXBUDGET_DATABASE_URL` к наблюдаемой БД; database OID должен совпасть.
Source UUID остаётся утверждением оператора: совпадение UUID/OID не доказывает, что
подключение относится к тому же серверу. URL/пароли не сохраняются.

```text
indexbudget stats pair --source-id <stable UUID> --output-dir captures --interval-seconds 60
indexbudget import-workload --config import-config.json --output-dir imported
indexbudget analyze --workload imported/workload.json --output-dir analysis
```

Оба снимка должны содержать начальный counter выбранной записи: сначала выполните
запрос хотя бы один раз, затем снимайте окно. Новый queryid без начального наблюдения
не получает искусственный ноль. Минута здесь пример, длительность окна задаёт оператор.

## Файлы входа

Конфигурация v1: `kind: pg_stat_statements_import_config`, `windows` (1–3 записи
`id, weight, before, after`), путь `examples`, обычные `constraints` и необязательные
`objective`, `table_write_rates`, `analysis_mode`, `candidate_ranking`.
Пути снимков и примеров отсчитываются от каталога конфигурации. Повтор той же пары
снимков отклоняется расчётчиком #66; разные профили не суммируются в общий трафик.
Окончательная проверка бюджетов/write profile выполняется существующими input/resolution
валидаторами. Ручной JSON v2 по-прежнему принимается без provenance.

Файл примеров v1: `kind: pg_stat_statements_examples`, `examples` со следующими полями:

```json
{
  "key": {"source_id": "d0d60c19-eb9d-42ee-9e01-935560eb7e20", "dbid": 42,
          "userid": 10, "queryid": "1", "toplevel": true},
  "sql": "SELECT id FROM public.records WHERE group_id = 1",
  "search_path": ["pg_catalog", "public"]
}
```

Полный ключ обязателен; `queryid` — десятичная строка signed bigint. Дубликаты ключей
и примеры, не принадлежащие окнам, — ошибка. Один пример на запись, без случайной
генерации литералов. **Контекст задаётся явно для каждой записи, в том числе для
SQL без параметров**: первый срез требует пример и search_path для всех импортируемых
SELECT. Path начинается с `pg_catalog`; это поддерживаемый консервативный контекст,
а не восстановление прежних настроек роли. Если фактический исходный контекст
отличался, оператор не должен выдавать такой пример за его подтверждение.
Не допускаются `$user`, временные схемы, NUL, пустые/повторные имена; максимум 16 схем.
Импорт устанавливает только transaction-local path своей выделенной read-only сессии,
закрывает её и не меняет параметры чужих соединений. Схемы таблиц фиксируются в SQL
результата; алиасы и правила неоднозначных имён проверяет существующий resolver.
Роль источника не выдаётся за роль текущего анализа; права/RLS и изменившийся каталог
могут менять поведение. Повторный analyze заново разрешает SQL по текущему каталогу.

## Соответствие SQL

Оба SQL разбираются JSqlParser. Только параметрические листья исходного AST могут
заменяться поддержанными скалярными литералами, NULL или явными casts. Повтор одного
номера параметра требует одинакового представительного значения. Условия AND/OR,
число IN-элементов, BETWEEN, JOIN, проекция, сортировка, LIMIT и явные casts должны
сохраниться. После привязки весь исходный AST проходит существующий whitelist;
канонические SQL обоих AST должны точно совпасть после разрешения схем таблиц.
Сопоставление консервативно: различия алиасов, написания токенов и избыточных скобок
могут отклоняться даже при эквивалентной семантике. Regex не заменяет AST-проверку.

Типы/операторы примера разрешаются существующим SQL-анализатором. Статистика PG16
**не содержит исходных bind types или значений**: проверка доказывает структуру и
пригодность конкретного примера, но не восстанавливает типы prepared statement.
`parameter_type_scope` явно помечает это ограничение. Generic/custom plan и разные
распределения параметров не моделируются.

## Частоты, отбор и охват

Для общего списка пригодны только полные matched/stable observations **во всех** окнах.
Подтверждённый ноль допустим, UNKNOWN/отсутствующая запись — исключение, не ноль.
Политика частичных снимков/сбросов/eviction остаётся [политикой #66](statistics-frequencies.md):
сохранившаяся стабильная пара может быть пригодна в partial-окне, но окно не объявляется
полным. Недоступные тексты, смена шаблона, DML/неподдержанный AST, неподходящий пример
и пропущенный контекст получают отдельные причины. Листы SQL не отбрасываются молча.

Берутся только `toplevel=true`: nested-наблюдения исключаются, чтобы один вызов и
его вложенные SQL не учитывались как независимая нагрузка. Разные userid при одинаковом
queryid — разные записи и разные стабильные `obs_<sha256 полного ключа>` query IDs.
Число одинаковых SQL-текстов не используется для объединения разных контекстов.

Каждый профиль в порядке конфигурации даёт очередь пригодных записей по убыванию
calls/hour, при равенстве — `(source_id, dbid, userid, queryid, toplevel)`.
Round-robin выбирает следующий ещё не выбранный ключ из каждой очереди, максимум 20.
Вес профиля не отменяет его участие. После отбора у каждого профиля остаётся полный
вектор всех query IDs и хотя бы одна положительная частота; иначе импорт неуспешен.
Ограничение 20 не меняет снимки и не умножает статистику по числу профилей.

Знаменатель охвата **для каждого окна отдельно** — все доступные matched/stable
top-level observations с известными counters, включая неподдержанные или исключённые
по лимиту SQL. UNKNOWN, недоступные идентичности и nested-записи не входят в этот
знаменатель. Их неполнота видна в манифесте. Это не доля всей нагрузки сервера.
Охват calls считается по calls/hour внутри окна; охват времени — по историческому
Δtotal_exec_time этого же окна. При нулевом знаменателе доля `null`.
Исторические миллисекунды не становятся planner cost, SLA или прогнозом ускорения;
calls не становятся частотами INSERT/UPDATE/DELETE строк.

## Выход, воспроизведение и пределы

Успех (exit 0): новый каталог с валидным `workload.json` v2 и `import-manifest.json`
v1 (`kind: pg_stat_statements_import`). Манифест перечисляет каждый известный ключ,
выбор/исключение с причиной, состояния/частоты по окнам, периоды, snapshots/source IDs,
правило отбора, охват, хэши шаблонов/примеров и ограничения. Исходные неподдержанные
SQL не копируются в диагностику; для выбранного SQL сохраняется явный признак
репрезентативной подстановки. Если пригодных SQL нет или профиль стал пустым,
exit 2 сохраняет только failed-манифест; успешного workload нет. Повреждённые входы,
несовместимые источники и ошибки каталога не публикуют частичный workload.

В `workload.json` используется существующее поле `provenance` v1 #68, без отдельного
конкурирующего DTO: source UUID, окна/охват и происхождение каждого SQL-примера.
В `selection_rule` после идентификатора алгоритма записаны `import_manifest=import-manifest.json`
и SHA-256 точных байтов файла (`sha256=...`). Окна #68 содержат фактические Δcalls, не
calls/hour; доля внутри одного окна эквивалентна частотной. Богатые периоды/идентичности,
SQL hashes и причины исключения остаются во внешнем манифесте. При повторном чтении
валидатор #68 проверяет версию, coverage и полное покрытие query/profile IDs.
Внешний файл не ищется/не загружается автоматически; хэш связывает его с workload
для проверки оператором. Соответствие SQL hashes при ручном редактировании не проверяется
автоматически контрактом #68; происхождение не является криптографической подписью.
Изменили SQL вручную — обновите provenance через импорт либо удалите весь блок и
считайте ввод ручным. Существующий input hash охватывает provenance вместе с workload.

Общий `AnalysisReport.workloadProvenance` сохраняет блок; JSON v3 экспортирует `workload_provenance`,
HTML использует существующее представление #68. Формулы, планы и выбранные
индексы не пересчитываются. Новые сводки/вёрстка #68/#69 не требуются для этого маршрута.

Конфигурация/примеры ≤1 MiB каждый, снимок ≤64 MiB и своих объявленных лимитов,
≤1000 примеров, ≤30000 различных полных ключей, каждый SQL ≤64 KiB. Превышение —
явная ошибка без скрытого top-N. Общий импорт ограничен RunContext (90 секунд по
умолчанию), ожидание окна уже завершено до его запуска. Файлы публикуются атомарным
переименованием private staging-каталога; выходной каталог должен быть новым.

[Синтетический полный комплект](../examples/observed-import/import-config.json)
имеет фиктивный database OID 42, проверяется unit-тестом и не подключается к вашему
стенду. Для реального запуска используйте собственные сохранённые снимки/ключи и
осознанно заданные примеры, не подменяйте их OID ради прохождения проверки.
`bash demo/check-import.sh` создаёт одноразовую PostgreSQL 16/HypoPG с pg_stat_statements
и проверяет реальную цепочку снимки → CLI импорт → обычный analyze → HTML/JSON/SQL.
Тест требует Docker; его фактический результат смотрите в CI `postgres-observed-import`.
