# Источник записи и смысл DML в демо и отчётах (#108)

Демо принимает **готовый** профиль из `workload.json` v2, созданного
[`import-workload` с `table_write_window`](table-write-profile.md). Сырые snapshots
не являются входом формы. Расчёт rates остаётся в CLI; frontend не вычисляет дельты,
write units, метрики или выбранные наборы.

В дополнительных параметрах выберите «Наблюдаемый профиль из CLI» и загрузите файл.
Копируются только `table_write_rates` и `table_write_rates_origin`. SQL, частоты вызовов,
веса и бюджеты формы сохраняются. Один явно выбранный write-window обслуживает все
профили и все бюджетные точки. Исторические rates применяются к фиксированному
датасету демо с указанными именами таблиц: это не наблюдение текущего запуска и не
проверка идентичности исходной БД и восстановленного датасета. Покрытие таблиц SQL
проверяет существующий CLI после resolution.

Дробные rates показываются без округления и недоступны для ручного редактирования.
Лимит формы 0–1 000 000 целых вызовов/час относится только к SQL-частотам. Источник,
окно, длительность, полнота, причины ограничений и строки/час сохраняются в черновике,
HTTP job, workload и отчёте. Загрузка не исполняет SQL из файла.

Смена источника явно очищает текущий профиль. Ручные значения, нули или выключенный
лимит автоматически не подставляются. При неполном наблюдении можно изучить его
диагностику, но включённый лимит (в том числе ноль) и write-серия требуют полного
профиля. Исправление: получить совместимое полное окно и повторить импорт либо явно
выбрать ручной источник и заполнить строки/час. Неизвестное значение, ноль и
отключённый лимит имеют разный смысл.

## Demo API

`POST /api/runs` и `/api/schema-previews` сохраняют прежний запрос
`{template_id, template_version, workload, series?}`. Дополнительный `write_source`
равен `manual` или `observed`; отсутствие сохраняет совместимость и определяет источник
по полям workload. Несовпадение выбора с содержимым, смешанные источники, неизвестные
rates и неполное наблюдение при активном лимите отклоняются до очереди. Полная проверка
workload остаётся в CLI. Наблюдаемый выбор без загруженного файла — ошибка, даже при
отключённом лимите. В UI выбор сохраняется отдельно и восстанавливается после reload.

## Экспорт

Обычный `report.json` сохраняет уже существующие поля `table_write_rates`,
`table_write_rates_origin`, `queries[].statement_kind` и `cost_interpretation`.
`series.json.settings` дополнительно содержит `table_write_rates_origin` того же
формата и поля `statement_kind` / `cost_interpretation` в `queries[]`. Тип берётся
из сохранённого результата AST-валидации общей подготовки; до неё он неизвестен.
Это добавочные поля: версии B-tree-only report v3 / series v1 и method-aware
report v4 / series v2 не меняются.

HTML показывает происхождение записи, таблицу строк/час, ограничения сбросов PG16
и отдельный смысл write proxy. В сводке смешанной нагрузки и карточках UPDATE/DELETE
написано: planner cost оценивает поиск и подготовку строк, фактическая модификация
таблицы и сопровождение индексов не включены. Это не прогноз полного ускорения DML,
миллисекунд, TPS или WAL. Историческое время и физические измерения не смешиваются
с cost или write proxy. SQL-вызовы не добавляются к табличным rates.

Обычный HTML, единый `report.html` серии и `series.html` используют сохранённые данные
без нового EXPLAIN. Старые сводки без новых полей открываются: неизвестные тип/полнота
обозначаются явно и не восстанавливаются эвристикой из текста SQL. Разные provenance
окон не объединяются лишь потому, что rates совпали. Выбранные наборы и формулы не меняются.

## Проверки

```sh
python3 -m unittest discover -s frontend/tests -v
node --test frontend/tests/test_app.js
./gradlew test --tests 'ru.itmo.indexbudget.report.*' --tests '*BudgetSeries*' reportPreview installDist
# Нужен PostgreSQL 16 + HypoPG image из demo/postgres/Dockerfile:
docker build -t indexbudget-import-test:local -f demo/postgres/Dockerfile .
python3 frontend/tests/observed-smoke.py
```

Сквозной скрипт создаёт и удаляет только свой контейнер со случайным loopback-портом.
Получает настоящие снимки #102 и pg_stat_statements, вызывает импорт #107, передаёт
rates через demo API в одиночный анализ и write-серию и сравнивает сохранённые rates,
окно, выбранные costs, индексы и расходы с прямым CLI. Все файлы остаются в
`build/write-profile-verification/<UUID>/`. Общая demo-БД не используется.
`--serve` после проверок оставляет временный API для браузерной проверки; остановка
Ctrl+C закрывает сервер и удаляет контейнер.

Синтетические предпросмотры: `observed-write`, `incomplete-write`,
`series-observed-write`. Они показывают смешанный SELECT/UPDATE и малые дроби;
это не измерения БД. Браузерная проверка `frontend/tests/observed-browser.cjs`
принимает `FRONTEND_TEST_URL` и `OBSERVED_WORKLOAD` (путь к реальному результату импорта).
Она проверяет загрузку, незавершённое окно, одиночный запуск, write-серию и ширины
1440/390/320 px. Права DML на целевой БД по-прежнему настраиваются отдельно
[по контракту DML](dml-analysis.md); эта задача не расширяет SELECT-only роль демо.

[Синтетический workload SELECT/UPDATE/DELETE](../examples/workload-v2-observed-write.json) показывает формат и дробные rates; это не сохранённое наблюдение настоящей БД.

### Фактическая проверка 12.11.2026

Локально выполнены Kotlin-проверки отчётов/серий и новых контрактов, 39 Python/HTTP
и 16 JavaScript-тестов. В общем Kotlin-прогоне два существующих теста, требующих
отдельных переменных подключения, были пропущены; новая сквозная проверка выполнена
отдельно на PostgreSQL 16.15 + HypoPG 1.4.2 без пропусков.

Реальный профиль из `table-stats` → `import-workload` прошёл demo API и прямой CLI
для одиночного анализа и write-серии. Сравнивались точные rates, origin и весь
`selected` (IDs, costs, plans, метрики и расходы). Нулевые бюджетные точки сохранили
пустой набор, ограниченный repair дал честный partial. Браузер прошёл загрузку,
ошибки неполного/отсутствующего профиля, reload, оба вида запуска и офлайн-открытие
на 1440/390/320 px; скриншоты просмотрены. Дополнительно проверены 21 вариант обычного
отчёта и 9 серий на 1440/900/390/320 px, включая старые сохранённые примеры, работу
без JavaScript, сортировку, каталоги и переносимость.

SELECT/UPDATE/DELETE, экранирование и сохранение DML-метаданных при partial проверены
на сохранённых моделях/синтетических фикстурах. Новый сквозной demo-прогон использует
SELECT-only роль; тесты исполнения/прав DML из #103 здесь не перезапускались.
Обновлённый workflow GitHub Actions и деплой на общий стенд в этой проверке не запускались.
