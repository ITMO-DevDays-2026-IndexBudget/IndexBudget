# Серия бюджетов через CLI (#75)

`analyze-series` последовательно сравнивает 3–5 значений одного бюджета на одном подготовленном пуле кандидатов. Это отдельный вход серии v1 поверх существующего workload v2; отчёт каждой точки сохраняет формат v3. Команда использует только HypoPG и EXPLAIN без ANALYZE, не создаёт реальные индексы и не выполняет рекомендации.

## Запуск и вход

```sh
./gradlew installDist
build/install/indexbudget/bin/indexbudget analyze-series \
  --workload demo/workload-poc.json \
  --series examples/budget-series-storage.json \
  --output-dir reports/budget-series-001 \
  --analysis-mode normal \
  --candidate-ranking frequency \
  --series-timeout-seconds 600
```

Подключение задаётся через `INDEXBUDGET_DATABASE_URL`. `.env` автоматически не читается. Каталог вывода должен быть новым или пустым; прежние артефакты не перезаписываются. `analyze-series --help` не требует БД.

[Пример storage-серии](../examples/budget-series-storage.json):

```json
{
  "schema_version": 1,
  "budget": "storage_budget_bytes",
  "values": [0, 16777216, 33554432, 67108864],
  "timeout_seconds": 600
}
```

Для [write-серии](../examples/budget-series-write.json) поле `budget` равно `write_budget_units_per_hour`; нужен полный `table_write_rates` общего workload. Значение выбранного бюджета в исходном workload заменяется для подготовки и каждой точки, второй бюджет и `max_indexes` сохраняются.

| Поле | Правило |
| --- | --- |
| `schema_version` | Обязательное целое `1`; это версия запроса серии, не workload. |
| `budget` | Обязательная строка `storage_budget_bytes` или `write_budget_units_per_hour`. |
| `values` | Обязательный массив из 3–5 различных неотрицательных чисел. Порядок запуска совпадает с порядком массива; сортировка не выполняется. |
| Storage-значение | Целое JSON-число от 0 до `9223372036854775807`; дробная запись и строка отклоняются. |
| Write-значение | Конечное число, представимое как Double; после преобразования значения должны оставаться различными. Положительный underflow даёт `NUMERIC_ERROR`, а не нулевой бюджет. |
| `timeout_seconds` | Необязательное целое от 1 до 86400 секунд, default `600`; явный `null` отклоняется. |

Вход серии ограничен 64 KiB UTF-8. Неизвестные поля, повторные ключи, неверные типы и содержимое после JSON отклоняются. `--series-timeout-seconds` переопределяет валидный JSON timeout; `--analysis-mode` и `--candidate-ranking` переопределяют соответствующие валидные поля workload. Повторные флаги и ошибочный JSON не скрываются CLI-переопределением. Без переопределений действуют настройки workload и прежние defaults `normal`/`frequency`.

## Пул, ресурсы и остановка

Общая подготовка выполняется при максимальном значении выбранного бюджета. Она читает каталог, разрешает SQL, получает полный baseline, генерирует кандидатов и использует обычный refill: до 16 допустимых кандидатов, резерв до 48, до 32 size-вызовов с учётом ошибок. [Правила подготовки](candidate-refill.md) и [режимы анализа](analysis-modes.md) сохраняются.

Затем каждая точка заново проходит существующий pipeline с собственными RunContext, JDBC-сессией, baseline, кэшем поиска и набором ошибок. Точка проверяет допустимость кандидатов и комбинаций по своему бюджету, сохраняя исходный пул; size-вызовы, генерация и refill не повторяются. Подготовленные оценки размера не обновляются между точками. Метрики и бюджеты считает общая доменная модель, каждый набор оценивается целиком.

Общий deadline отсчитывается с начала команды и ограничивает подготовку и все точки. У подготовки и каждой точки одновременно действуют свои пределы выбранного режима; сетевые и SQL-таймауты ограничиваются оставшимся временем. Достижение локального лимита одной точки не означает автоматическую остановку всей серии: следующая может начаться, пока общий deadline не исчерпан и серия не отменена. Ошибка точки также не переносится в следующую. При общей остановке новые точки не начинаются; уже опубликованные результаты сохраняются. После отмены/таймаута экспортируется сохранённый результат без нового EXPLAIN. Сессии освобождаются во всех путях завершения. При завершении JVM сохранение ещё не опубликованной точки не гарантируется.

В stderr подготовка помечена `scope=preparation`, точки — `scope=point ordinal=N`; поэтому сброс счётчиков при новом запуске виден явно. Для каждой начатой подготовки/точки выводятся все шесть эффективных лимитов, пять фактических счётчиков, статус и причины остановки. Сохранённые ошибки `partial` печатаются отдельными строками `CODE: JSON` с той же областью и номером точки. Пропущенные точки сообщают причину без вымышленных счётчиков и лимитов.

## Каталоги и машинная сводка v1

```text
budget-series-001/
  .indexbudget-series-owner
  series.json
  point-01/
    report.json
    report.html
    indexes.sql
  point-02/
    ...
```

`point-01` соответствует первому значению `values`, далее до `point-05`. Каталог создаётся только для начатой точки. Обычные JSON/HTML/SQL одной точки описывают её run ID, исходный hash workload, эффективный бюджет и один выбранный набор. При failed `indexes.sql` не публикуется; при ошибке экспорта ссылки на неполученные артефакты отсутствуют. Пропущенная точка не получает вымышленных метрик или файлов.

Перед первой публикацией серия атомарно занимает каталог файлом `.indexbudget-series-owner` (`CREATE_NEW`). Этот служебный файл сохраняет ID владельца и остаётся в каталоге; конкурирующая серия получает `EXPORT_FAILED` и не заменяет чужую сводку или точки. Повторная проверка пустоты сама по себе не используется как механизм владения.

`series.json` публикуется до подготовки, обновляется после каждой точки и в конце серии. Обновлять его может только владелец каталога; замена сводки атомарна через временный файл. Опубликованные каталоги точек при этом сохраняются. Пока серия работает, `status` равен `running`; этот снимок не является форматом возобновления. До начала точки её запись имеет `status: "skipped"`, который заменяется при получении результата.

| Поле сводки | Смысл |
| --- | --- |
| `schema_version`, `spec_version` | `1` и `"0.2"`; независимая версия сводки. |
| `series_id` | ID команды серии; отличается от ID подготовки и точек. |
| `status` | `running` во время работы; итоговый `completed`, `partial` или `failed`. |
| `duration_millis`, `timeout_seconds` | Фактическая длительность команды и эффективный общий лимит в секундах. |
| `budget`, `values` | Изменяемый бюджет и исходный порядок его значений. |
| `comparison_scope` | Всегда `fixed_candidate_pool`: общий исходный пул, без обещания одинакового пула оценённых комбинаций. |
| `source` | Hash исходного workload, имя переменной подключения и границы наблюдения условий. |
| `settings` | Эффективные objective, режим, рейтинг; исходные constraints, общие SQL/профили и write profile. Изменяемый бюджет точки задаёт её `budget_value`; максимум подготовки — `preparation.maximum_budgets`. |
| `preparation` | ID подготовки, её отдельные counters и шесть `limits`, максимальные бюджеты, наблюдённые условия, финальные IDs/определения/DDL/оценки кандидатов и ошибка подготовки, если она возникла. |
| `points` | Все запрошенные точки, включая не начатые. |

`source.workload_input_hash` — тот же SHA-256 исходного workload, что в отчётах точек: defaults, подстановка бюджета и CLI-переопределения его не меняют. `workload_source` равен `manual_json` либо `pg_stat_statements`; `workload_source_id` сохраняет UUID источника из provenance либо `null` для ручного входа. Полные окна/охват provenance сохраняются в отчётах точек. `source.connection_configuration` содержит только имя `INDEXBUDGET_DATABASE_URL`; адрес и пароль туда не записываются. `source.observation_scope` указывает, что сравниваются каталог, baseline, планы и версии без snapshot isolation всей БД.

У `preparation.candidates` сохраняются `id`, физические `schema`/`table`, упорядоченные `keys` с направлением и порядком NULL, `included_columns`, `ddl`, `estimated_bytes`, `budgeted_bytes`, `write_units_per_hour`. Это один общий пул; полный список отклонённых/нерассмотренных кандидатов и причины подготовки доступны в обычной диагностике точек.

| Поле точки | Смысл |
| --- | --- |
| `ordinal`, `budget_value` | Порядковый номер с 1 и значение выбранного бюджета. |
| `status`, `run_id` | Состояние точки и ID начатого run; у не начатой ID равен `null`. |
| `conditions_match`, `condition_changes`, `conditions` | Результат сравнения наблюдённых условий с подготовкой, список изменившихся частей и наблюдённые факты. `null` означает, что сравнение недоступно. |
| `selected_index_ids` | IDs выбранного набора; `[]` — пригодный пустой набор, `null` — пригодного результата нет. Определения берутся из общего пула. |
| `metrics` | Готовые средние/худшие отношения, baseline/selected costs, профильные метрики и `budget_usage`; `null`, если пригодного результата нет. |
| `statistics` | Counters этого run: EXPLAIN/evaluation/repair attempts, completed evaluations, cache hits. Работа подготовки учитывается отдельно. |
| `limits` | Шесть эффективных пределов режима в тех же полях/единицах, что диагностика обычного отчёта. Доступны и при ошибке экспорта начатой точки. |
| `stop_reasons` | Сохранённые причины остановки обычного поиска. |
| `errors` | Все сохранённые ошибки результата, в том числе partial; `null` у не начатой точки. |
| `artifacts` | Карта `report.json`/`report.html`/`indexes.sql` → относительный путь от каталога серии; отсутствующий файл не получает ссылку. |
| `error` | Безопасная ошибка точки/пропуска либо `null`: `code`, `message`, `query_id`, `profile_id`, `details`. |

`metrics` содержит `baseline_mean_cost`, `mean_cost`, `mean_ratio`, `worst_ratio`, `budget_usage` и `profiles`. Расходы — `estimated_bytes`, `budgeted_bytes`, `write_units_per_hour`, `index_count`, `size_safety_factor`. Профильные строки содержат ID, нормированный вес, baseline/selected cost, абсолютный и процентный выигрыш, отношение. Неизвестные расходы и отношения при нулевом baseline остаются `null`; ноль ими не заменяется. Это значения доменной модели из результата точки, без отдельного пересчёта в сводке.

## Статусы и сопоставимость

| Итог | Правило и код выхода |
| --- | --- |
| `completed` | Все точки completed и наблюдаемые условия каждой совпали с подготовкой; exit `0`. |
| `partial` | Есть хотя бы один пригодный выбранный набор, но есть partial/failed/skipped, несовпавшие или недоступные условия; exit `3`. Пригодный пустой набор тоже считается результатом. |
| `failed` | Подготовка не удалась либо ни у одной точки нет пригодного результата; exit `1`, либо `2` для ошибки входа при подготовке. |

Невалидный или неподдержанный вход даёт exit `2`; численная ошибка — `1`. Ошибка публикации общей сводки даёт `EXPORT_FAILED`, exit `1`; ранее опубликованные точки сохраняются. Ошибка экспорта отдельной точки отмечает её как failed с `EXPORT_FAILED`; серия продолжает следующие точки и возвращает partial/exit `3`, если есть пригодный результат другой точки, иначе failed/exit `1`. Состояния точек — `completed`, `partial`, `failed`, `skipped`. Ошибка подготовки сохраняется в `preparation.error`; точки остаются skipped с причиной. Общая отмена/таймаут также сохраняются в `error` не начатых точек.

Условия включают `catalog_hash`, полный `baseline_costs` по query ID, `baseline_plans_hash`, доступные `postgres_version`/`hypopg_version` и безопасный `source_fingerprint`. Fingerprint источника — SHA-256 фактов открытой сессии: фактические `inet_server_addr()`/`inet_server_port()`, `current_database()`, `SESSION_USER` и `CURRENT_USER`. Они читаются вместе с версиями через ограниченный общим deadline SQL; getter возвращает только сохранённое значение без нового SQL. Список хостов JDBC URL, пароль и backend PID в fingerprint не входят; DSN и исходные реквизиты не публикуются. Если фактический сетевой адрес или порт недоступен, включая Unix socket, fingerprint остаётся `null`, а сопоставимость источника неизвестна. Fingerprints служат для сравнения внутри серии и не доказывают неизменность кластера за одним адресом, не заменяют снимок каталога или дамп БД.

`condition_changes` различает каталог, baseline costs, baseline plans, версии, источник и недоступные условия. При обнаруженном изменении `conditions_match: false`; если получить условия не удалось либо fingerprint хотя бы одной из сравниваемых сессий неизвестен (`source_unavailable`), значение — `null` при отсутствии другого обнаруженного изменения. Такой результат сохраняется, но нельзя объяснять наблюдаемый эффект только бюджетом.

Совпадение сравниваемых фактов означает лишь отсутствие обнаруженного изменения. Сводка не фиксирует все данные, распределения PostgreSQL-статистики, настройки планировщика или внешнюю нагрузку и не обеспечивает snapshot isolation серии. Каждый поиск исследует свой ограниченный набор комбинаций; больший бюджет не обещает меньшего cost, глобального оптимума или изменения рекомендации. Совпавшие наборы должны сравниваться как совпавшие. Planner cost — условные единицы планировщика; длительность анализа, оценка размера и write proxy имеют отдельный смысл и не доказывают реальное ускорение SQL.

Сводный автономный HTML серии относится к #76. В #75 входят машинная сводка и существующий автономный HTML каждой точки.
