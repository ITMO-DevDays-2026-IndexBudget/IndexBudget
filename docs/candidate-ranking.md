# Рейтинги shortlist (#72)

Необязательное поле входа JSON v2 `candidate_ranking` и флаг `--candidate-ranking` выбирают `frequency` или `baseline_cost`. Без поля и флага сохраняется прежний `frequency`. Флаг имеет приоритет над валидным JSON; исходный файл проверяется целиком. Значения регистрозависимы, `null`, неизвестная строка, иной тип и повтор флага недопустимы.

```sh
build/install/indexbudget/bin/indexbudget analyze \
  --workload demo/workload-poc.json \
  --output-dir reports/ranking-frequency \
  --candidate-ranking frequency

build/install/indexbudget/bin/indexbudget analyze \
  --workload demo/workload-poc.json \
  --output-dir reports/ranking-baseline-cost \
  --candidate-ranking baseline_cost
```

CLI-переопределение не меняет SHA-256 исходного JSON. Эффективная стратегия записывается в `candidate_ranking` отчёта v3 и видна в CLI/HTML, включая partial/failed и раннее завершение до shortlist. Старые отчёты v2/v3 без этого поля используют неявный `frequency`; требования v3 к INCLUDE сохраняются.

## Формула и порядок

Для профиля `s` нормированная частота `u_s(q) = f_s(q) / Σ_q f_s(q)`. `Q(c)` — множество различных query IDs, породивших канонический кандидат `c`:

```text
frequency:     rating_s(c) = Σ_{q ∈ Q(c)} u_s(q)
baseline_cost: rating_s(c) = Σ_{q ∈ Q(c)} u_s(q) × cost(q, empty)
```

Например, частый дешёвый SQL с `f = 1000`, baseline cost `1` и редкий дорогой SQL с `f = 1`, cost `10000` имеют общий знаменатель `1001`. `frequency` ставит первым кандидата частого SQL: `1000/1001 > 1/1001`. `baseline_cost` ставит первым кандидата дорогого SQL: `10000/1001 > 1000/1001`. Это возможность повлиять на shortlist; польза конкретного индекса определяется оценкой полного набора.

Новый рейтинг сравнивает точные десятичные числители `Σ f_s(q) × cost(q, empty)` через `BigDecimal.valueOf` исходных конечных `Double`. Общий положительный знаменатель одинаков для всех кандидатов одной сценарной очереди, поэтому его исключение сохраняет порядок и равенства. Произведения и суммы рейтинга не переводятся обратно в `Double`: overflow/underflow произведения не меняет порядок и положительную поддержку. Округление метрик наборов до 9 знаков к рейтингу не применяется.

Существующие проверки `normalizedFrequencies` сохраняются при обеих стратегиях: переполнение суммы частот или превращение положительного нормированного значения в ноль даёт `NUMERIC_ERROR`. Точный числитель не расширяет допустимый вход. Проверки расходов/метрик в общей domain-реализации также сохраняются.

После рейтинга действует прежний tie-break: для двухключевых кандидатов лучший приоритет группы генерации, затем стабильный candidate ID; для одноключевых — ID. INCLUDE не увеличивает число ключей. После канонизации каждое query ID учитывается один раз, в том числе при нескольких OR-ветвях. Порядок коллекций и OID HypoPG не задают результат.

Веса профилей не участвуют в рейтинге или квотах. При любом допустимом положительном относительном весе сценарий сохраняет ход во внешнем round-robin. Умножение всех score одной очереди на одну положительную константу не меняло бы её порядок. Нормированные веса для среднего критерия по-прежнему рассчитывает общий модуль domain.

## Baseline, ноль и ошибки

`AnalysisPipeline` передаёт `CandidateGenerator.generate(resolved, catalog, context, baseline)` сохранённый полный `EvaluationResult` пустого набора вместе с разрешённым workload. Дополнительного EXPLAIN и повторного расчёта профильных `B_s`, `M` или `R` нет. Совместимый overload по умолчанию вызывает прежний трёхаргументный метод. `ProfileAwareCandidateGenerator` реализует оба; `baseline_cost` требует baseline с точными query IDs и пустыми candidate IDs. Неверный/отсутствующий baseline даёт явную ошибку контракта.

Нулевая частота или cost даёт нулевой вклад; выбираются только кандидаты с положительным рейтингом. Нулевой рейтинг во всех сценариях сохраняется как `ZERO_BASELINE_COST_SUPPORT`, отдельно от `GLOBAL_CANDIDATE_LIMIT`. Профиль с нулевой стоимостью всех используемых SQL не даёт положительной очереди, другие профили продолжают участвовать. Если все профильные baseline нулевые, pipeline возвращает пустой набор до генерации по прежнему правилу. Отрицательные и нечисловые costs/частоты не заменяются нулём.

## Область изменения и сравнение

Рейтинг применяется после локальной генерации, канонизации и объединения происхождения. Сохраняются ограничения 16 колонок до пар / 32 локальных / 16 глобальных, локальная квота INCLUDE, внешний round-robin по profile ID и чередование очередей арности ключей. После отбора HypoPG получает только финальный shortlist; бюджетный отказ не возвращает вытесненный кандидат.

Не меняются полная оценка каждого набора, robust/mean, бюджетный компаратор, greedy/fixed-`S0` repair и оба incumbents из общего исследованного пула. Planner cost не является временем; рейтинг не обещает оптимум или ускорение.

Сравнение стратегий фиксирует SQL, каталог/baseline, бюджеты, objective, финальное число кандидатов и лимиты поиска. Состав shortlist — результат сравнения. Сохраняются оба shortlist, выбранные наборы, метрики профилей/среднего/худшего случая, estimated/budgeted bytes, write units, size/EXPLAIN/evaluation counters и длительность. Objective и глубина отдельными факторами не меняются.

[Контрольный синтетический эксперимент](experiments/candidate-ranking-2026-11-11/README.md) использует заданные полные cost vectors, показывает улучшение и ухудшение. Это проверка реализации, а не измерение PostgreSQL. `baseline_cost` остаётся экспериментальным, `frequency` — default до убедительных результатов на реальной нагрузке.

`CandidateRankingHypopgIntegrationTest` входит в `bash demo/check-hypopg.sh` и проверяет оба рейтинга на одноразовой PostgreSQL/HypoPG: 18 SQL, по 16 кандидатов, один baseline, 17 полных оценок и 306 EXPLAIN на запуск. Экспорт использует сохранённые планы; сессии очищаются, физические индексы не создаются. Без `INDEXBUDGET_HYPOPG_TEST_URL` этот тест пропускается.

Нормативные правила — в [спецификации §5](../IndexBudget-spec-v0.2.md#5-ограниченная-генерация-кандидатов-и-широкие-таблицы), стык — в [контрактах генератора](contracts.md#полный-shortlist-кандидатов-12), выходные поля — в [формате отчёта v3](report-v3.md).
