# Пополнение shortlist после бюджетного отсева (#70)

[Спецификация §5](../IndexBudget-spec-v0.2.md#5-ограниченная-генерация-кандидатов-и-широкие-таблицы)
задаёт ограниченную подготовку кандидатов. Генератор оставляет до 32 локальных кандидатов после
ограничения колонок до 16, канонизации и удаления реальных дублей. Из объединённого пула один
round-robin профилей с чередованием singles/pairs формирует начальные 16 и резерв до 48.
Резерв продолжает очереди с сохранённых позиций и не содержит повторных candidate IDs.

Подготовка рассматривает эту очередь до получения 16 индивидуально допустимых кандидатов.
Доступный write budget проверяется до дорогого размера; storage проверяется после получения
оценки с запасом. Вся подготовка ограничена 32 вызовами `estimateSize`, включая ошибки,
и общим deadline команды/поиска. Потеря сессии,
отмена и deadline прекращают подготовку; локальная ошибка гипотезы допускает продолжение
только после успешной очистки. Неизвестные оценки остаются `null`.

## Числовой пример

Это синтетический пример с явно заданными размерами и costs, а не замеры PostgreSQL.
Один SQL `q1` имеет baseline cost 100. Заданы `max_indexes = 1`, `storage_budget_bytes = 120`,
write budget отключён. Очередь содержит 18 различных кандидатов в фиксированном порядке:

| Кандидаты | `estimated_bytes` | `budgeted_bytes` | Индивидуально допустимы | Cost `q1` |
| --- | --- | --- | --- | --- |
| `c01`–`c14` | 1000 | 1200 | Нет | Не оценивается |
| `c15` | 50 | 60 | Да | 80 |
| `c16` | 50 | 60 | Да | 70 |
| `c17` | 50 | 60 | Да | 40 |
| `c18` | 50 | 60 | Да | 50 |

Без пополнения поиск получил бы только `c15` и `c16` из первых 16. С резервом он получает
`c15`–`c18`; при единственном SQL и одном слоте выбран `c17`. Repair не добавляет новых
оценок: пары не помещаются по числу индексов, одиночные замены уже оценены greedy.

| Наблюдение | Только первые 16 | С пополнением |
| --- | --- | --- |
| Size-вызовы | 16 | 18 |
| Допустимые кандидаты для поиска | 2 | 4 |
| Выбранный набор | `c16` | `c17` |
| Selected planner cost | 70 | 40 |
| Полные оценки / EXPLAIN с baseline | 3 | 5 |

Здесь резерв улучшает planner cost за два дополнительных запроса размера и два EXPLAIN.
На других данных рекомендация может остаться прежней; улучшение качества, реального времени
запроса или SLA не гарантируется. Size-вызов может включать несколько SQL адаптера; счётчик
`size_attempts` считает вызовы порта, а не JDBC statements. Planner cost и реальное время различаются.

Фрагмент `candidate_diagnostics` для этого примера:

```json
{
  "initial_shortlisted_candidates": 16,
  "reserve_candidates": 2,
  "reserve_candidate_limit": 48,
  "max_size_attempts": 32,
  "shortlisted_candidates": 16,
  "preparation": {
    "examined_candidates": 18,
    "size_attempts": 18,
    "budget_rejected_candidates": 14,
    "candidate_errors": 0,
    "refilled_candidates": 2,
    "final_shortlisted_candidates": 4,
    "stop_reason": "RESERVE_EXHAUSTED"
  }
}
```

`shortlisted_candidates` сохраняет прежний смысл начального отбора и остаётся равным 16;
итог 4 записывается в новом `preparation.final_shortlisted_candidates`. Это аддитивное
расширение схемы v3 без изменения смысла прежних полей. В `candidates` остаются все 18 записей
с размерами и причинами бюджетного отказа.
Исчерпание очереди означает, что новые кандидаты больше не рассматриваются; это не утверждение
о полном пространстве индексов. При остановке по 32 size-вызовам причина — `SIZE_LIMIT` с warning;
поиск может завершиться `completed` на подготовленной части. При deadline отчёт сохраняет
полный baseline, уже измеренные записи и неизвестный остаток, а запуск возвращает `partial`.

## Фиксированный пул для серии бюджетов

`CandidatePreparation.prepareFixedPool` подготавливает один пул до 16 при наибольших бюджетах
серии. `selectFixedPool` разрешает лишь меньшие storage/write budgets при неизменном остальном
входе и фильтрует этот пул в памяти. `AnalysisPipeline.runWithFixedPool` проверяет вход через
`selectFixedPool` до открытия JDBC и до раннего завершения по нулевому бюджету: несовместимость
даёт `INVALID_INPUT` без сессии. Затем для каждой точки используются отдельные RunContext,
сессия и кэш оценки наборов; размеры и refill не повторяются. При нулевом бюджете полный
`reportBatch` фиксированного пула сохраняется.
Например, уменьшение storage budget в этом примере до 59 исключит все четыре кандидата,
а увеличение списка за счёт нового обхода резерва не допускается.

`analyze-series` использует этот стык для общей подготовки, общего deadline и последовательных
независимых точек; [вход и сводка серии](budget-series.md). Сводка отмечает обнаруженное
изменение baseline/каталога относительно подготовки. Условия внешней БД не объявляются
неизменными только на основании использования фиксированного пула.

При нулевом бюджете точки статистика `preparation` остаётся общей (18 size-вызовов,
14 отказов, 4 подготовленных кандидата). Область обозначена как
`preparation_scope: "common_pool"`. Отдельная диагностика точки:

```json
{
  "fixed_pool_selection": {
    "pool_candidates": 4,
    "admissible_candidates": 0,
    "budget_rejected_candidates": 4,
    "size_attempts": 0
  }
}
```

HTML подписывает эти таблицы как «Общая подготовка пула» и «Текущая бюджетная точка»;
shortlist текущей точки равен 0. Для обычного запуска область подготовки — `run`,
а `fixed_pool_selection` — `null`.
