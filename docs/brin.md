# Одноколоночный BRIN (#114)

BRIN включается явно: `"index_methods": ["btree", "brin"]` в workload v2.
Можно выбрать только `["brin"]`; отсутствие поля сохраняет B-tree. Пример:
[workload-v2-brin.json](../examples/workload-v2-brin.json).

Поддержаны скалярные диапазонные WHERE (`<`, `<=`, `>`, `>=`, `BETWEEN`) на одной
колонке. Нет INCLUDE, направлений сортировки, partial/expression индексов и настройки
pages_per_range/opclass. Каталог выбирает default opclass отдельно для метода.
BRIN не размножает все B-tree варианты: после общего column cap он добавляет только
применимые одиночные определения. Лимиты 16 колонок / 32 локальных кандидата /
16 подготовленных кандидатов, резерв 48, 32 size-попытки и пределы EXPLAIN общие.
Отсутствие opclass отражается как `NO_BRIN_OPERATOR_CLASS`, без выдуманного нулевого
размера. Полные правила — [§5 спецификации](../IndexBudget-spec-v0.2.md#5-ограниченная-генерация-кандидатов-и-широкие-таблицы).

[PostgreSQL описывает BRIN](https://www.postgresql.org/docs/16/brin-intro.html)
как индекс диапазонов физических блоков, полезный при корреляции значения с
расположением строк. [HypoPG поддерживает BRIN](https://hypopg.readthedocs.io/en/rel1_stable/usage.html#supported-access-methods),
но его оценки не являются измерением времени чтения или сопровождения записи.
Отрицательный результат остаётся полноценным результатом сравнения.

## Вход, ручной набор и версии

`index_methods` — непустой массив уникальных строк `btree`/`brin`; порядок массива
не задаёт приоритет. Неизвестные методы, дубли, null и неверные типы отклоняются.
Выбор задаётся JSON для `analyze` и `analyze-series`; отдельного CLI override нет.

В `manual_indexes` можно передать:

```json
{"schema":"brin_demo","table":"events","method":"brin","keys":[{"column":"sequence"}]}
```

Без `method` остаётся B-tree. Ручной метод независим от автоматического выбора;
смешанный ручной набор оценивается целиком и не меняет incumbents поиска.
Для BRIN даже явные `direction: "asc"` и `nulls: "last"` во входе запрещены.

Workload остаётся v2 с аддитивными строгими полями. Старый reader отклоняет их,
а не выполняет другой анализ. При разрешённом или ручном BRIN выходной report имеет
**schema_version 4**, даже если выбран пустой набор или получен failed. B-tree-only
сохраняет v3. В v4 у BRIN `direction`/`nulls` равны null: сортировка неприменима.
Метод сохраняется в каждом определении и DDL; эффективный автоматический список —
в `index_methods`, HTML и SQL-заголовке. Readers v3 должны отклонять v4.

Сводка серии с BRIN имеет v2, точки — report v4; запрос серии по-прежнему v1.
B-tree-only сохраняет прежнюю сводку v1/report v3. В сводке сохраняются метод,
collation/opclass ключей; HTML использует тот же подготовленный пул. Размеры
для точек не измеряются заново. [Формат отчёта](report-v3.md),
[ручное сравнение](manual-index-comparison.md), [серии](budget-series.md).

## Реальный воспроизводимый пример

```sh
bash demo/check-brin.sh
```

Нужны JDK 25 и локальный Docker. Скрипт собирает PostgreSQL 16.15 + HypoPG 1.4.2,
создаёт собственный одноразовый контейнер и не читает общую `.env` или адрес стенда.
Тест создаёт миллион строк в `brin_demo.events`: возрастающий bigint `sequence`,
160-байтовый payload и JSON-колонку без подходящего BRIN opclass. Данные и
`VACUUM ANALYZE` готовятся до анализа; настройки планировщика не меняются.

Проверяются default opclass, размеры, полные векторы пустого/одиночных/смешанного
наборов, cleanup после успеха и ошибки opclass, повторный baseline, реальные дубли
и отличие индекса с reloptions. Реальный индекс создаётся только отдельным шагом
фикстуры для проверки каталога и удаляется до запуска pipeline. Обычный анализ
и бюджетная серия не создают физических индексов; закрытие сессий и отсутствие
новых EXPLAIN при экспорте проверяются.

Все полученные артефакты находятся в `build/brin-verification/run-*/`: workload,
`measurements.json`, два анализа (`generous`, `tight`) и серия из трёх точек.
Скрипт включён через интеграционный тест в существующий CI HypoPG; результаты
BRIN загружаются как artifact. [Сохранённый прогон](../examples/brin-recorded/measurements.json)
содержит следующие значения:

| Набор | Оценка размера, байт | С запасом, байт | Cost диапазона | Cost всех строк | Write proxy, ед./ч |
| --- | ---: | ---: | ---: | ---: | ---: |
| Baseline | 0 | 0 | 33 318,40 | 37 500,00 | 0 |
| BRIN | 24 576 | 29 492 | 23 046,75 | 37 500,00 | 115 |
| B-tree | 29 024 256 | 34 829 108 | 636,73 | 37 500,00 | 115 |
| BRIN + B-tree | 29 048 832 | 34 858 600 | 636,73 | 37 500,00 | 230 |

Это факты одного прогона PostgreSQL 16.15/HypoPG 1.4.2, а не эталон точных costs
для всех окружений: статистика и версии влияют на оценки. При бюджете 100 000 000
байт выбран B-tree; при 49 152 байтах — BRIN. Весь миллион строк имеет тот же cost
с каждым набором: отрицательный результат сохранён. Смешанный набор не лучше
B-tree по cost диапазона, но требует больше места и proxy units. Выбранные
robust/mean совпали; различие критериев здесь не заявляется.

Согласованные артефакты двух запусков:

- Большой бюджет: [HTML](../examples/brin-recorded/generous/report.html), [JSON](../examples/brin-recorded/generous/report.json), [SQL](../examples/brin-recorded/generous/indexes.sql).
- Малый бюджет: [HTML](../examples/brin-recorded/tight/report.html), [JSON](../examples/brin-recorded/tight/report.json), [SQL](../examples/brin-recorded/tight/indexes.sql), [workload](../examples/brin-recorded/workload-tight.json).

Ручной смешанный набор при малом бюджете измерен отдельно и отмечен недопустимым
по месту. Write proxy равен для одиночных B-tree и BRIN только из-за общей формулы
по числу колонок: это **не доказательство одинаковой реальной цены записи**.
Фактические задержки, размер физических индексов, TPS и WAL этот эксперимент
не измеряет. Costs нельзя переводить в обещание ускорения или SLA.
